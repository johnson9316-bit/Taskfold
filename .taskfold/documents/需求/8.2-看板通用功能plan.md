## 实施决策

### 1. Board 就是 Project

M2 的用户术语为“项目”，但持久化与既有兼容接口继续使用 Board：

```text
Project (UI / M2 domain)
        =
taskfold_boards row (storage / M1 compatibility)
└── Milestone (看板列)
    └── Requirement Card (需求卡片 / 具体小需求)
        └── taskfold_cards.board_id + milestone_id (card ownership)
```

不创建 `projects` 表，不引入 `project_id -> board_id` 映射，也不重建或重映射既有 Board/Card 数据。M2 只为 Card 新增可空的 `milestone_id`：历史卡片保留为空，并显示在系统“未归属”迁移列。这一选择直接复用现有的 ID 校验、Board 汇总、归档、默认工作区和按 Board 筛卡逻辑，并避免两份项目真相。

### 2. 结构轴与执行轴必须分离

M2 的通用看板不是“可改名称的状态列”，而是将每张 Card 的两个正交维度分开保存：

```text
项目结构轴（用户组织）                 执行生命周期轴（M1 保留）
Board -> Milestone -> Card position    Card.status + claim + execution + attempts
```

- `milestoneId + position` 是主看板唯一的列归属和列内排序依据。拖拽、排序、创建到列、跨项目移动都只写这一轴。
- `status` 继续是固定的 M1 执行状态机。领取、派发、依赖提升、心跳、阻塞、解除、完成、回收、诊断和 agent tools 仍以它为准；M2 不删除、重命名或放宽这些状态及其校验。
- 既有 `taskfold.cards.move(id, status, position)`、`taskfold_move`、`openclaw taskfold move --status` 继续表示**状态流转**，以保留 M1 API 与 agent 行为。`position` 为旧调用形状保留，但在 M2 中不得改变列内位置；M2 UI 的列间移动不得调用它。
- 新增专门的 `moveMilestone` 操作。它不得写 `status`、claim、execution、attempts、startedAt、completedAt 或生命周期来源时间；同理，任何状态操作不得改写 `milestoneId` 或列内 `position`。
- 事件语义也必须分离：既有 `moved` 继续记录状态变化；新增 `milestone_moved` 记录跨列移动，并携带 `fromMilestoneId` / `toMilestoneId`。仅调整同列顺序不创建状态迁移事件。

### 3. 里程碑列、项目配置与资料库

项目仍然只有一个持久化主实体：`taskfold_boards`。M2 在其上增加项目概览字段：

```text
version, current_objective, core_value,
source_of_truth, repository_url, planning_path
```

`description` 继续承载简短项目简介；当前状态、需求、路线图、复盘和环境说明进入资料库，避免把长文塞入 Board 行。

新增 `taskfold_milestones`，它是 M2 看板列的唯一真相：

```text
id, board_id, title, description, color, position,
state, created_at, updated_at, completed_at, archived_at
```

- `board_id + position` 决定列顺序；`state` 只表示里程碑是否 active、completed 或 archived，不定义 Card 工作流，也不复用 Card `status`。
- Card 增加可空 `milestone_id` 与 `board_id + milestone_id + position` 索引。Card `position` 自 M2 起只在所属里程碑列内排序；既有 `status` 字段保持不变，但不再决定 M2 主看板的列。
- 迁移前已有 Card 的 `milestone_id` 保持为空；UI 将空值显示为系统“未归属”迁移列，不伪造为真实里程碑。
- 新项目创建时在同一事务中使用用户输入的首个里程碑名称创建首列和基础资料条目；后续新 Card 必须选择一个 active 里程碑。

新增 `taskfold_project_documents`，以 `board_id` 关联既有 `taskfold_boards`。最小字段为：

```text
id, board_id, key, section, type, title, summary,
target, content, position, hidden_at, created_at, updated_at
```

- `section` 固定为 `project`、`codebase`、`environment` 或 `knowledge`。
- `type` 固定为 `markdown`、`json`、`link`、`path` 或 `secret_ref`。
- `markdown` 和 `json` 使用 `content`；`link`、`path` 和 `secret_ref` 使用 `target`。`secret_ref` 只允许名称、环境变量名或受控路径，不允许保存凭据值。
- 标准 `key` 覆盖 `project`、`config`、`requirements`、`roadmap`、`state`、`retrospective`、`architecture`、`concerns`、`conventions`、`integrations`、`stack`、`structure`、`testing`、`dev_environment`、`test_deploy`、`notes`、`research`、`todos`、`seeds` 和 `onboarding`；里程碑以 `taskfold_milestones` 为唯一真相，不再创建重复的 Markdown 里程碑清单。
- 用 SQLite `CHECK`、运行时 normalizer 和 Gateway 校验共同限制 section、type、key、长度、URL、路径、JSON 和 Markdown 输入。`path` 只作语法和长度校验，不执行 `stat`、文件读取或工作区授权。
- 保持 `STRICT` 表、外键、位置索引、`node:sqlite` 与现有键值 Store 抽象；不新增另一份数据库。
- M2 不导入 `.planning` 文件：资料库只借鉴其目录组织。`planning_path` 仅记录入口路径，真实文件投影留给 M4。

### 4. API 保持兼容，新增范围最小

- 继续保留 M1 的 `taskfold.boards.*` 和 `taskfold.cards.*`；不因 UI 文案改为“项目”而破坏已有脚本和 manifest data binding。
- `taskfold.cards.move` 保留为 Card 状态流转接口；不为它增加 `milestoneId` 参数，也不让它承担主看板拖拽。它接受旧 `position` 参数以保持请求兼容，但 M2 实现忽略该参数。
- 新增 `taskfold.projects.milestones.list/create/update/reorder/complete/archive/restore` 和 `taskfold.cards.moveMilestone`；拖拽列间卡片只调用后者，并明确传入目标里程碑和列内位置。
- 新增 `taskfold.projects.documents.list/create/update/hide/restore/delete`，名称反映 M2 用户语义，内部以 `boardId` 作为项目 ID。
- 新增专门的 `taskfold.cards.moveProject`，而不是允许通用 `cards.update` 隐式修改 `automation.boardId`。
- `taskfold_move` 保留为 agent 的状态流转工具；新增 `taskfold_move_milestone`。CLI/slash command 保留 `move --status`，并增加 `project milestone move-card`；所有入口只包装相同 Store 方法，不能复制业务逻辑。

## 实施步骤

### 阶段 0：建立 M2 变更基线

1. 在完成的 M1 提交上记录依赖锁定、OpenClaw 版本和 taskfold SQLite schema 版本。
2. 导出现有 Board/Card 数据样本：至少包含 `default` Board、显式 Board、卡片、评论、关联、附件和已归档卡片。
3. 为 M2 增加测试入口。测试必须能创建临时 SQLite 数据库，并覆盖 Store、Gateway 与 UI 冒烟；当前仓库没有可复用测试目录时，按 M1 实际的构建工具补齐最小测试约定。

**完成信号**：M1 可安装且测试样本可重复加载；开始 M2 前后能比较 Board/Card 数据。

### 阶段 1：扩展契约与持久化

修改范围：

- `src/contract/index.ts`
- `src/backend/src/persistence-types.ts`
- `src/backend/src/store-inputs.ts`
- `src/backend/src/store-normalizers.ts`
- `src/backend/src/sqlite-store.ts`
- `src/backend/src/store.ts` 与其现有继承层

实施内容：

1. 扩展 `TaskfoldBoardMetadata` 与 Board input/normalizer/SQLite serializer，加入版本、当前目标、核心价值、权威来源、仓库地址和规划目录字段。
2. 定义 `TaskfoldMilestone`、创建 Card 所需的 `milestoneId` 输入及其输出契约；将 `milestoneId` 和列内 `position` 从通用 Card update 移除，只允许专用里程碑移动方法写入，保留 Card `status` 契约，避免把里程碑与状态混为一层。
3. 定义 `TaskfoldProjectDocument`、资料区、资料类型、标准 key、创建/更新输入和列表结果；项目 ID 在契约中明确为现有 `boardId`。
4. 扩展 Card 事件契约、normalizer 和 SQLite 事件表：加入 `milestone_moved`、`from_milestone_id`、`to_milestone_id`；调整事件生成逻辑，使状态变更和结构移动不再共用 `moved` 的含义。
5. 将 `SCHEMA_VERSION` 从 3 升至 4：为 `taskfold_boards` 增加上述可空列，增加 `taskfold_milestones` 和 `taskfold_project_documents`，为 Card 增加可空 `milestone_id`，为事件增加列归属字段，并建立 `(board_id, milestone_id, position)`、列排序与资料排序索引。
6. 按现有 `TaskfoldKeyedStore` 模式增加 `PersistedTaskfoldMilestone`、`PersistedTaskfoldProjectDocument`、SQLite Store、`open()` 的内存命名空间和 `openSqlite()` 注入，确保测试和 SQLite 运行时走同一业务 API。
7. 在 Store 中实现里程碑和文档的列出、新增、编辑、排序、完成、归档、恢复和删除；所有写入走 `enqueueMutation()`，从而继续触发现有 `plugin.taskfold.changed` 刷新事件。
8. 实现幂等的项目初始化：新项目在同一事务中创建用户命名的首个里程碑和基础资料条目；M1 Board 升级后首次打开或显式迁移时补齐资料目录，但不伪造里程碑或改变已有 Card 的空归属。
9. 保存前校验项目存在或可从已有卡片推导；验证 JSON；拒绝不合规的 key/section/type；`secret_ref` 不提供秘密值字段或导入路径。
10. 实现里程碑完成前置校验：仅当列内未归档 Card 都处于 M1 终态时允许写入 `completed_at`；拒绝时返回未完成 Card 的稳定 ID 和标题，且不修改任何 Card 状态。

**完成信号**：新旧 SQLite 均可打开；升级不改写任何既有 Card 的 status、执行数据或历史；里程碑列、卡片归属/排序、状态与列归属解耦、项目配置、四个资料区、标准目录、五种资料载体的 CRUD/排序/隐藏均有单元测试。

### 阶段 2：把现有 Board 提升为项目行为

修改范围：

- `src/backend/src/store-core.ts`
- `src/backend/src/store-card-helpers.ts`
- `src/backend/src/store-automation.ts`
- `src/backend/src/store-normalizers.ts`
- `src/backend/src/gateway-workspace-methods.ts`
- `src/backend/src/workspace-access.ts`

实施内容：

1. 提供 Project 看板视图结果：基于 `listBoards()` 返回的摘要、设置和卡片计数，并按里程碑返回有序列和其卡片；不创建第二份项目数据。
2. 兼容“仅卡片引用、没有显式 Board 记录”的历史数据：项目列表必须显示这类 Board；第一次保存设置时才通过现有 `upsertBoard()` 固化其元数据。`default` Board 按同样规则可配置。
3. 将已归档 Board 视为已归档项目：默认项目列表隐藏；恢复前拒绝在其中创建卡片、将卡片移入或发起新派发；历史卡片仍可通过归档视图读取。归档不会取消已有 run，Store 必须返回运行中 Card 摘要，供 UI 在确认前展示。
4. 在项目上下文创建卡片时，将 `TaskfoldBoardMetadata.defaultWorkspace` 合并为卡片 automation workspace。显式卡片工作区优先；继承前必须沿用 Gateway 的工作区权限校验，不能因为默认值保存在数据库中而绕过目录授权。
5. 实现专门的卡片跨里程碑移动 Store 方法：验证目标里程碑属于同一项目且为 active，原子更新 `milestoneId` 与列内 position，并记录 `milestone_moved`；不得写 Card `status` 或调用 `cards.move`。
6. 实现专门的跨项目移动 Store 方法：验证源卡片、目标项目、目标里程碑和归档状态，原子更新 `boardId + milestoneId`，并保留卡片其余元数据、父子关系和一般关联。UI 在调用前负责二次确认；Store 不接受“悄悄改 Board”的通用 patch。
7. 将既有 `store.move()` 收紧为状态流转兼容层：保留其参数形状，但忽略旧 `position` 输入；通用 `cards.update` 也不得修改 `milestoneId` 或列内 position。

**完成信号**：历史 Board 自动作为项目出现；默认工作区正确继承且不越权；里程碑排序、卡片跨列、归档和跨项目移动的正反路径都有测试。

### 阶段 4：UI 改造

M1 完整导入的 UI 源码路径以实际仓库落点为准。修改必须沿用其 Lit 组件、状态管理、样式和 Gateway 调用方式，不新建 React/Tailwind/shadcn 子应用。

实施内容：

1. 将用户可见的“Board”入口改为“项目”，增加项目列表、搜索、排序和“全部项目”总览。总览按项目分组，不将不同项目的里程碑列合并或跨项目重排。
2. 在项目页组织项目头部、里程碑看板、项目配置和资料库；项目详情、设置和资料使用清晰的视图切换，而非嵌套卡片。
3. 用里程碑列替换现有 `STATUSES.map(renderColumn)` 主看板。Card 状态以紧凑徽标、详情操作和筛选保留，不再渲染为主列；列间拖拽调用跨里程碑移动，状态控件仍调用既有状态流转接口。
4. 项目内建卡固定当前 Board ID 和当前里程碑；M1 遗留的空归属卡片显示在“未归属”迁移列。
5. 跨项目移动使用目标项目和目标里程碑选择器以及确认对话；已归档项目、完成或归档的里程碑不可选。确认界面必须说明既有依赖和关联会保留。
6. 项目配置页包含项目概览、当前版本/目标、权威来源、仓库/规划路径和默认工作区；长文不塞入设置表单，转入对应资料条目。
7. 资料库按“项目、代码库、环境与发布、知识沉淀”分区；新项目显示标准资料目录，支持 Markdown、JSON、链接、本地路径和密钥引用的表单、列表、排序、隐藏、恢复、编辑和删除。本地路径只作为文本资料，不触发读取、存在性检查或目录授权。
8. 环境资料和密钥引用必须有明确安全提示；JSON 使用格式校验；路径和链接按类型显示，Markdown 使用 M1 的安全渲染方案。
9. 为列内排序和列间移动提供可复核的拖拽以及键盘/菜单后备操作；处理空项目、仅历史卡片项目、未归属迁移列、加载错误、保存失败、归档项目和窄屏布局；归档存在运行中 Card 时要求确认；总览、项目列表和项目头部不能遮挡现有看板操作。

**完成信号**：按照 [[8.2-需求]] 的多项目、设置、资料、归档和卡片归属闭环，在实际 OpenClaw Tab 中可完成。

### 阶段 5：迁移、回归与分发

1. 在 M1 数据样本上启动 schema 4：确认 Board 扩展字段默认为空、标准资料目录幂等补齐、既有卡片保留在未归属迁移列；Board/Card ID、状态、位置、内容、评论、关联、附件、运行信息和历史事件不变。
2. 重复启动和重复访问项目列表，确认不会创建重复 Board、重复标准资料、重复里程碑或隐式移动卡片。
3. 运行 M1 的完整功能冒烟，并追加 M2 的九类验收。
4. 在原生 `workboard` 同时启用时，重复项目创建、里程碑/卡片拖拽、归档、项目配置和资料库操作；确认没有 Gateway、CLI、tools、Tab 或 SQLite 路径冲突。
5. 提交 M2 变更、更新 README 和迁移说明；从干净 Git clone 安装后执行新建项目和 M1 数据升级两条验证路径。
