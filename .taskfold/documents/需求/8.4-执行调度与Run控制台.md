# 开发任务执行与 Run 控制台（评审稿）

> 状态：待审核。本文件从 [[8.4-GSD内化与开发执行集成]] 中抽出“开发执行”部分，目的是先评审一个用户真正可操作的执行闭环。批准前不改写现有 M4 路线图，也不改变其 GSD 投影范围。
>
> **执行后端以 [[8.7-待开发一波]] 为准：** Taskfold 通过 `ACP Runner` 直接调用
> OpenClaw 公共 ACP Runtime 和官方 `@openclaw/acpx`。本文件的 Run、UI、账本和安全语义
> 继续有效；其中旧的 `coding-agent` / `AgentRunner` 表述均已由 ACP 术语取代。

## 现状判断

当前 Taskfold 已有一套从 OpenClaw Workboard 继承的通用派发后端：

- `taskfold.cards.dispatch` 能挑选 `ready` Card、领取任务、创建隔离 worktree、启动 OpenClaw subagent，并把 `runId`、`sessionKey`、执行状态和有限 worker log 写回 Card。
- CLI、slash command、Gateway 与 agent tool 已有派发入口；Card 也保存 claim、execution 与 attempts。
- 新项目看板只展示 Card 结构、状态和交付事实，没有“开始执行”、运行详情、终止、接管或恢复入口。

因此，当前用户在看板中把 Card 改为 `ready`，并不会从界面启动实际开发；现有 `dispatch` 更像兼容性的批量后台能力，不是可审计、可由人确认的产品工作流。

现有能力不能直接作为 M4 交付，原因如下：

| 已有实现 | 仍缺少的产品能力 |
|---|---|
| Card 级 `execution`、`attempts`、worker log | 独立、不可混淆的 `runs` / `run_events` 账本 |
| 批量挑选 ready Card 并启动 subagent | 对某一张 Card 的预检、`dry_run`、显式确认和启动结果 |
| 临时 worktree 与工作区授权检查 | Git 基线、repo 互斥、清理结果、允许目录/命令/网络/预算策略的可见审计 |
| Card 的 `running` / `blocked` / `done` 状态 | `queued`、`running`、`awaiting_human`、`failed`、`aborted` 等 Run 生命周期 |
| 有限 worker log 和 Card 事件 | Run 详情、摘要时间线、人工回复、终端接管命令、重启后 reconciliation |
| CLI / Gateway 的派发入口 | M3 项目看板内的启动、观察、终止和恢复体验 |

## 目标

让用户能从一张 Taskfold Card 发起一次经过人工确认的开发任务，并在同一处回答：

1. 这次执行会改哪个仓库、使用哪个 agent、在什么 worktree 中运行？
2. 它现在是否正在运行、卡在哪里、是否需要人决定？
3. 人能否停止它、回复它，或进入真实终端接管同一个会话？
4. 这次执行的结果、关键事件、工作区和成本摘要能否在重启后追溯？

Taskfold 是调度与审计层，不是代码执行者。真实开发由 `Taskfold ACP Runner` 经 OpenClaw
ACP Runtime 和官方 `@openclaw/acpx` 启动的 harness 负责；Taskfold 不复制完整 transcript，
不在浏览器中伪造终端。

## 核心决策

### 第一版先服务普通 Card

第一版可从任意活跃项目中的 Card 启动，不要求项目已经接入 GSD，也不扫描、导入或写入 `.planning/`。

- GSD phase、plan、wave 在后续投影完成后作为可选 `run` 关联字段补入。
- 启动不依赖某个 `.planning` 文件存在，避免“我只是要执行 `提交git`”被 GSD 接入阻塞。
- 未来 GSD 投影可为 Run 提供额外上下文、准入 gate 与关联视图，但不得替换本文件定义的 Run 账本。

### Run 与 Card 状态分离

Card 的 `status` 是需求生命周期；Run 的 `status` 是一次执行会话生命周期。二者有关联，但不得互相冒充：

| 事件 | Card 状态 | Run 状态 | 交付事实 |
|---|---|---|---|
| 用户确认启动 | `todo` / `ready` 可启动；宿主接受后更新为 `running` | `queued` -> `running` | 不改写 |
| agent 需要决定 | 保持 `running`，显示“需要你处理”标记 | `awaiting_human` | 不改写 |
| agent 正常结束 | 转为 `review`，等待人验证 | `done` | 不推断验证或发布通过 |
| agent 启动失败、失败或人工终止 | 转为 `blocked`，记录原因 | `failed` / `aborted` | 不改写 |
| 人确认验收 | 由现有 Card 操作转为 `done` | 保留历史 | 由人更新验证/发布事实 |

`awaiting_human` 绝不自动跨过。Run 成功也不等于验证完成、发布完成或 Card 已完成。

### 单项目、单 repo、单 active Run

- 同一规范化仓库根目录同一时刻只允许一个 `queued`、`running` 或 `awaiting_human` Run。
- 每个 Run 在受控 Git worktree 中运行；绝不在用户主工作区直接写代码。
- 多 repo 可各自运行一个 Run；同 repo 多 worktree 并行、自动合并与 wave 并行留给 [[8.5-流程规划与Skills增强]]。
- 新 Run 只能由用户点击确认或明确的 CLI / Gateway 调用启动；不在本阶段自动派发、cron 巡检或 AI 自动开工。

## 用户体验

### Card 详情

在 Card 详情增加 `执行` 区域，按当前状态显示以下动作：

| 条件 | 用户可见动作 |
|---|---|
| 无活跃 Run，Card 未归档且项目活跃 | `预检并启动` |
| 预检通过、尚未确认 | `查看执行计划`、`确认启动`、`取消` |
| Run `queued` / `running` | `查看运行详情`、`终止运行` |
| Run `awaiting_human` | `查看问题`、`记录决定并继续`、`终端接管`、`终止运行` |
| Run 已结束 | `查看结果`、`基于此 Card 重试` |

`预检并启动` 打开确认对话框，而不是直接启动。对话框必须展示：

- 项目、Card、默认工作区与规范化仓库根目录。
- Git HEAD、工作树是否干净、将创建的 worktree 名称和路径。
- 目标 agent / provider / model、执行模式、预估上下文来源。
- 将要传给 agent 的上下文包摘要；`dry_run` 可查看完整文本但不创建 worktree 或会话。
- 当前 repo 是否有活跃 Run；有则明确拒绝并提供跳转。
- 本次适用的权限、预算、目录、命令与网络策略摘要。

### 项目执行视图

项目页增加 `Runs` 标签，与 Board、Settings、Documents 并列：

- 默认显示活跃 Run，支持查看最近结束的 Run。
- 每行显示 Card、Run 状态、agent、开始时间、最后事件、等待人工原因和 worktree 状态。
- `awaiting_human` 项必须在项目页和 Card 上显著可见，不依赖用户翻进详情。
- Run 详情按时间线展示摘要事件、预检结果、人工回复、错误、终止结果和清理结果；不展示或存储完整宿主 transcript。

窄屏优先显示活跃 Run 与“需要你处理”，详情进入单独视图；不将时间线压进看板列。

## 数据与接口

SQLite schema 在当前 v5 之后升级。Run 是独立实体，不再仅以 Card 的 `attempts` 元数据承载。

```text
taskfold_runs
  id, card_id, board_id, repository_root,
  status, backend, agent_id, provider, model,
  host_ref_kind, host_ref_id, resumable_session_id,
  source_workspace, worktree_path, worktree_branch,
  git_head_before, git_head_after,
  context_digest, policy_digest,
  awaiting_reason, result_summary, failure_summary,
  started_at, ended_at, created_at, updated_at

taskfold_run_events
  id, run_id, kind, summary, detail_json,
  actor_type, actor_id, created_at

taskfold_execution_policies
  board_id, enabled, default_agent_id,
  max_runtime_seconds, max_cost_usd, max_daily_cost_usd,
  allowed_workspace_roots, allowed_command_groups,
  network_mode, updated_at
```

- `host_ref_kind + host_ref_id` 指向 ACP Runtime 的 session / run handle；它是状态查询、终止、关闭和接管的外部关联键。
- `resumable_session_id` 只在当前 ACP harness profile 已验证可恢复时写入；没有它时，`takeover` 必须明确返回“此 Run 不支持终端接管”，不能伪造命令。
- `context_digest`、`policy_digest` 只保存摘要与哈希；完整 prompt 仅在用户显式 `dry_run` 时返回给当前调用者，不长期保存。
- `run_events.detail_json` 只保存经过字段白名单的结构化摘要；不得保存 token、密钥、环境变量值、完整命令输出或完整 transcript。
- Card 保留现有 `execution` 与 `attempts` 作为 M1 兼容投影；它们不再是 Run 的唯一真相。迁移不删除历史 attempts。
- 第一版复盘文件写入 `<TASKFOLD_HOME>/runs/<project>/<run>/`。未验证 gsd-core 归档行为前，不向 `.planning/phases/**/runs/` 写入任何文件。

新增 Gateway / CLI / tool 契约：

| 操作 | Gateway | 说明 |
|---|---|---|
| 预检 | `taskfold.runs.prepare` | 返回可启动性、阻塞原因与完整 `dry_run` 上下文；无副作用。 |
| 启动 | `taskfold.runs.start` | 只接受 prepare token / 版本与显式确认，防止预检后环境已变化仍盲目启动。 |
| 列表 | `taskfold.runs.list` | 按项目、Card、状态、时间过滤。 |
| 详情 | `taskfold.runs.get` | 返回 Run、摘要事件、可用动作与脱敏引用。 |
| 人工回复 | `taskfold.runs.reply` | 只允许 `awaiting_human`；写入事件与 `HANDOFF.md`。 |
| 终止 | `taskfold.runs.abort` | 调宿主取消；失败也必须记录“取消未确认”。 |
| 接管 | `taskfold.runs.takeover` | 返回已验证的终端命令与 cwd，或明确不可接管的原因。 |
| 重试 | `taskfold.runs.retry` | 重新走 prepare / confirm，不复用旧 worktree。 |

旧 `taskfold.cards.dispatch` 保留给 M1 兼容与运维，不作为项目 UI 的启动接口。M4 的启动、
观察、终止和关闭均只能经过 `ACP Runner`；旧 dispatcher 不得成为第二条执行后端。

## 安全与准入

Run 启动必须全部通过以下检查；任一失败均不得创建 worktree 或宿主会话：

1. 当前 Gateway 调用者具备 `operator.write`，项目和 Card 均未归档。
2. Card 不是 `done`，没有未结束的 Run，且 repository root 可由当前调用者的允许工作区规范化验证。
3. 目标路径是 Git 仓库；记录 HEAD、分支、dirty 状态和 submodule 状态。
4. 仓库根目录没有其他活跃 Run；worktree 创建、命名、路径和清理策略均可预览。
5. agent、provider、model、目录权限、原生命令、网络模式与预算均命中项目执行策略。
6. 上下文来源仅来自 Card、已授权的项目 Documents、明确绑定的 GSD 投影（未来）和受控的 Skill profile；禁止读取任意路径或将 Documents 当作执行脚本。
7. 发现 `.env`、私钥、凭据文件或未授权路径时只报告风险，不读取、不复制、不传入 prompt。

人工终止不承诺回滚代码。系统只负责请求宿主停止、记录最终可确认状态、保留 worktree，并在安全时提供显式清理操作。

## 宿主适配验证门

在写业务代码前，必须针对当前实际 OpenClaw 版本完成最小 Spike，并把结果写入实现记录：

1. 能否从插件直接加载 `openclaw/plugin-sdk/acp-runtime`，按指定 `cwd` 为官方 `@openclaw/acpx` harness 调用 `ensureSession` / `startTurn`，并得到稳定的持久化 handle。
2. 能否获得结构化 turn event、`getStatus` 状态、结束结果和可区分的失败原因。
3. 能否对仍在运行的任务调用 `cancel` / `close`；取消请求与最终确认如何区分。
4. 各 harness profile 是否存在可恢复 session；若存在，其真实终端接管命令与 worktree `cwd` 是否可用。Claude Code、Codex、OpenCode 分别记录，禁止通用化假设。
5. restricted workspace 下，Taskfold 创建 worktree、ACP harness 写权限、项目 MCP 与 Skills 是否都符合权限边界。
6. Gateway / 插件重启后，能否以持久化 ACP handle 对账仍在运行、已结束或不可确认的任务。

任一关键能力不具备时，功能按降级路径实现或暂停：

- 没有可靠取消：只允许“标记需人工处理”，不把按钮命名为“已终止”。
- 没有可恢复 session：隐藏接管命令，保留人工处理指引。
- 没有事件流：先做轮询摘要，不伪造实时日志。
- 不能安全创建 worktree：拒绝执行，不降级为主工作区写入。

## 分阶段实现

### 阶段 A：宿主 Spike 与领域契约

- 完成上述 OpenClaw API 验证和一个真实 Git 仓库的 start / observe / abort / resume 实验。
- 定义 `Run`、`RunEvent`、`ExecutionPolicy`、prepare token 与状态机契约。
- 决定 Card 与 Run 的状态映射，补齐 schema 迁移与历史 Card attempts 的兼容读法。

完成信号：可以用测试 double 覆盖状态机，并用真实 ACP Runtime 证据证明至少“`ensureSession`、`startTurn`、观察、取消请求、重启后识别”五项事实。

### 阶段 B：安全启动与账本

- 把现有 dispatcher 的 worktree、claim 与 workspace 授权逻辑提取为确定性的 Git / 准入适配器；实现唯一的 `ACP Runner`，封装 `ensureSession`、`startTurn`、`getStatus`、`cancel` 和 `close`。
- 实现 `prepare` / `start` 的乐观并发保护、repo 互斥、Git 基线、独立 Run / Event 持久化和复盘目录。
- 为启动失败、worktree 清理失败、宿主接受后本地落账失败分别定义补偿与人工恢复记录。

完成信号：从 CLI 与 Gateway 对一张普通 Card 进行 `dry_run` 和确认启动；Run、worktree、宿主引用和摘要事件均可对账。

### 阶段 C：项目 UI 与人工处理

- 在 Card 详情实现预检、确认、启动、活跃状态、运行详情、终止和重试。
- 增加项目 Runs 视图与 `awaiting_human` 的显著入口。
- 接入 reply / takeover；无法接管时给出原因和工作区位置，不生成伪命令。

完成信号：用户无需 CLI 即可从一张 Card 发起、观察并处理完整一次 Run。

### 阶段 D：恢复、审计与 GSD 可选绑定

- Gateway 启动时做 reconciliation，将 Run 标记为恢复、已结束、异常或需人工处理。
- 完善复盘档、清理操作、失败重试和运行历史。
- 在 [[8.4-GSD内化与开发执行集成]] 的投影稳定后，为 Run 增加可选 phase / plan / wave 关联与上下文来源；不改变普通 Card 的启动路径。

完成信号：服务重启后没有无解释的永久 `running` Run；每个活跃或异常 Run 都有可执行的下一步。

## 非目标

- 不做 GSD 扫描、reindex、phase / plan / wave 展示或 `.planning/` 写回；这些继续由 [[8.4-GSD内化与开发执行集成]] 定义。
- 不做同 repo 多 Run 并行、自动合并、冲突解决、WIP 自动排程或 cron 巡检。
- 不做 AI 自动开工、自动批准权限、自动跨过 `awaiting_human` 或自动把 Card 标记为 `done`。
- 不做浏览器终端、transcript 镜像、密钥管理、云端同步、多人协作或第二套执行服务。
- 不将 Documents、来源资料、Proof 或 Artifact 自动作为 prompt 的全部内容；执行上下文必须显示来源并由用户确认。

## 验收标准

1. **普通 Card 启动**：在没有 `.planning/` 的项目中，用户能从一张 `todo` 或 `ready` Card 完成预检、查看 `dry_run`、确认启动；系统只创建一个隔离 worktree 和一个 Run。
2. **安全拒绝**：归档项目/Card、无权限工作区、非 Git 路径、dirty 基线不符合策略、同 repo 有活跃 Run、缺少 agent 或预算超限均被明确拒绝，且没有创建宿主任务。
3. **运行可见**：项目 Runs 视图与 Card 详情均能看到活跃 Run 的状态、最后摘要事件、agent、worktree 和“需要你处理”原因。
4. **人工边界**：Run 成功只将 Card 送往 `review`；验证、发布和最终 `done` 均需人工操作。`awaiting_human` 只能由 reply、takeover 或 abort 结束。
5. **终止与接管**：用户可请求终止；结果以宿主确认状态记录。仅在真实支持时显示终端接管命令，并在实际 worktree 中验证可用。
6. **恢复与审计**：重启后每个未结束 Run 都进入恢复、异常或需人工处理之一；Run / Event / worktree / 宿主引用可追溯，且不保存完整 transcript 或秘密值。
7. **兼容**：现有 Card、execution、attempts、CLI、slash command、agent tools 与 `taskfold.cards.dispatch` 不被破坏；项目看板的里程碑归属、状态和 M3 delivery 不被 Run 写入错误改写。
8. **真实宿主验收**：在可信 OpenClaw Control UI 中完成桌面与移动端的预检、启动、运行详情、终止、错误态和恢复冒烟；同时保留 Gateway、CLI、Store 与 SQLite 迁移测试。

## 需你确认的决策

| 决策 | 建议 | 可选方向 |
|---|---|---|
| 首版是否允许无 GSD Card 执行 | 是，先解决通用项目看板的“执行”按钮 | 也可强制只执行关联 GSD plan，但会延后可用性 |
| 启动入口 | Card 详情的“预检并启动”，必须确认 | 也可只提供项目 Runs 页批量入口；不建议 |
| Card 成功后的状态 | 自动进入 `review`，由人完成验收 | 自动 `done` 不建议，会混淆代码运行与交付事实 |
| `awaiting_human` 时 Card 状态 | 保持 `running`，以 Run 状态表达等待 | 自动改 `blocked` 会使可继续的会话语义变差 |
| Git dirty 策略 | 默认拒绝；未来可项目级显式放宽 | 默认允许不建议，难以可靠复盘 |
| 复盘文件位置 | 首版 `<TASKFOLD_HOME>/runs/` | 通过 gsd-core 归档验证后再考虑 `.planning/phases/**/runs/` |
| 未验证的宿主能力 | 先 Spike，按降级路径实施 | 不建议基于旧文档或推断直接承诺接管 / 实时流 |
