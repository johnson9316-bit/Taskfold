# 竞品与替代方案

> 调研日期：2026-07-28。资料来自公开 GitHub README 与仓库 API；功能和活跃度会变化，开工前应再次核实。

## 结论

此前文档有“开源项目选型”，但缺少以用户替代路径、产品重叠和差异化为中心的竞品分析。这个缺口已补上。

taskfold 不能把“AI agent 看板”“多 agent 调度”或“worktree 隔离”当作核心卖点。这一赛道已经有成熟或快速迭代的社区产品。可成立的定位是：

> **面向个人开发者的 GSD 工作控制台：以 `.planning/` 为流程真相，呈现 GSD 的 phase / plan / wave，并在需要时把 agent 执行、人工接管和复盘关联回同一条 GSD 交付链路。**

GitHub 公开检索到 GSD 原生看板/同步项目，但未发现已经形成明显社区规模、同时覆盖 GSD 文件兼容、可视化和 agent 执行调度的产品。这不是“没有竞争”，而是细分切口尚未被明确占据；必须尽快用真实 GSD 用户验证需求。

## 竞争格局

| 分组 | 用户可替代的选择 | 对 taskfold 的意义 |
|---|---|---|
| GSD 原生 | `claude-gsd-jira-plugin` | 证明用户需要将 GSD 生命周期映射为可视化工作流；但它把数据同步到 Jira，不解决本地控制台和执行调度。 |
| 通用 agent 调度台 | dev-3.0、kanbots、hopeitworks；Vibe Kanban 为体验基准 | 仍是最大威胁。活跃项目已覆盖多 CLI、并行、worktree、实时观察、人工介入等大部分“调度”功能；Vibe Kanban 可用于研究体验与迁移路径。 |
| Agent 原生规划 | Roadmap Skill、Beads | 覆盖 local-first、依赖图、MCP 与任务状态；taskfold 不能只做又一个任务数据库。 |
| 通用研发管理 | Plane、Linear、GitHub Projects、Planka、Kanboard | 解决协作和看板，但不理解 GSD 产物与阶段循环。个人开发者不是它们的最优用户。 |

## 重点竞品

| 项目 | 已覆盖能力 | 与 taskfold 的重叠 | 关键差异与策略 |
|---|---|---|---|
| [Vibe Kanban](https://github.com/BloopAI/vibe-kanban) | 多 coding agent、并行/串行编排、任务状态、工作树、开发服务器、MCP 配置集中管理、远程项目 | 高。README 已声明项目正在逐步停止维护（sunsetting）；2026-07-28 API 快照约 27.5k stars、Apache-2.0。 | 不与其比“支持多少 agent”，也不把它视为持续演进的直接威胁。保留为体验与并发调度的基准，并关注其用户迁移需求；差异化仍是 GSD 文件、阶段 gate、phase/plan/wave 可视化和交付复盘。 |
| [dev-3.0](https://github.com/h0x91b/dev-3.0) | 明确面向个人开发者；Kanban、每任务 worktree、tmux、跨项目活动面板、多 CLI、需要人关注的提醒 | 高。它的“个人 agent fleet cockpit”定位与目标用户直接重叠。2026-07-28 API 快照 229 stars、Apache-2.0。 | 它不强制流程，主张通过 agent 的 MCP 接入 Linear/Jira。taskfold 应主打“GSD 决策与产物本身就是界面和调度约束”，而非取代终端预览体验。 |
| [kanbots](https://github.com/leodavinci1/kanbots) | 本地 SQLite、11 个 agent CLI、每 run worktree、实时 tool 流、决策暂停/继续、MCP、显式 promote、autopilot | 很高。其 local-first 与人工接管能力已接近规划中的执行调度层。 | 它以通用 issue 为中心，数据在 `.kanbots/`；没有 GSD `.planning/` 兼容和 GSD 阶段语义。避免复制其通用 issue/运行时设计，把重点放在 GSD 投影和可追溯交付链。 |
| [hopeitworks](https://github.com/zkarahacane/hopeitworks) | 可配置 pipeline、依赖 DAG、容器/微虚拟机隔离、审查、PR/CI、HITL、成本与恢复；声明可接受 GSD/BMAD/Jira/Markdown | 方向重叠最广，尤其是“计划到 PR”的自动化。 | 它明确是流程无关的重型执行平台，依赖 Docker、Postgres 和队列。taskfold 保持个人本机、GSD 固定流程、复用 OpenClaw 生态，不追赶企业级运行基础设施。 |
| [claude-gsd-jira-plugin](https://github.com/Dumorro/claude-gsd-jira-plugin) | 通过 Claude Code hook 监测 GSD 生命周期，将 milestone / phase / plan / verify 映射到 Jira 六列看板 | 最直接的 GSD 视觉化替代，但功能窄。 | 它依赖 Jira Cloud，核心是同步。taskfold 应提供本地、文件原生、跨项目和执行调度；可将其映射规则作为需求验证素材，不将 Jira 集成列入 M1。 |
| [Roadmap Skill](https://github.com/shiquda/roadmap-skill) | local-first JSON、Kanban、依赖图、MCP，面向 Claude Code/Codex/OpenCode 等 | 规划层中等重叠。 | 它不负责开发执行，也不认识 GSD 产物。taskfold 的最低差异化是从需求到 GSD phase 再到 run 的闭环。 |
| [Beads](https://github.com/gastownhall/beads) | agent 优化的依赖图 issue tracker、`ready` 检索、声明/关闭、持久记忆、Dolt 同步、多种 agent 集成 | 数据与依赖层有竞争关系。 | Beads 优先解决 agent 的结构化长期记忆，主要是 CLI/数据库而非 GSD UI 与调度。不要在 M1 引入第二个任务真相；导入或互操作不纳入当前路线图。 |

## 对产品范围的影响

1. **目标用户已收敛为个人开发者。** 不把多人协作、容量排期、权限或团队报表作为近期承诺。
2. **M1 不做通用 agent fleet。** 首先证明能把一个已有 GSD 项目的 `.planning/` 清晰投影到看板；没有 GSD 输入时只提供最小个人工作项能力。
3. **M2 调度只做单 repo、单 run。** worktree、并行波次和自动化运行不是卖点先决条件；先证明 phase 到 run 到人工交接的闭环可信。
4. **工作树隔离应保留为后续增强。** 竞品已把它视为并行调度的常规能力，C1 串行化只是风险控制起点，不能成为长期体验终点。
5. **不建立第二份项目真相。** `.planning/` 与 taskfold 独有账本的分权，是相对通用看板最重要的架构约束。

## 验证计划

| 优先级 | 验证 | 通过标准 |
|---|---|---|
| P0 | 亲自试用 Vibe Kanban（体验基准）、dev-3.0、kanbots：以同一个个人仓库完成“建任务、启动 agent、需要人决策、验收”的路径 | 写出每一步的摩擦与 taskfold 必须明显更好的一个场景；若找不到，缩减或停止调度层。 |
| P0 | 找 3 位实际使用 GSD 的个人开发者访谈/观察 | 至少 2 人明确表示 `.planning/` 的阶段和产物难以追踪，且愿意使用本地可视化控制台。 |
| P1 | 用 `claude-gsd-jira-plugin` 的 phase/plan 映射验证 GSD 看板列设计 | 能确认 GSD 的可视化状态与现有 story/task 状态不会产生两套含义。 |
| P1 | 比较 worktree 模式与同 repo 串行模式 | 明确 C2 的触发条件，例如用户同时运行两个无依赖 Plan 的比例和冲突率。 |

## 需要持续监控的风险

- dev-3.0、kanbots 或其他活跃调度台若加入 `.planning/`/GSD 解析，taskfold 的差异化会迅速收窄。
- gsd-core 若官方提供 UI、聚合或调度接口，taskfold 应转向官方生态扩展而非平行实现。
- OpenClaw Workboard 若扩展为通用 agent 调度台，插件内嵌不再构成价值；仍需靠 GSD 专属模型保留定位。
- 竞品多数在快速迭代，所有“未提供”的判断只能作为当前快照，不能作为永久前提。
