## 一、背景与调研结论

用户诉求：本项目的需求（父 Card）要能再挂**子需求**；看板要能支持**子看板**。

2026-10-14 对 TAPD（腾讯云官方文档镜像）与开源项目（GitHub sub-issues 官方文档、Plane / Vikunja 源码、Jira 官方与社区、Linear 官方、Quire 官方博客）做了核实：

| # | 结论 | 证据 |
| --- | --- | --- |
| 1 | **视图不持有数据，板不嵌套实体**（最强不变量） | Jira 板 = 过滤器投影（社区问「板里建板」→ 做不到）；TAPD / GitHub / Linear / Plane 全是平铺命名视图；连以「嵌套看板」为卖点的 Quire 官方也写明「Nothing about your data changes underneath; only the way the board renders it」（Task Bundle 开关，关掉回平铺） |
| 2 | **「子看板」的社区普遍答案 = 多命名视图 + 过滤** | GitHub Projects（每 view 独立 layout + filter）、Linear custom views、TAPD 多看板（支持跨板复制/移动）、Jira board + JQL |
| 3 | **层级深度无共识** | Jira 官方：「Sub-tasks cannot have sub-tasks of their own」（1 层，靠市场插件 ALM Works Structure 补层级）；GitHub：8 层；TAPD / Plane：不限 |
| 4 | **子项四件套：单父 + 防环 + 树形展示 + 进度汇总** | Plane / Vikunja 源码；Vikunja 另做孤儿修复 CLI（Taskfold 删卡自动清链，无此问题，见第三节） |

层级只长在数据（工作项树）上；「子看板」是同一棵树的另一种渲染/过滤，不是独立数据域。TAPD 直接印证：需求 app 管多层需求结构，看板 app 管多块平级命名板，两者读写同一批工作项。

## 二、评审结论（2026-10-14 拍板）

| # | 决策点 | 结论 |
| --- | --- | --- |
| R1 | 「子看板」形态 | **项目内多命名视图**（社区普遍形态）；「点需求 → 聚焦其子树」作为视图的**过滤维度**内嵌，不做独立全屏 drill 模式 |
| R2 | 嵌套深度 | 放开为任意子需求，**硬限 8 层**（对齐 GitHub）+ 防环校验兜底 |
| R3 | 看板列内子结构 | **树形缩进**渲染（Quire 式）；拖拽**只移动单卡**，不做整捆拖拽（不引入 Quire 的 Alt-bundle 语义） |
| R4 | 归档带子项的需求 | **推迟**；已知边界记录于第六节（两层模型下已存在的既有行为，非本次引入） |

## 三、数据模型（无新增字段）

- 沿用 `contains` / `contained_by` 成对关系，**不新增字段、不新增表 → 不 bump `TASKFOLD_FORMAT_VERSION`**。
- **单父不变**：一张卡最多一个父需求（8.9 §2.1 保持）；换父自动从旧父 detach。
- **深度**：从最顶层需求到最深子卡最多 **8 层**；挂载时校验（目标深度 + 1 ≤ 8）。
- **防环**：挂载时沿 `contained_by` 链上行，链中不得出现被挂卡（参照前置依赖的防环实现，`store-core.ts` 的 "dependency link would create a cycle."）。
- **执行语义不变**：需求卡（含子需求）不可启动执行，只有叶子任务卡可执行（8.9 §8 保持）。
- **与前置依赖分离不变**：`parent` / `child` 仍只表执行依赖；需求卡不得作执行依赖（保持）。
- **删除**：维持现状——`removeReferencesToCard` 自动清链，子项退回「未归属」，无孤儿数据（Vikunja 需要孤儿修复 CLI 的问题这里不存在）。
- **前端派生（不落盘）**：子树结构、面包屑、子项进度（x/y）都从链接现算，不新增存储字段。

## 四、实现分解（五步，各步可独立验收）

### P1 store 放开嵌套（core）

- `store-core.ts` `setCardRequirementDirect`：移除两道闸——"requirement cards cannot be assigned to another requirement"（约 1661 行）与 "nested requirements are not supported"（约 1716 行）；替换为防环校验 + 深度校验（≤8 层）。
- 保留：不能挂自己、目标必须是需求卡、必须同项目、归档项目/卡拒绝、claim 守卫、`contains`/`contained_by` 成对维护、换父自动 detach。
- 测试：`test/project-store.test.ts` 现有 nested 断言反转；新增 8 层边界（第 8 层通过、第 9 层拒绝）、防环（A→B→A 拒绝）、深链换父用例。
- Gateway `taskfold.cards.requirement.set` 已存在，无需新增；**CLI（`packages/cli`）目前没有挂需求的参数，P1 一并补**（AI 写库的通道）。

### P2 看板列内树（UI）

- 「按需求分列」：列 = 顶层需求；列内按子树**缩进嵌套**渲染（子需求 + 其下任务），参照 `renderBoard` 的 requirement 分支改造。
- 现有实现会把「挂在需求下的子需求卡」从列渲染中跳过，放开后要改为渲染。
- 拖拽只移动单卡（拖入某列 = 改挂该列顶层需求或 detach 到未归属）；子树不整捆移动。

### P3 列表树与详情（UI）

- 列表视图（`boardView.layout = "list"`）：行按子树缩进 + 折叠；折叠状态为会话级 UI 状态，不落盘。
- 卡片详情：面包屑（祖先链，可点击跳转）+「子需求」区（直接子项列表）+ 进度汇总（x/y，含后代）。

### P4 按需求聚焦（视图过滤，「子看板」轻形态）

- 看板/列表支持「聚焦某需求子树」：只渲染该子树 + 面包屑返回；即用即走，不保存为视图。
- 这是 R1 里「过滤维度」的最小可用形态，P5 的过渡。

### P5 多命名视图（「子看板」正式形态）

- `boardView` 升级为多视图：`views: [{ id, name, filter, groupBy, sortBy, sortDirection, layout }]` + `activeViewId`；每视图 = 过滤（含「某需求子树」维度）+ 分组 + 排序 + 布局（board/list）。
- 切换器进顶部控件区（TAPD 式多命名视图）；持久化沿用 `boardView` 现有通道（OpenClaw：插件级 `projects.json`；VS Code：`workspaceState`）。
- 兼容：旧数据只有单份 `boardView` → 迁移为单个默认视图；需评估 `normalizeBoardView` 的读旧写新与格式版本门控（只丢偏好、不坏数据）。
- 链路：`packages/openclaw/src/backend/src/gateway-project-methods.ts`、`packages/vscode/src/methods.ts`（boardView.update 通道扩参）。

## 五、验收

1. 需求可挂子需求至 8 层；第 9 层拒绝，报错指明深度限制。
2. 防环：挂载形成环被拒绝；换父自动 detach 旧父。
3. 需求卡（含子需求）不能启动执行（回归）。
4. 看板按需求分列：列内子树正确嵌套渲染；拖单卡语义正确（改挂 / detach）。
5. 列表树、详情面包屑、进度汇总正确；折叠为会话态不污染数据。
6. 聚焦过滤可用（P4）；多命名视图可建、可切、重启后保持（P5）。
7. 全量测试绿；旧版 core 打开含嵌套的数据：不损坏、写入被拒（旧校验）、显示退化可接受。

## 六、已知边界与推迟项

- **归档（R4 推迟）**：归档需求卡后，其未归档子项在「按需求分列」中不可见——这是两层模型就存在的既有行为；归档列策略（灰显列 / 子项移入未归属）留后续卡决定。
- **整捆拖拽**：不做（Quire 的 bundle + Alt 语义不引入）。
- **嵌套项目（C 形态）**：不做；与「一仓库一项目」的项目发现模型冲突。
- **旧 core 兼容**：含嵌套数据在旧版 core 打开——`setCardRequirement` 仍会拒绝挂到需求上（旧校验），读取与显示退化，数据不损坏。

## 七、对 8.9 的修订

8.9 §8 原文「层级固定为两层：`父需求 Card -> 子执行 Card`。不支持需求嵌套需求，也不支持子 Card 再挂子 Card。」——依本文件 R2 修订为：**放开至最多 8 层子需求嵌套（防环校验兜底）**。8.9 其余约束（单父、需求卡不可执行、层级与前置依赖分离、不新增存储）保持不变。（2026-10-14 评审通过，修订已落到 8.9 正文。）
