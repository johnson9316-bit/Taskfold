# Taskfold 看板插件（M1 规格）

> 跨主题请从 [[README]] 进入；发现矛盾时以 [[1-规划评审]] 为准。本文件是 **M1 唯一的实施与验收依据**；全项目里程碑与阶段门见 [[8-路线图与验收]]。

## 当前状态

M1 的目标是交付可与 OpenClaw 原生 Workboard **同时启用**的 Taskfold 插件（插件 ID：`taskfold`）。它完整复制官方 Workboard 功能层并保留其实现方式，再完成必要的插件身份隔离、打包和分发；它不是整个 OpenClaw 控制台，也不是独立 Web 应用。

| 项目 | 已定基线 |
|---|---|
| 上游来源 | `openclaw/openclaw` Workboard |
| 固定快照 | `78d6c6c0471723721243d67fb053f3810c622bf8` |
| 本机验证宿主 | OpenClaw `2026.7.1-2` |
| 插件 ID / 显示名称 | `taskfold` / `Taskfold` |
| M1 后续扩展 | M2 先进行通用看板改造；M4 起才增加 GSD 映射和开发执行能力 |

## 成功定义与复制边界

完成 M1 时，Taskfold 是一个可从本地目录链接安装、也可从 Git 仓库安装的 OpenClaw 插件。它保留固定快照中 Workboard 的完整行为和宿主集成方式，同时不会和 OpenClaw 自带的 `workboard` 插件争夺公开命名空间。

必须导入以下功能层及其全部直接依赖：

1. `extensions/workboard/` 的插件入口、存储、命令、工具、Gateway 集成、运行与诊断逻辑。
2. `packages/workboard-contract/` 的共享契约、状态和类型。
3. `ui/src/pages/workboard/`、`ui/src/lib/workboard/`、`ui/src/styles/workboard.css` 的页面、状态、样式及直接 UI 依赖。

导入时保留上游的目录拓扑、模块边界、Lit + Vite + TypeScript 技术栈、OpenClaw 插件 API 和既有宿主依赖。复制边界是 **Workboard 功能层**，不是整个 OpenClaw 控制台、聊天、会话或其他无关模块。

## 允许与禁止的变更

### 允许的 M1 变更

1. 将所有公开的插件身份和注册命名空间改为 Taskfold / `taskfold`：
   - manifest 的显示名、Tab 和 UI 标识使用 `Taskfold`；插件 ID、包名和运行时标识使用 `taskfold`；
   - CLI 与 slash command 使用 `taskfold` 和 `/taskfold`；
   - 工具名使用 `taskfold_*`；
   - Gateway 方法及其他对外注册标识使用 `taskfold` 前缀。
2. 为可安装和可分发所必需的 manifest、构建、打包和依赖锁定调整。
3. 新增或更新 `README`、`UPSTREAM.md`、`THIRD-PARTY-NOTICES`、`LICENSE` 与安装/验证记录。
4. 为保留上述功能而必须同步调整的内部引用；调整不得改变上游行为、数据语义或交互流程。

### M1 明确不做

- GSD `.planning/` 投影、GSD 数据模型或 GSD 专属工作流。
- ACP 执行调度、独立 run 账本、worktree 编排或其他执行层扩展。
- MCP、AI 建议、自动化、度量和新的 Skills 集成。
- `taskfold serve`、独立 Web 应用、独立 HTTP/SSE 替代层或第二套插件外运行时。
- React/Tailwind/shadcn 等前端重写、新看板交互设计、重新划分架构或替换 Workboard 宿主依赖。

## 实施顺序与交付物

1. **固定来源**：记录上游仓库、commit、导入日期和导入范围；建立导入清单，以该快照的 Workboard 目录与直接依赖为完整性基准。
2. **完整导入**：复制功能层并保留上游拓扑；先按上游方式构建和加载，再做命名空间替换。
3. **身份隔离**：完成 `taskfold` 的 manifest、入口、CLI、slash command、工具、Gateway 与 UI 标识改名，确认能与原生 Workboard 并存。
4. **打包与资料**：准备锁定依赖、安装说明、MIT 许可证和来源说明；`UPSTREAM.md` 必须列出固定 commit、同步日期和全部本地改动，`THIRD-PARTY-NOTICES` 必须保留 OpenClaw 的 MIT 署名。
5. **本机与 Git 验证**：链接本地目录完成宿主运行验证，提交 Git 后从干净 clone 复验 Git 安装。

M1 仓库的最终交付物为：完整可安装源码、锁定依赖与构建约定、`README`、`UPSTREAM.md`、`THIRD-PARTY-NOTICES`、MIT `LICENSE`、可追溯 Git 提交，以及可复核的验证记录。

## 验收

### 1. 来源完整性

- `UPSTREAM.md` 精确记录 `78d6c6c0471723721243d67fb053f3810c622bf8`、上游路径、导入日期和本地 patch。
- 导入清单覆盖插件、共享契约、UI/状态/样式及直接依赖；未导入整个 OpenClaw 控制台。
- 与上游的差异仅包含本文件“允许的 M1 变更”；任何行为性改动必须撤回或移至 M2 重新立项。

### 2. 构建与加载

在本机 OpenClaw `2026.7.1-2` 中，完成上游对应的构建/测试后执行：

```bash
# 本机开发安装
openclaw plugins install --link /home/john/src/personal/Taskfold
openclaw plugins inspect taskfold --runtime
openclaw plugins doctor

# Git 仓库分发安装
openclaw plugins install <Git-仓库地址>
```

- `inspect taskfold --runtime` 能加载插件并显示其运行时注册内容。
- `plugins doctor` 没有阻止 `taskfold` 加载的错误。
- 原生 `workboard` 与 `taskfold` 可同时启用，CLI、slash command、工具、Gateway 和 UI 入口均无命名冲突。

### 3. 功能等价

固定快照的 Workboard manifest 和运行时注册内容是 M1 功能等价性的完整边界；不能因验收未列出某项功能而删除或弱化它。至少完成并记录以下代表性闭环：

1. 创建看板和卡片，编辑卡片信息，改变状态，在看板和详情中查看结果，并按可用条件筛选。
2. 创建父子依赖，验证受依赖状态、解除依赖和派发逻辑仍遵循上游行为。
3. 对卡片进行领取、心跳、释放、完成、阻塞和解除阻塞，确认状态、诊断和运行记录可见。
4. 添加评论、证据或附件，并在卡片详情中读取其结果。
5. 验证运行信息、通知、统计和派发能力已注册且可调用；若某项依赖本机 agent 或宿主配置，须记录其上游一致的可用结果或错误语义，而不是新增 taskfold 专属实现。

### 4. Git 分发复验

- Git 仓库至少存在一个包含完整交付物的可追溯提交。
- 从干净 clone 执行 Git 安装命令成功，不依赖开发者本机的未提交文件、全局链接或未记录构建产物。
- `README` 覆盖安装、启用、升级、卸载和本机开发方式；验证记录包含所用 OpenClaw 版本、命令结果和功能冒烟结论。

## M1 退出门

只有来源完整性、构建与加载、功能等价和 Git 分发复验四类验收都完成，M1 才可标记完成。M1 完成后，M2 可以在该插件基础上完成多项目、项目设置和项目资料改造；M4 才能增加 GSD 能力。两个阶段都不得回头把 M1 当作独立应用或重新实现 Workboard 的理由。
