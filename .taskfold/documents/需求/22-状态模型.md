# 状态模型：固定类别 + 项目自定义状态

> 状态：设计已定稿（2026-10-13），按「实施步骤」分步落地；每步完成后在文末「实施进展」登记。

## 一、为什么改

看板状态下拉里是 `Triage / 待办池 / 待办 / 已计划 / 就绪 / 运行中 / 查看 / 已阻挡 / 已完成` 九项，不像看板，更不像 AI 工作台：

1. **九个状态名写死在代码里**（`contract/index.ts` 的 `TASKFOLD_STATUSES`），调度、认领、依赖提升都直接认名字，用户无法调整。
2. **其中三个是系统内部状态**：`scheduled`（定时未到，系统设）、`ready`（派发开关）、`blocked`（run 失败/超时，系统设）。它们被当成看板列展示，人没法分清，手拖也会被系统改回来。
3. **没有"已取消"**，不做的卡只能留在列里或归档。
4. **中文文案是机器翻译**：`review` → "查看"、`blocked` → "已阻挡"、`triage` 未翻译。

## 二、调研

| 项目 | 做法 | 来源 |
| --- | --- | --- |
| Linear | 默认 Backlog → Todo → In Progress → Done → Canceled；底层固定 5 个类别（backlog / unstarted / started / completed / canceled），类别内可加自定义状态 | [Linear 文档](https://linear.app/docs/configuring-workflows.md) |
| Plane | 5 个固定分组（Backlog / Unstarted / Started / Completed / Cancelled），各组可增删状态；另有系统保留的 Triage 收件箱，不算普通状态 | [Plane 文档](https://docs.plane.so/core-concepts/issues/states) |
| Jira | 3 个状态类别 To Do / In Progress / Done，看板列映射到类别 | [Atlassian 文档](https://support.atlassian.com/jira-software-cloud/docs/assign-statuses-and-edit-columns-in-a-team-managed-project/) |
| Vibe Kanban（AI agent 看板） | `TaskStatus` 仅 Todo / InProgress / InReview / Done / Cancelled 五个 | [task.rs](https://raw.githubusercontent.com/BloopAI/vibe-kanban/main/crates/db/src/models/task.rs) |
| TAPD | 状态名由项目自定义（故事墙：规划中 → 产品流程 → UI 流程 → 开发流程 → 交付流程 → 已完成 / 已暂停；缺陷：沟通中 → 修复流程 → 验证流程 → 已修复 / 已关闭）；筛选里固定有"所有结束状态 / 所有未结束状态" | 2026-10-13 在 TAPD 实际界面核对 |

共同点：状态数量在 5 个左右；有"已取消/关闭"；系统逻辑只认**类别**，状态名可自定义；Triage 是收件箱而不是流程中的一列；"定时未到""依赖满足""被卡住"在这些系统里是属性，不是状态。

## 三、设计决定

1. **4 个固定类别**，代码只认它们：`unstarted`（待开始）、`started`（进行中）、`completed`（已完成）、`cancelled`（已取消）。
2. **状态定义存 `.taskfold/config.yml` 的 `statuses` 列表**（入 Git，VS Code / CLI / OpenClaw 共用）：`{ id, name?, category, color?, role? }`。`name` 缺省时用 i18n 里内置 id 的译名。列表顺序即看板列顺序。
3. **默认状态集**（新项目、未配置 `statuses` 的项目）：

   | id | 显示名 | 类别 | role |
   | --- | --- | --- | --- |
   | `todo` | 待办 | unstarted | — |
   | `running` | 进行中 | started | — |
   | `review` | 待评审 | started | review |
   | `done` | 已完成 | completed | — |
   | `cancelled` | 已取消 | cancelled | — |

   沿用现有 id 不改名：`done` / `todo` / `running` 的卡文件不用重写，旧脚本里的 `--status done` 照常可用。
4. **`role` 只有两个**：`review`（run 成功结束时卡移到哪）、`intake`（自动拆解与 specify 的入口，原 triage 的职责）。其余引擎动作按类别取"该类别第一个状态"：开始执行 → 第一个 `started`；完成 → 第一个 `completed`；新卡默认 → 第一个 `unstarted`。
5. **三个内部状态变成卡片标记**：
   - `scheduled` → 沿用 `automation.scheduledAt`，"被定时挡住"由 `scheduledAt > now` 计算，状态保持待办。
   - `ready` → **派发标记**（卡片级布尔）。它是调度器的派发开关，不是纯派生：`dispatcher` 只拾取带此标记的卡，`promote()` 是人工"批准给 agent 执行"，依赖全部完成时也自动设置。
   - `blocked` → **阻塞标记** `{ reason, at }`。run 失败 / 超时 / 重试耗尽时系统设置，人工"解除阻塞"清除；状态保持原列。
6. **`triage` / `backlog` 不进默认集，但已有项目不丢**：迁移时若项目里有卡在用，就登记进该项目的 `statuses`（category=unstarted，`triage` 同时标 `role=intake`）。
7. **引擎不再用 `status === "running"` 判断 run 是否活着**，只看 `execution.status` 与 `attempts`。
8. **兼容策略**：`format_version` 升到 4，沿用 `file-store-format.ts` 的门控——旧版 core 读到 4 自动只读并提示升级。读取侧永远容忍旧值，写入侧才升版本。

## 四、旧 → 新映射

| 旧状态 | 新状态 | 标记 | 备注 |
| --- | --- | --- | --- |
| todo / running / review / done | 不变 | — | id 沿用 |
| scheduled | todo | 定时（`scheduledAt` 已有） | |
| ready | todo | 派发标记 | |
| blocked | running | 阻塞标记 | 与 Jira / Linear"受阻工作仍在进行中"一致 |
| triage | triage（登记为自定义状态，unstarted，role=intake） | — | 仅在项目有卡使用时保留 |
| backlog | backlog（登记为自定义状态，unstarted） | — | 同上 |
