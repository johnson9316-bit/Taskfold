## 需求生命周期 + GSD 循环（主线流程）

**两段是串联的，不是二选一**：需求侧（taskfold 补的漏斗）负责「做什么、按什么顺序」，GSD 循环（gsd-core 已有）负责「怎么做完」。

```
┌──── 需求漏斗（taskfold 补，gsd-core 没有）────┐   ┌──── GSD 循环（gsd-core 已有）────┐
│ ① 收集 → ② 分析分类 → ③ 优先级排序           │ → │ Discuss →(UI Design)→ Plan →     │
│    ↑                                        │   │ Execute → Verify → Ship          │
└────┼───────────────────────────────────────┘   └──────┬─────────────────────┬─────┘
     │                                                  │  修复回环            │
     └────────── 缺陷 / 反馈回流 ───────────────────────┴─────────────────────┘
                                                    落地为 .planning/ 产物
```

衔接点：需求排序完成后进入 `ROADMAP.md` 成为一个 GSD **Phase**，由此启动 Discuss。详见 [[3-需求与工作管理]]。

### ① 需求收集（Inbox）

| 能力 | 说明 | 阶段 |
|------|------|------|
| 快速捕获 | CLI / Dashboard / agent tool 一句话建需求，落到 `inbox` 状态 | M2 |
| 多来源接入 | 从对话记录、MD 文件、Git issue 导入 | M3 |
| **AI 去重** | 新需求入池时向量/关键词比对，提示「疑似重复 #xxx」 | M4 |
| 原始诉求留痕 | MD 正文保留提出人原话，不被后续加工覆盖 | M2 |

### ② 需求分析与分类

| 能力 | 说明 | 阶段 |
|------|------|------|
| 分类维度 | `type`（特性/优化/技术债/调研）、`module`、`labels` | M2 |
| **AI 澄清** | agent 读需求，提问缺失信息，补全背景 / 目标用户 / 约束 | M3 |
| **AI 生成验收标准** | 输出 Given-When-Then 形式的 AC，写入 MD 正文 | M3 |
| **AI 拆解** | 需求 → 子任务（前端/后端/测试），带估算建议 | M3 |
| 规模估算 | 故事点（斐波那契）或人日 | M2 |

### ③ 优先级排序

| 能力 | 说明 | 阶段 |
|------|------|------|
| 基础优先级 | `urgent / high / normal / low` | M0（已有） |
| **RICE 打分** | Reach × Impact × Confidence ÷ Effort，字段化存储、自动排序 | M2 |
| MoSCoW | Must / Should / Could / Won't，用于个人范围裁剪 | M3 |
| **AI 排序建议** | 结合价值、依赖、风险给出排序建议 + 理由，**人确认后生效** | M4 |
| 依赖感知 | 被阻塞项自动降权并高亮 | M3 |

> 原则：AI **只给建议不自动改**优先级。优先级是产品判断，必须留人的决策点。

### ④ 实现与验证

| 能力 | 说明 | 阶段 |
|------|------|------|
| 当前重点规划 | 从需求池选择近期重点并排序 | M3 |
| 看板执行 | 拖拽流转 + WIP 限制 | M0（拖拽已有）/ M3（WIP） |
| 缺陷跟踪 | Bug 作为独立工作项，关联需求 / phase | M2 |
| 验收 | 勾选 AC 清单，全绿方可进 `done`（准出条件，[[3-需求与工作管理]]） | M3 |
| **AI 日报 / 周报** | 读 events 流水生成进展摘要与风险提示 | M4 |
| 度量 | 燃尽、CFD、周期时间、缺陷逃逸率（[[7-数据与接口]]） | M4 |

### GSD 阶段循环（核心逻辑，来自 gsd-core）

**这是 taskfold 的骨架。** 以下为 gsd-core 既定模型，taskfold **不改造、只呈现与聚合**。

| 阶段 | 做什么 | 产出产物 | 触发条件 |
|------|--------|---------|---------|
| **Discuss** | 在规划前先固化实现决策 | `XX-CONTEXT.md` | `ROADMAP.md` 中存在该 phase 的目标 |
| **UI Design**（条件） | 仅含视觉部分的 phase 才走 | `XX-UI-SPEC.md` | 视觉复杂度值得单独契约时 |
| **Plan** | 研究、拆解、校验计划能塞进新上下文 | `XX-RESEARCH.md`、`XX-YY-PLAN.md` | Discuss 完成；串行子 agent：researcher → planner → plan-checker |
| **Execute** | 按 wave 并行执行，每 executor 全新上下文 | 原子代码提交、`XX-YY-SUMMARY.md` | 计划校验通过 |
| **Verify** | 核对「建出来的」是否等于「想要的」 | `XX-VERIFICATION.md`、`XX-UAT.md` | 所有 executor 完成 |
| **Ship** | 建 PR、归档 phase 产物 | 更新 `STATE.md`、归档 | Verify 确认与需求一致 |

**层级与并行模型**：

```
Project
└── Phase（十进制编号 01, 02…；一个可交付单元，跑完整循环）
    └── Plan（XX-YY）
        └── Wave（按依赖分组，同 wave 内并行）

Plan 01（无依赖）  ─┐
Plan 02（无依赖）  ─┼── Wave 1（并行）
Plan 03（依赖 01） ─┴── Wave 2（等待）
```

每个 executor 拿到全新的 200K 上下文窗口（大模型可至 1M），这是 gsd-core 对抗 context rot 的核心手段。

**回环**：Verify 可产出定向修复计划，即存在 Verify → Execute 的回退。taskfold 必须把这个回环**显式画出来**并计入度量（[[7-数据与接口]] 的「Verify 返工率」）。

**GSD 概念与 taskfold 既有设计的对应关系**：

| GSD 概念 | taskfold 对应 | 说明 |
|---------|-------------|------|
| `PROJECT.md` | Product（[[3-需求与工作管理]]） | 愿景、约束、决策 |
| `REQUIREMENTS.md`（v1/v2/out-of-scope） | 需求分级（[[3-需求与工作管理]] 的 MoSCoW） | GSD 只有平铺文档，taskfold 补排序与打分 |
| `ROADMAP.md`（phase 分解 + 状态） | 工作规划 / 路线图（[[3-需求与工作管理]]） | 天然对应，直接渲染 |
| **Phase** | Release 下的可交付单元 | **依赖驱动，非时间盒**；个人开发者按当前重点推进，不引入 Sprint 概念 |
| **Plan（XX-YY）** | WorkItem `type=task`（[[3-需求与工作管理]]） | |
| **Wave** | 并行执行分组 | taskfold 新增可视化维度 |
| `STATE.md`（position / decisions / blockers / metrics） | 当前位置 + 阻塞 + events 源 | **度量的原始输入** |
| `continue-here.md` | 会话恢复上下文 | 来自 `/gsd-pause-work` |

**GSD 没有、由 taskfold 补的**：个人当前重点、缺陷实体、RICE 优先级、跨项目聚合、度量历史与图表。多人分工、时间盒迭代和团队容量不在当前范围。

## 模块① 流程管理

**目标：让「研发流程标准化」可配置、可执行、可审计**，而不是写在 wiki 里没人遵守。

### 工作流定义

**内建默认工作流就是 GSD 阶段循环**（[[3-需求与工作管理]]），不是通用 kanban 套壳。这是 taskfold 与其他看板的根本区别。

```
phase（GSD 主流程，来自 gsd-core，taskfold 不改造）：
  discuss →[ui_design]→ plan → execute → verify → ship
                                            └── 修复回环 ──┘（Verify → Execute）

story（需求漏斗，taskfold 补）：
  inbox → analyzing → ready → （进入 ROADMAP.md 成为 phase）
              └── rejected / deferred ──┘

task（= GSD 的 Plan，XX-YY）：
  todo → doing → blocked → done

bug（GSD 无此实体，taskfold 补）：
  new → confirmed → fixing → fixed → verifying → closed
            └─ rejected / duplicate ─┘
```

要点：

- `phase` 的状态**不由 taskfold 定义**，而是读 `.planning/ROADMAP.md` 与 `STATE.md` 得到；taskfold 只呈现与聚合（[[7-数据与接口]]）。
- 因此 `phase` 的流转**不走 taskfold 的准入准出检查器**（[[3-需求与工作管理]]），gate 由 gsd-core 自己把（plan-checker、verifier）。taskfold 的检查器只作用于 `story` / `task` / `bug`。
- v0.1 的五列（`triage/todo/doing/blocked/done`）保留为 `task` 的默认流；`inbox` 取代 `triage` 作为 story 入口。

配置示例（M2+；`<TASKFOLD_HOME>/workflows.yaml` 表示 taskfold 插件的数据目录。M1 完全沿用复制的 Workboard 配置约定）：

```yaml
story:
  states:
    - { id: inbox,     label: 需求池,   category: todo }
    - { id: analyzing, label: 分析中,   category: todo }
    - { id: ready,     label: 待排期,   category: todo,  entry: [has_ac, has_estimate] }
    - { id: doing,     label: 开发中,   category: active, wip: 3 }
    - { id: verifying, label: 验证中,   category: active }
    - { id: done,      label: 已完成,   category: done,  entry: [all_ac_checked] }
  transitions:
    - { from: inbox, to: analyzing }
    - { from: "*",   to: rejected, requires_comment: true }
```

### 流程要素

| 要素 | 说明 | 阶段 |
|------|------|------|
| 状态与流转 | 允许的迁移路径，非法流转被拒 | M3 |
| **准入/准出条件** | 如「进 done 必须 AC 全绿」「进 ready 必须有估算」 | M3 |
| WIP 限制 | 每状态在制品上限，超限告警 | M3 |
| 必填字段规则 | 按状态要求字段（如进 fixing 必须有复现信息） | M4 |
| 流转留痕 | 每次迁移写 `events`（from/to/actor/时间） | **M2（度量依赖，优先）** |
| 工作流模板 | 内置 `personal` / `kanban` / `bugfix` 三套预设，一键套用 | M3 |
| 自定义字段 | 按产品定义扩展字段，存 `extra_json` | M4 |

### 准入/准出条件（内置检查器）

| 检查器 | 语义 |
|--------|------|
| `has_ac` | 已有验收标准 |
| `all_ac_checked` | 验收标准全部勾选 |
| `has_estimate` | 已估算 |
| `no_open_blockers` | 无未解除的 `blocks` 关联 |
| `has_comment` | 本次流转填写了说明 |

> 检查器**默认全部关闭**，由个人按需开启。流程管理最大的失败模式是一上来就把自己的工作卡死。

## 模块② 工作项管理

### 层级

```
Workspace（工作区，= 一个 taskfold 实例）
└── Product（产品/项目）
    ├── Release（发布计划）→ Iteration（迭代）→ WorkItem
    └── WorkItem（不属于任何迭代 → 需求池）
```

### WorkItem 统一模型

**决策：单表 + `type` 字段**，不为 story / task / bug 分表。理由：插件量级下分表带来的查询与 UI 复杂度大于收益；差异字段进 `extra_json`。

| type | 含义 | 典型父子关系 |
|------|------|-------------|
| `epic` | 史诗 / 大需求 | 父：Release |
| `story` | 需求 / 用户故事 | 父：epic；子：task |
| `task` | 任务 | 父：story |
| `bug` | 缺陷 | 关联：story / phase |
| `spike` | 技术调研 | 独立 |

### 关联关系

`links` 表，`(from_id, to_id, kind)`：

| kind | 语义 |
|------|------|
| `parent` | 层级归属 |
| `blocks` | 阻塞（影响优先级与预警） |
| `relates` | 一般关联 |
| `duplicates` | 重复 |
| `verifies` | bug 验证某 story |

### 操作与视图

| 能力 | 说明 | 阶段 |
|------|------|------|
| 看板视图 | 按状态分列，拖拽流转 | M0 ✅ |
| **表格视图** | 批量查看/编辑，列可配 | M3 |
| 列表视图 | 分组（按 phase/状态/优先级） | M3 |
| 筛选器 | 组合条件，可保存为常用视图 | M3 |
| 批量操作 | 多选后批量改状态/优先级/当前重点 | M3 |
| 详情抽屉 | 字段 + MD 正文 + AC + 评论 + 变更历史 | M0 部分 ✅ / M2 补全 |
| 全文检索 | 标题 + MD 正文（SQLite FTS5） | M3 |
| 变更历史 | 从 `events` 渲染时间线 | M2 |

## 模块③ 工作规划（长周期：往哪走）

**回答「未来 1–2 个季度交付什么」**，对应 TAPD 的「制定长期发布计划有效进行产品规划」。

| 能力 | 说明 | 阶段 |
|------|------|------|
| **发布计划 Release** | 版本号、目标、时间窗、包含的 Epic/Story | M3 |
| **产品路线图视图** | 时间轴上排布 Release / Epic，可拖拽调整 | M3 |
| Epic 分解 | Epic → Story 的树形视图与完成度汇总 | M3 |
| 目标（轻量 OKR） | 季度目标，关联 Epic，看达成率 | M4 |
| 依赖视图 | 跨 Epic / 跨产品的 `blocks` 关系图 | M4 |
| 容量前瞻 | 按历史速率推算 Release 是否装得下 | M4 |
| **AI 规划建议** | 给定目标与需求池，建议 Release 划分 + 风险 | M4 |

> 路线图**不是甘特图**（[[2-产品定位与范围]] 已排除）。只做「Release/Epic × 时间轴」的粗粒度色块，不做任务级依赖排程与关键路径。

## 模块④ 个人执行计划（短周期：下一步怎么推进）

**回答「这 1–2 周最该推进什么、先做什么、哪些工作应交给 agent」**。它不模拟团队的 Sprint、容量和分工，而是帮助个人开发者控制有限注意力与并行度。与模块③的区别：模块③回答中长期要交付什么；本模块回答当前行动顺序与人机协作节奏。

| 能力 | 说明 | 阶段 |
|------|------|------|
| **当前重点** | 从需求池或路线图中选出近期要推进的工作项，支持排序与暂存 | M3 |
| **重点规划** | 根据优先级、依赖、截止日与 GSD 阶段给出建议顺序；人确认后生效 | M3 |
| **个人待办** | 跨项目聚合进行中、`awaiting_human` 与 blocked 工作项 | M3 |
| 执行边界 | 对个人 WIP 与同 repo run 数告警，避免同时开太多工作 | M3 |
| 日历视图 | 展示个人截止日、里程碑与计划窗口 | M4 |
| **计划 vs 实际** | 记录当前重点的中途增删、完成情况与阻塞原因 | M4 |
| 重点回顾 | 按周期生成完成项、遗留项与范围变化摘要 | M4 |
| **AI 重点规划** | 给候选集、依赖与历史记录，返回建议顺序与风险 | M4 |
