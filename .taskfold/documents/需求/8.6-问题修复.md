## 已确认卡住：宿主 SDK 缺一个能力，这个仓库改不了

`--admin` 派发的 worker 拿不到任何 `taskfold_*` 工具，却照样把卡片收敛成 `review`——这条本以为是"拆开 `dispatcher.ts` 里一个 `if`"就能修的缺陷，深挖之后发现根本改不了，因为它依赖的宿主能力不存在。

**现象**（在归档的 `fb-probe` 项目里建两张一次性测试卡，`--admin` 派发，测完清理）：worker 两次都没能调用任何一个 `taskfold_*` 工具，卡片却都收敛成 `status: review`，无评论、无 proof、无 summary：

- 第一次：worker 依次调用 `workboard_heartbeat`/`workboard_comment`/`workboard_proof`/`workboard_complete`（宿主自带 Workboard 插件的工具，跟 prompt 里写明的 `taskfold_*` 是两码事），四次全部 `card not found`。
- 第二次：明确只准调用 `taskfold_complete`，session transcript 里模型的原话是它的工具列表里**根本没有 `taskfold_*`**，只有 `workboard_*`；于是它改用通用 `exec` 工具 `echo` 出一段长得像工具调用的字符串蒙混过去。

**表面根因**：`src/backend/src/dispatcher.ts` 里三处 `assertRestrictedTaskfoldTarget` 调用（约 367/399/445 行）都套着 `if (!workspaceAccess.unrestricted)`，`--admin` 会跳过它们，而这是唯一会告诉宿主"这次派发要挂 `confinedToolNames: TASKFOLD_TOOL_NAMES`/`requiredToolNames: TASKFOLD_REQUIRED_WORKER_TOOLS`"的地方（`resolveAgentTaskfoldWorkspaceRuntime` → `prepareSandboxWorkspaceAuthority`，`workspace-access.ts:122-163`）。

**真根因（一查到底才发现）**：`prepareSandboxWorkspaceAuthority` 这个回调来自 `gateway.ts:93-99` 的 `(api.runtime as unknown as {sandbox?: {prepareWorkspaceAuthority?: ...}}).sandbox`——这是**硬转类型转出来的**，而 `api.runtime.sandbox.prepareWorkspaceAuthority` 在当前装的 OpenClaw（2026.7.1-2）整个已安装包里**不存在**（`grep -rn "prepareWorkspaceAuthority" node_modules/openclaw/` 零命中；公开的 `PluginRuntime` 类型定义里也没有 `sandbox` 字段）。也就是说：

- 不只 `--admin`，**任何 workspace 受限的正常派发也从来没能挂载过工具**——这条调用每次都因为回调是 `undefined` 直接短路成 `sandboxed:false`，所以受限派发在这个版本上 100% 会在"target agent is not sandboxed"这行报错，跟宿主有没有配置沙箱无关。
- 公开 SDK 里确实有一个真实存在的沙箱相关导出——`openclaw/plugin-sdk/sandbox` 的 `resolveSandboxRuntimeStatus({cfg, sessionKey})`——但它的返回值只有 `{sandboxed, mode, ...}`，**不支持"请求挂载这些工具"这个语义**。
- 再查实际起 worker 用的 `runtime.subagent.run(params)`，其参数类型 `SubagentRunParams` 里**没有任何工具或 `agentId` 相关字段**——一个 subagent 拿到什么工具，完全由它解析到的 agent（这台机器上是 "main"）的静态配置决定。检查了 `~/.openclaw/openclaw.json` 的 `agents` 配置，也没有任何按 agent 设工具白名单的字段。

结论：`workspace-access.ts` 里整套 `confinedToolNames`/`requiredToolNames`/`prepareSandboxWorkspaceAuthority` 机制，是照着一个**从未在任何已发布 OpenClaw 版本里存在过的宿主接口**写的。当前公开的插件 SDK 没有给插件任何"让我派发的 subagent 挂上我自己的工具"的入口——这不是 Taskfold 自己代码里能拆开的一个 `if`，而是宿主能力缺口。

同时确认：`finishExecutionForRun`（`store-workflow.ts:205-206`，`succeeded = outcome === "ok"`）只看宿主 `subagent_ended` 的粗粒度信号——"agent 这一轮正常结束"，跟"worker 有没有调用过 `taskfold_complete`"无关。两者叠加：只要 worker 拿不到工具（目前是所有派发路径），不管它到底做没做事，卡片都会悄悄收敛成 `review`，卡片上一点证据都留不下。

**这轮不修**：改法只有两种，一是等/找上游给插件补一个"请求挂载工具到指定 subagent run"的能力，二是弄清楚 `agentId`/工具集是否能通过其他配置手段静态解决（比如让 "main" agent 静态启用 Taskfold 工具——如果 SDK 有这个开关的话，还没找到）。两种都超出这个仓库能单方面解决的范围，本轮记录到此为止。

## 待决定

1. **UI 能力缺口。** 83 个已注册 Gateway 方法里，UI 只调 42 个；41 个是 agent/CLI 专属 —— 评论、claim、心跳、release、附件、通知、导出都没有界面入口（`ui/src` 里零个 `comment`）。是有意如此（人用看板、agent 用工具），还是要补人工入口？补的话至少需要卡片详情里的评论区 + 接 `taskfold.cards.comment`。
2. **`/taskfold/` 静态路由鉴权。** 声明的 `auth: "plugin"` 含义是插件自负鉴权，而它没鉴：HTML 与 JS 无凭证可取。穿越（编码/原始）404、缺失 404、非 GET 405、页面不含卡片数据，所以暴露面只有静态产物。默认 loopback 绑定下可接受；绑 LAN/tailnet 前必须定：维持现状 + 文档写清，还是改 `auth: "gateway"`。


## 待验证

1. **真实 worker run 端到端——卡在宿主能力缺口上，不是"还没试过"。** 放行 `--admin` 跑了两次真实 dispatch：机制本身没问题（claim → 起 subagent → `subagent_ended` 收敛），但 worker 两次都没能调用任何一个 `taskfold_*` 工具。深挖后确认这不是 `--admin` 特有的问题，而是当前 OpenClaw 版本的插件 SDK 没有给插件任何"给我派发的 subagent 挂工具"的入口，任何派发路径（包括理论上的 sandboxed 路径）都会撞上同一个缺口——见「已确认卡住」一节。历史上那次成功记录（卡片 `252615eb`）具体走的是什么路径，本轮没能重建，无法解释它当时为什么能成功。
2. **43 个 tool 一个都没冒烟——同一个缺口挡住的。** 两次 `--admin` 测试里 worker 拿到的都不是 Taskfold 工具集，所以两次尝试都没有一次真正的 `taskfold_*` 调用发生。这条要等上游给插件补齐"挂载工具到指定 subagent run"的能力（或找到其他静态配置手段）才谈得上真正冒烟这 43 个 tool。
