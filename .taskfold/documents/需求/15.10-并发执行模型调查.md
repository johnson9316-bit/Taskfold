## 一、Q1：上游 stock workboard 的 owner 模型

**结论：与 Taskfold 逐条等价，回落链完全相同，且官方文档明确把"同 owner 同时只跑一张卡"写成设计行为，不是缺陷。上游不是天生并行的——它和 Taskfold 一样，默认情况下（没人手工分配 `agentId`）会把所有卡塞进同一个默认 owner 桶，从而全局退化成串行。**

证据：

1. **回落链逐字等价**：`workboardCardSlotOwner`（`tpm/.../src/store-constants.ts:48-59`）：`claim.ownerId`（未过期时）→ `card.agentId` → `DEFAULT_WORKBOARD_DISPATCH_OWNER = "workboard-dispatcher"`（`:23`）。与 Taskfold `resolveDispatchOwner`（`dispatcher.ts:225-232`）唯一区别是常量名，其余逻辑（含"传/不传 `now` 区分就绪候选 vs 占用槽位"这个细节）完全一致。
2. **官方文档明确写死"一次一张/owner"**：`~/.nvm/.../openclaw/docs/plugins/workboard.md:241-256`「Worker selection」一节原文：
   > Each pass starts **at most 3 workers by default**. … A pass starts only one card per owner/agent and skips owners that already have running or review work on the board.
   > … Unassigned cards: `subagent:workboard-<boardId>-<cardId>` (**Gateway resolves the configured default agent**)
   即"未分配 agent 的卡都路由到同一个配置好的默认 agent"是**官方写明的行为**，不是推断。
3. **上游自己的测试把这一行为当规格钉住**：`dispatcher-ownership.test.ts:50-86`「falls back to one default owner for persisted blank and unassigned agents」——两张 `agentId` 为空/未设置的卡，`maxStarts: 3`，结果只起 1 个；`:566-594`「keeps one worker slot across 25 concurrent board dispatches」——25 张卡共享 `agentId: "shared-worker"`，25 次并发 dispatch 调用，最终只有 1 张变成 `running`。
4. **但"不同 owner 之间"确实并行**：`dispatcher-ownership.test.ts:245-284`「preserves priority order among available owners when workers start successfully」——4 张卡分属 `primary-worker`/`primary-worker`(同一个)/`independent-worker`/`normal-worker` 三个不同 owner，`maxStarts: 2`，结果 `urgent`（primary-worker）和 `high`（independent-worker）**在同一次 dispatch 里同时起跑**，同 owner 的第二张仍留在 `ready`。这证明上游的并发单位是"owner"，多 owner 天然并行，单 owner 强制串行。
5. **上游比 Taskfold 多一层数据库级守卫**：`claimIfOwnerAvailable`（`sqlite-store.ts:1265-1283`）在 `BEGIN IMMEDIATE` 事务内扫描其余卡片，命中同 owner 占用即返回 `"owner_busy"`；接口定义见 `persistence-types.ts:55-77`（`WorkboardCardStore.claimIfOwnerAvailable`）。**Taskfold 的 `sqlite-store.ts` 全文搜索 `claimIfOwnerAvailable` 无结果**——这层跨进程正确性保证在 Taskfold 里缺失（`需求/15.8-并发与补偿设计.md` 第三节已详细分析这个差距，见「五、与既有规划的关系」）。
6. `maxStarts` 默认值双方一致：`DEFAULT_DISPATCH_MAX_STARTS = 3`（Taskfold `dispatcher.ts:29`）对应上游 `DEFAULT_DISPATCH_MAX_STARTS = 3`（`tpm/.../src/dispatcher.ts:35`）。

## 二、Q2：上游怎么配置多 worker

**结论：没有插件专属的"并发度"配置项。多 worker = 给不同卡片分配不同的 `agentId` 字符串，工具/UI 都已内置写入口；`agentId` 在"受限"调度场景下会解析到宿主 `agents.entries` 里的真实多 agent 配置，但在"非受限"（本地/CLI/进程内）场景下可以是任意字符串，不强制对应真实 agent。**

证据：

1. **工具面**：`workboard_create` 的 `agentId` 参数（`tools.ts:252`，`Optional(Type.String({description:"Assigned agent id."}))`）；`workboard_list` 支持按 `agentId` 过滤（`:207`,`:224`,`:234`）。
2. **UI 面**：卡片编辑弹窗有专门的 Agent 选择器（`browser/pages/workboard/view-card-modal.ts:325-336`「fieldAgent」+ `renderAgentPicker`），选项来自 `buildAssignableAgentOptions(props.agentsList, ...)`（`agent-filter.ts`），草稿字段 `state.draftAgentId` 最终随 patch 一起提交（`browser/lib/workboard/card-state.ts:150`：`agentId: state.draftAgentId`）。
3. **`agentId` 的语义来源是宿主的 agent 列表，不是插件自造的概念**：`AgentsListResult` 类型来自 `@openclaw/gateway-protocol`（`browser/api/types.ts:3`），即卡片可选的 agent 池就是宿主 `agents.entries` 配置出的多 agent 舰队（参见 `~/.nvm/.../openclaw/docs/gateway/config-agents/entries-and-multi-agent.md` 的 `agents.entries.home`/`agents.entries.work` 多 agent 示例）。
4. **`agentId` → 工作区解析确实接了宿主多 agent 配置**：`gatewayDispatchOptions`（`tpm/.../src/gateway-helpers.ts:128-129`）：`resolveAgentWorkspace: (agentId) => resolveWorkboardAgentWorkspace(context.getRuntimeConfig(), agentId)`。
5. **但这条解析只在"受限"调度路径上被真正调用**：`resolveGatewayWorkboardWorkspaceAccess`（`gateway-helpers.ts:96-112`）在 `!params.client`（进程内/无远程客户端）时直接返回 `{unrestricted: true}`，此时 `dispatcher.ts` 里 `if (!workspaceAccess.unrestricted) { … resolveAgentWorkspace … }` 这段整体跳过（`tpm/.../src/dispatcher.ts` 对应 `runWorkboardDispatch` 的 `!requestedWorkspace || kind==="scratch"` 分支）。即：本地/CLI/无远程客户端的调度不要求 `agentId` 对应真实配置的 agent，纯字符串标签即可参与 owner 分桶。
6. **插件 manifest 里没有并发配置**：`tpm/.../extensions/workboard/openclaw.plugin.json` 全文没有 `concurrency`/`maxConcurrent`/`workerCount`/`capacity`/`parallel` 任何字段（唯一暴露的调度参数是 dashboard action `dispatch` 的 `boardId`）；对整个 `extensions/workboard/src|browser` 做同样关键词 grep，命中只有两处代码注释（"owner-capacity snapshot"/"owner's capacity slot"），没有配置项。真正的"worker 池"概念在宿主层（见 Q3）。
7. **`maxStarts` 是唯一可调的调度参数，但它是"每轮起多少张新卡"的上限，不是"总并发上限"**：`workboard.cards.dispatchWithOptions` 网关方法透传 `maxStarts`（`gateway-helpers.ts` 的 `createWorkboardDispatchHandler`），Taskfold 也有等价能力（`readOptionalPositiveInteger(rawMaxStarts, ...)`）。

## 三、Q3：OpenClaw 宿主层面的并发约束

**结论：宿主完全支持高并发，且把"多 worker 并行"当成一等公民的架构能力，不是靠插件各自实现。Taskfold 目前实际并发度（≈1）远低于宿主允许的默认上限（8）。宿主层不是瓶颈。**

证据（均为本机全局安装 `openclaw@2026.9.4` 的官方文档，不是插件文档）：

1. `docs/gateway/config-agents/entries-and-multi-agent.md:93`：`agents.entries.*.subagents.maxConcurrent`——"max concurrent child-agent runs across subagent execution. Default: `8`."；同页 `:94` `maxChildrenPerAgent` 默认 5，`:95` `maxSpawnDepth` 默认 5（1–5 可调）。
2. `docs/gateway/config-tools/sessions-and-subagents.md:108-129`：`agents.defaults.subagents.maxConcurrent` 同样默认 `8`，配置示例：
   ```json5
   agents: { defaults: { subagents: { maxConcurrent: 8, runTimeoutSeconds: 900, ... } } }
   ```
3. `docs/concepts/queue.md:19-21`：
   > A lane-aware FIFO queue drains each lane with a configurable concurrency cap (default 1 for unconfigured lanes; `main` uses `min(16, max(8, available CPU parallelism))`, and `subagent` defaults to 8).
   > Each session run is then queued into a **global lane** (`main` by default) so overall parallelism is capped by `agents.defaults.maxConcurrent`.
   即宿主的主会话 lane 默认并发上限至少 8（通常更高，取决于 CPU），子 agent lane 默认 8。
4. `docs/concepts/parallel-specialist-lanes.md`：官方专门的"如何设计多 agent 并行"指南（不是某个插件写的，是宿主概念文档），第二阶段给出显式配置样例：
   ```json5
   agents: { defaults: { maxConcurrent: 4, subagents: { maxConcurrent: 8, delegationMode: "prefer" } } }
   ```
   并明确把并发当"稀缺资源设计问题"："OpenClaw already serializes runs per session and caps global parallelism through the command queue. Specialist lanes add policy on top."
5. **没有找到 workboard/taskfold 专属的并发配置字段**——所有并发相关配置都在通用 `agents.*`/`messages.queue.*` 段，插件（包括 stock workboard）不需要也没有另开一套并发配置 schema。

**结论落地**：Taskfold 现在"实际一轮只起 1 个"，不是撞到了宿主的硬限制（宿主默认允许 8 个并发子 agent），是插件自己的 owner 分桶把请求压缩成了 1 个。

## 四、Q4：Taskfold 支持并行的最小改动是什么

**结论：Taskfold 已经原样继承了上游全部的 `agentId` 写入能力（工具、CLI、UI），且和上游一样，本地/CLI 调度场景下 `agentId` 不需要对应宿主真实多 agent 配置。理论上"给不同卡分配不同的 `agentId` 字符串"可以零代码解锁并行（受 `maxStarts=3`/轮限制）。但这条路径存在两个未被工具层强制的隐患，且和 Taskfold 自己更早的产品规划（"按 repo 并行"）不是同一个粒度。**

### 4.1 `agentId` 写入口已全部存在

| 位置 | 证据 |
|---|---|
| `taskfold_create` 工具 | `git show HEAD:src/backend/src/tools.ts:265`：`agentId: Type.Optional(Type.String({description:"Assigned agent id."}))` |
| `taskfold_specify` 工具（把 triage/backlog 卡定案为 todo 时可带 agentId） | `tools.ts:895` |
| `taskfold_decompose` 子卡 | `tools.ts:947` |
| `taskfold_reassign` 工具（改已认领卡的 assignee，需要 claim token） | `tools.ts:1097`：`agentId: Type.Optional(Type.String({description:"New assignee id."}))` |
| `taskfold_list` 按 agentId 过滤 | `tools.ts:215`/`:236`/`:246` |
| CLI `taskfold create --agent <id>` | `git show HEAD:src/backend/src/cli.ts:182`（`.option("--agent <id>", ...)`）→ `:205`（`agentId: options.agent`） |
| UI 卡片编辑表单 | `git show HEAD:ui/src/pages/projects/project-view.ts:2572`：`<label>...<input name="agentId" /></label>`；assignee 展示见 `:1847` |

即 Q4 第一问「有没有工具/网关/CLI/UI 写入口」——**全部都有**，且是从上游逐字段照搬来的，不是需要新增的能力。

### 4.2 `agentId` → 工作区解析机制也照搬了，行为与上游一致

- `resolveTaskfoldAgentWorkspace(config, agentId)`（`git show HEAD:src/backend/src/workspace-access.ts:96-97`）= `resolveAgentWorkspaceDir(config, agentId ?? resolveDefaultAgentId(config))`，与上游 `resolveWorkboardAgentWorkspace` 同构，同样接到宿主 `agents.entries`（`workspace-access.ts` 内 `resolveAgentConfig`/`listAgentIds` 直接读 `TaskfoldConfig` 里的 agents 段）。
- **本地/无远程客户端调度同样不受这条解析约束**：`resolveGatewayTaskfoldWorkspaceAccess`（`gateway-helpers.ts:69-84`）与上游逐行一致——`!params.client` 时直接 `{unrestricted: true}`；dispatcher 的 `if (!requestedWorkspace || kind==="scratch") { if (!workspaceAccess.unrestricted) { ... } }`（`dispatcher.ts:354`）在 unrestricted 时整段跳过。
- **推论**：Taskfold 目前的典型使用场景（单人本地、CLI 或进程内网关调用，没有配置远程 Gateway 客户端）下，给卡片设置任意不同的 `agentId` 字符串（哪怕宿主根本没配置对应的 `agents.entries`）就足以让 `resolveDispatchOwner` 把它们分进不同的 owner 桶，从而在同一次 dispatch pass 里并行起跑——**不需要改一行 Taskfold 代码，也不需要真的搭一个宿主多 agent 舰队**。这是本次调查里最重要的一条"最小代价"证据。

### 4.3 这条零代码路径没有被工具层强制的隐患

1. **不保证"同一份代码/同一个工作区的卡永远同一个 agentId"**：Taskfold 的工作区隔离（是否用独立 worktree）由 `card.metadata.automation.workspace.kind` 决定，与 `agentId` 无关（`materializeWorkspace`，`dispatcher.ts:145-147` 起）。如果操作者为了"解锁并行"给两张实际指向同一个 repo/同一份工作区的卡分配了不同 `agentId`，它们会真的同时起两个 worker 写同一份代码——这正是 `需求/9-风险与取舍.md:19` 早就点名的"同 repo 写入互踩"风险，工具层目前没有任何检查会拦这种情况。
2. **owner 分桶本身在 Taskfold 里只是应用层启发式，不是事务级保证**：`需求/15.8-并发与补偿设计.md` 第三节已核实，Taskfold 的 `selectStartableCards` 里的 `runningByOwner`/`selectedOwners` 只在内存里聚合单次 `list()` 快照，两个并发 dispatch pass（不同进程/不同 boardId 过滤）可能各自选中同一个新分配的 `agentId` 下的不同卡，两次 `claim` 的 revision CAS 都会成功——即"给卡分配不同 agentId 实现并行"这件事本身没问题，但"防止同一个 agentId 被两个 pass 同时超发"这层保证目前是缺的（上游有 `claimIfOwnerAvailable` 事务内断言，Taskfold 没有）。

### 4.4 另一条路径：改 `resolveDispatchOwner` 的默认回落

如果不想依赖"操作者手工给每张卡填 `agentId`"这个人工纪律，改动点是 `dispatcher.ts:225-232` 的最终回落分支（当前落到全局常量 `DEFAULT_DISPATCH_OWNER`）。这条路的代价和风险见「六、支持并行的方案选项」选项 B/C，这里不重复。

## 五、Q5：社区/官方其它插件的做法

**结论：需要明确区分"官方架构层的通用做法"和"某个具体插件（workboard）的选择"——生态里没有第二个可比较的先例，官方倾向是把并发当宿主级通用能力（agent/lane + `maxConcurrent`），而不是让业务插件各自发明调度模型。**

1. **workboard 是上游仓库里唯一带"卡片 + owner 并发调度"模型的扩展**：`gh api repos/openclaw/openclaw/contents/extensions` 拉到当前 157 个 bundled extension 目录，用 `task|queue|cron|board|schedul|flow|order|beam|orchestr` 关键词过滤，命中 `beam`、`llm-task`、`workboard` 三个；逐一核实：
   - `beam`：HTTP 网关的入站请求限流/镜像转发（`docs/plugins/beam.md:154,201`：`concurrency-limited` 指的是"进入的 HTTP 请求数"，与多任务执行调度是完全不同的领域，不可比。
   - `llm-task`：单次 JSON 生成的无状态工具（`extensions/llm-task/README.md`），**没有自己的调度器**，文档原文写明"Designed to be called from workflow engines (for example, Lobster via `openclaw.invoke --each`) without adding new OpenClaw code per workflow"——并发/迭代能力被有意设计成"甩给外部调用方"，插件自己不管。
   - `workboard`：本次调查的主体，唯一实现了"多张卡、按 owner 分桶、批量派发 worker"这套模型的扩展。
   - **结论**：生态（至少官方 bundled 部分）里没有第二个"任务看板 + 执行调度"的先例可比较，因此"其它插件怎么做并发"这一问在 bundled extensions 范围内**没有可参照的另一套设计**——只能拿宿主通用能力（下一条）做参照。
2. **官方文档明确把 workboard 的"一次一张/owner"写成设计行为**（见 Q1 证据 2），这是"官方文档说的"，不是某插件私下的选择——即官方对**这一类**任务看板类扩展的态度就是"owner 是并发单位"，多 worker 靠多 agent，不是靠看板插件内部加并发数配置。
3. **官方对"如何获得真并行"的建议落在宿主架构层，不落在具体插件**：`docs/concepts/parallel-specialist-lanes.md` 通篇是"把不同工作路由到不同 agent/lane"的通用指南，适用于任何插件，不是 workboard 专属，也印证了 Q2/Q3 的结论——并发是 `agents.*`/lane 的通用能力，业务插件只需要正确使用 `agentId`，不需要重新发明。
4. **ClawHub 第三方市场**：一次 `WebSearch`（"openclaw ClawHub plugin marketplace task queue concurrency workboard"）只返回 OpenClaw 官方发布说明和 `docs.openclaw.ai/plugins/workboard` 本身，没有找到独立于官方文档之外的、可具名引用的第三方并发最佳实践页面——**未能确证**，不代表不存在，只是本次检索强度下没有找到。

## 六、Taskfold 串行的根因

**一句话**：Taskfold 现在一次只跑一张卡，是因为它**原样继承**了上游 workboard「按 owner（claim/`agentId`）分桶、同一 owner 同时只留 1 个活跃槽位」的调度模型（这套模型本身在上游也一样会退化成串行——见 Q1），而 Taskfold 现网 102 张卡的 `agentId` 全部为空，全部回落到同一个全局常量 `"taskfold-dispatcher"`，导致"设计上支持多 owner 并行"的机制在"没人配置 `agentId`"这个实际使用场景下**表现为**全局串行。这不是 Taskfold 相对上游新引入的限制——上游代码今天原样部署、不配置 `agentId`，会得到一模一样的结果（Q1 证据 2/3 已用上游自己的官方文档和测试证明）。

但要分两层说清楚，避免"这就是继承的、不用管"的误判：

1. **表层原因（直接触发）**：`agentId` 数据缺失 → 回落到共享常量 → owner 分桶退化成 1 个桶。这一层"继承自上游"，上游同样如此。
2. **结构性原因（Taskfold 自己的设计空白）**：owner 分桶用的 key（`agentId`/claim owner）从一开始就和 Taskfold 自己更早写下的并行意图（"每个 repo 可以各自跑一个 Run"——见下一节）**不是同一个维度**。上游选 `agentId` 作为并发单位，是因为 workboard 面向的是"一个 Gateway、多个配置好的 agent 角色"这种场景（多人/多角色共享一个看板）；而 Taskfold 是"单人、多 repo/多项目"场景，天然的并行边界是 repo/工作区，不是 agent 角色。Fork 时把 owner 模型整体照搬，但没有针对 Taskfold 自己的使用场景重新设计 owner key，这是 Taskfold 自己的设计空白，不能全部归因于"继承上游"。

## 七、支持并行的方案选项（不代为取舍）

以下选项互不排斥，可以组合；每条给改动面、代价、风险，最终选择留给产品决策。

### 选项 A：不改代码，给需要同时跑的卡分配不同 `agentId`

- **改动面**：零代码改动。使用已存在的入口——CLI `taskfold create --agent <id>`、`taskfold_create`/`taskfold_specify`/`taskfold_decompose`/`taskfold_reassign` 工具的 `agentId` 参数、UI 卡片编辑表单的 assignee 输入框。
- **前提**：仅在本地/CLI/进程内（unrestricted）调度场景下成立（Taskfold 当前的典型使用场景属于此类）；`agentId` 不需要对应宿主 `agents.entries` 里的真实配置。若之后启用受限 Gateway 客户端调度，则 `agentId` 必须能在 `agents.entries` 解析出真实工作区，否则会报"target agent workspace is unavailable for restricted dispatch"（`dispatcher.ts` 对应分支）。
- **代价**：纯操作约定，没有任何机制强制"同一 repo/同一工作区的卡永远用同一个 `agentId`"——由使用者自己保证这条不变量，容易被后续新建的卡（不带 `agentId`，默认回落到共享常量）遗漏，行为上会变成"部分卡并行、部分卡继续挤在默认桶里串行"这种混合状态，需要使用者理解清楚才不会困惑。
- **风险**：低（不动核心代码）。但如果误给"指向同一份代码"的两张卡分配了不同 `agentId`，会触发 `需求/9-风险与取舍.md:19` 点名的"同 repo 写入互踩"——两个 worker 同时写同一个工作区，目前没有工具层检查会拦截这种情况。
- **额外已知缺口**：即使只用这条路径，`需求/15.8` 已指出 Taskfold 缺少上游那层"事务内 owner 断言"（`claimIfOwnerAvailable` 等价物），两个并发 dispatch pass 理论上仍可能让同一个 `agentId` 超发（见 Q1 证据 5、Q4.3 第 2 点）——这是一个独立于"要不要并行"的正确性缺口，即便维持现状不做任何并行化也建议单独跟踪。

### 选项 B：把 owner 分桶 key 从 `agentId`/常量改成"按卡片目标工作区（规范化 repo 根路径）分桶"

- **改动面**：核心调度路径——`resolveDispatchOwner`（`dispatcher.ts:225-232`）的最终回落分支，从 `DEFAULT_DISPATCH_OWNER` 改成基于 `card.metadata?.automation?.workspace` 的规范化仓库根路径（`sourcePath`/`path`）；`selectStartableCards`（`dispatcher.ts:233-283`）里两处调用点同步。
- **代价**：这条路径精确对齐 Taskfold 自己更早写下的产品意图——"多 repo 可各自运行一个 Run"（见下一节证据）——不需要使用者手工分配 `agentId`，同 repo 的卡自动挤到一起串行，不同 repo 的卡自动并行。
- **风险**：中——这是被 `需求/15.8-并发与补偿设计.md` 判定为"最高风险，动核心写路径"的同一段代码（该文档 Step 1 计划把 owner 断言搬进数据库事务）。两项工作有先后依赖，需要协调实施顺序：如果先按本方案换 owner key 语义，`需求/15.8` 里已经写好的 Step 0（把 `resolveDispatchOwner` 提取到 `store-constants.ts`）、Step 1（事务内断言）都要跟着换成新 key 重新设计和重新测试。
- **未决问题**：
  - scratch 卡（没有 `workspace.sourcePath`）没有 repo 根可用作 key，需要单独定义分桶策略（继续挤共享桶，还是给 scratch 卡也发一个近似"永远不限并发"的唯一 key——后者等于间接决定了 `需求/15.8` 分叉2 的答案）。
  - **Taskfold 目前完全没有 dispatcher owner 相关的自动化测试**（见「未能确证的问题」）——上游对应的 `dispatcher-ownership.test.ts`（30.1K）/`dispatcher.races.test.ts`/`dispatcher-compensation.test.ts` 在 Taskfold 里全部缺失（`git ls-tree -r HEAD --name-only` 确认 `test/` 下没有任何 `dispatcher*.test.ts`）。改这段代码前如果不先补一批等价测试，回归验证只能靠人工。

### 选项 C：默认 owner 不参与槽位限制（或槽位数从 1 放宽）

- **改动面**：`selectStartableCards`/`resolveDispatchOwner` 对默认 owner 分支的特殊处理。
- **代价**：改动最小，不需要理解 repo 语义。
- **风险**：中高——这正是 `需求/15.8-并发与补偿设计.md` 第八节「分叉2」列出的"路 B"，该文档**明确标注不推荐**，理由原文："与 `selectStartableCards` 现状和上游都不一致；无 `agentId` 的卡失去容量保护，可能同时起 N 个 subagent"。如果这些卡恰好指向同一个 repo，会直接撞上选项 A 同样的"同 repo 写入互踩"风险，而且是无差别地对所有未分配 `agentId` 的卡生效，覆盖面比选项 A 大。
- 本次调查认为该选项的风险特征与既有设计评审（15.8）已经给出的结论一致，此处不重复论证，仅作为选项列出。

### 选项 D：维持现状，把"一次一张"当作当前阶段的既定范围

- **改动面**：无。
- **代价**：无法并行，用户明确表达的等待时间问题不会缓解。
- **依据**：与 `需求/8.4-GSD内化与开发执行集成.md:38`、`需求/9-风险与取舍.md:19` 早已写明的"当前阶段默认每 repo 一个 active run"这条既有验收范围一致——从既有规划角度看，"不能同时跑多张卡"在 repo 内部本来就是阶段性的既定设计，真正待建的能力是 `需求/8.5-流程规划与Skills增强.md` M7 的"受控并行执行"（多 worktree + 显式合并 + 项目级开关，默认仍串行）。
- **风险**：无新增技术风险；机会成本是用户体验问题持续存在。

**本次调查的观察（非强制取舍）**：选项 A 是唯一"零代码、可立即验证"的路径，但需要使用者自行承担"避免同 repo 分配不同 agentId"的纪律；选项 B 是唯一直接对齐 `需求/4`/`需求/8.4` 既有文字表述（"多 repo 可各自运行一个 Run"）的路径，但动核心写路径且与 `需求/15.8` 已规划的工作有耦合，需要协调先后顺序；选项 C 已被更早的设计评审明确判定不推荐；选项 D 不解决问题但零风险。四者的代价性质不同（人工纪律 vs 工程风险 vs 已被否决 vs 机会成本），不存在一个在所有维度都更优的选项，取舍取决于产品对"现在就要能并行"这件事的紧迫程度。

## 八、与既有规划的关系

**结论：Taskfold 自己的既有规划已经多次、一致地表态过并发度设计意图，且这个意图与当前代码的实际行为不完全一致——这是本次调查里最应该被优先参考的一条依据。**

1. **既有规划设定的粒度是"每 repo 一个 active run"，不是"全局一个"**：
   - `需求/4-执行调度与AI.md:216`："**并行度控制**：GSD 的 wave 模型给出逻辑并行边界，但不能替代文件系统隔离。M2 默认每 repo 只允许一个 active run，并且必须在独立 worktree 中执行……M3 才评估同 repo 多 worktree 并行与合并策略。"
   - `需求/8.4-执行调度与Run控制台.md:69`（原文，最直接的一条）："**多 repo 可各自运行一个 Run；同 repo 多 worktree 并行、自动合并与 wave 并行留给 [[8.5-流程规划与Skills增强]]。**"
   - `需求/8.4-GSD内化与开发执行集成.md:38`："每个 repo 同时只允许一个 active run；每个 run 必须在独立 Git worktree 中执行……"
   - `需求/11-交接与待决.md:36`、`需求/1-规划评审.md:27,49`、`需求/12-竞品与替代方案.md:40` 反复重申同一件事："默认单 repo、单隔离 worktree、单 active run"。
   - **这条"多 repo 可各自运行一个 Run"与当前 dispatcher 的实际行为直接冲突**：当前 owner 分桶维度是 `agentId`/claim owner，与"repo"完全无关；两张指向不同 repo、都没填 `agentId` 的卡，今天会被塞进同一个默认 owner 桶，无法像既有规划说的那样"各自运行"。这是既有文字表述和当前实现之间一个明确的、可指出具体行号的落差，建议作为后续设计的最高优先输入。
2. **既有规划已经预告了"受控并行执行"作为未来能力，且明确给了边界**：`需求/8.5-流程规划与Skills增强.md:33-36,47`（M7 范围）："在 M4 单 run 模型保持可用的前提下，评估多个独立 worktree 的并行 run、队列容量、显式合并顺序和冲突处理。并行执行必须以项目级开关启用……不能依赖 wave"理论上不冲突"作为唯一保障。"验收条件第 3 条："对至少两个互不冲突的计划，可在独立 worktree 中受控并行运行……**默认仍保持单 repo 串行**。"即：即使未来做了"同 repo 多 worktree 并行"，产品对"默认行为"的态度依然是"单 repo 默认串行，并行是显式 opt-in"——这限定了「支持并行的方案选项」里任何一条改动的默认值都不应该是"默认全部并行"。
3. **`需求/15.8-并发与补偿设计.md` 已经摸到了这个问题的边缘，但停在"待定"**：该文档「风险与未确证项」第 1 条原文（`:436-446`）明确警告："**`DEFAULT_DISPATCH_OWNER` 的语义变成强制——最可能导致"上线后调度停摆"的一项**……若现网有多张无 `agentId` 的卡同时活跃，上线后它们会互相阻塞。"并给出了检查生产库的 SQL；「分叉2」（`:477-484`）把"默认 owner 的槽位是否也是 1"列为两条路都有明确代价的**待定**分叉，结论是"取决于查库结果"。这份文档写作时机比本次调查早，已经预见到"默认 owner 独占槽位"会造成大面积阻塞，但当时的落脚点是"要不要放宽默认 owner 的槽位保护"（对应本文档选项 C），**没有讨论"换成按 repo 分桶"这个方向**（对应本文档选项 B）。本次调查认为选项 B 与 `需求/4`/`需求/8.4` 的文字表述吻合度更高，值得和 `需求/15.8` 的既有结论放在一起重新评估，但这本身也是一个需要产品决策的点，不在本文档里替 `需求/15.8` 改结论。

## 九、未能确证的问题

1. **ClawHub 第三方插件市场的并发最佳实践**：一次 `WebSearch` 未找到独立于官方文档之外的可具名引用页面。不代表不存在，只是本次检索强度不足以确证。
2. **`lobster`（`openclaw.invoke --each` 所属的工作流引擎）的 `--each` 是否支持并发迭代**：`docs/tools/lobster.md` 只有一处提到 `--each` 的用法示例，没有找到并发/顺序执行的明确说明。`llm-task` README 提到"设计为被 Lobster 通过 `--each` 调用"，但 Lobster 自身的迭代并发模型本次未深入核实（判断价值有限：`llm-task`/`lobster` 与 Workboard/Taskfold 是完全不同的产品形态，即使确证了也不直接影响本文档结论）。
3. **`需求/15.8` 提到的生产库核查 SQL 本次未执行**（`SELECT count(*) FROM taskfold_cards WHERE agent_id IS NULL AND archived_at IS NULL AND (status='running' OR execution_status='running' OR claim_owner_id IS NOT NULL)`）——背景事实已给出"102 张卡 agent_id 全为空"，但"当前同时处于活跃状态（running/有效 claim）的默认 owner 卡数量"这个更精确的数字本次未重新查询，若要推进选项 B/C 的决策，建议先补这一步。
4. **选项 B 的具体实现细节（repo 根路径规范化、scratch 卡分桶策略、与 `需求/15.8` Step 0/1 的合并顺序）没有在本次调查里设计到位**——本文档只回答"这是不是一个可行方向、和既有规划是否吻合"，不是一份实施设计；如果产品决定走这条路，需要单独写一份类似 `需求/15.8` 那样的实施设计文档。
5. **上游 `openclaw/openclaw` 仓库里 `extensions/` 之外（比如宿主核心 `packages/` 或独立仓库）是否还有其它面向"多任务调度"的内部机制**：本次只检索了 `extensions/` 顶层目录列表，没有对宿主核心代码做等价深度的调度机制审计，`docs/concepts/queue.md`/`parallel-specialist-lanes.md` 是文档层面的核实，不是逐行读源码级别的核实（对比 Q1/Q2 对 workboard 源码的读取深度）。
