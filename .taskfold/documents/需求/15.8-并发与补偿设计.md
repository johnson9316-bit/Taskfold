## 一、Taskfold 现状：revision CAS 完整机制

### 1.1 revision 存在哪、谁递增

| 项 | 事实 | 证据 |
|---|---|---|
| 列 | `taskfold_cards.revision INTEGER NOT NULL DEFAULT 0` | `sqlite-store.ts:483`，走 `ensureColumn()` |
| 引入 | schema 6→7，提交 `57a8484`（2026-07-29） | 提交信息「卡片新增持久化 revision 列（schema 6→7）」 |
| 当前 schema | `SCHEMA_VERSION = 8` | `sqlite-store.ts:38` |
| 契约定义 | `TaskfoldCard.revision: number`，注释明确写了为什么不用 `updatedAt` | `src/contract/index.ts:508-514` |
| 递增者 | **唯一持久化边界** `stampCardRevisions()` 包裹 `TaskfoldKeyedStore`，在 `register` 与 `compareAndSwap` 两条路径上 in-place 递增 | `store-core.ts:105-123` |
| 递增函数 | `nextTaskfoldCardRevision()`：0 或非法值当「未盖章」→ 盖 1；否则 +1 | `store-constants.ts:41-48` |
| 新建卡 | `createDirect` 里 `revision: 0`，注释「Stamped to the first real revision by the persistence boundary below」 | `store-core.ts:550-551` |

关键设计：递增被收到 store 包装器里，**任何 call site 都无法绕过**。这是 `revision` 能当乐观并发 token 的前提（`store-core.ts:100-103` 注释原文）。

### 1.2 CAS 在哪个 SQL 语句里做

`TaskfoldSqliteCardStore.compareAndSwap`（`sqlite-store.ts:1530-1551`）：

```
runTransaction(db, () => {                           // BEGIN IMMEDIATE
  SELECT revision FROM taskfold_cards WHERE id = ?   // 先验
  if (row.revision !== expectedRevision) return false
  insertCard(db, value.card)                         // 后写（UPSERT + 7 张子表）
  return true
})
```

`runTransaction`（`sqlite-store.ts:125-136`）= `BEGIN IMMEDIATE` / `COMMIT` / 异常 `ROLLBACK`。`BEGIN IMMEDIATE` 在读 revision **之前**拿写锁，所以另一个 Gateway 进程不可能通过同一次检查（`sqlite-store.ts:1539-1540` 注释原文）。

连接层 pragma：`busyTimeoutMs: 5000`、`synchronous: NORMAL`、`foreignKeys: true`（`sqlite-store.ts:703-709`）；WAL 模式由宿主的 `configureSqliteConnectionPragmas` 负责（`sqlite-store.ts:594-595` 注释提到 WAL）。

### 1.3 冲突抛什么错

`TaskfoldRevisionConflictError(cardId, expectedRevision)`（`store-core.ts:86-95`）。三处抛点：

1. `updateCard` 的读前检查（`store-core.ts:637`）——快速失败，不进事务。
2. `persistCard` 的 swap 失败（`store-core.ts:817`）——真正的跨进程裁决。
3. `claimExecution` 的独立读前检查（`store-workflow.ts:100`）。

`persistCard`（`store-core.ts:803-819`）还有一条降级：后端不实现 `compareAndSwap` 时退回 `register`，只靠 `updateCard` 的读前检查 + 进程内队列。**这条降级路径就是所有 memory-store 测试走的路**（见 6.2）。

### 1.4 调用方怎么处理冲突

| 调用方 | 策略 | 证据 |
|---|---|---|
| `claim()` | `retryOnRevisionConflict` 重跑 `claimOnce`，`CARD_CAS_MAX_ATTEMPTS = 3`；重跑时重新读卡，让真正的竞争以 `card already claimed by X` 语义化错误浮现，而不是给调用方一个无法处置的 revision 冲突 | `store-core.ts:98`/`822-834`、`store-workflow.ts:245-253` |
| `claimExecution()` | **不重试**，`expectedRevision` 必填，冲突直抛。UI 的 prepare→start 两段式确认负责刷新 | `store-workflow.ts:83-88`，`card-execution.ts:264`→`ui/src/main.ts:923` |
| `reconciler.ts` | 传 `{ expectedRevision: card.revision }`，冲突被 per-card try/catch 吞掉，下一轮对新状态重算 | `reconciler.ts:109`、`:159-161`、`:176-180` |
| `dispatcher.ts` | 自己的 `store.update()` **不传** `expectedRevision`，只通过 `store.claim()` 间接用 | `dispatcher.ts:419-424`（claim）、`:466`/`:509`（无 CAS 的 update） |
| gateway `cards.update` | **不透传**，操作员编辑是 last-writer-wins | `gateway-workspace-methods.ts:69-90` |

### 1.5 另一层：进程内互斥队列

`enqueueMutation()`（`store-core.ts:214-222`）把所有写操作串成一条 Promise 链。它和 revision CAS **不是两层并发控制**，而是「进程内串行 + 跨进程 CAS」的分工。现状如此，本设计不改。

### 1.6 测试与实测

- `test/card-revision.test.ts`：⚠️ 实为 **8 个**用例（原写 6 个，2026-09-18 六路复核清点更正），`openSharedDatabase()` 开两个 store 指向同一 db 文件，模拟两个 Gateway（注释原文：「they share no in-process mutation queue, so only a database-level guard can keep them from both winning」）。
- [[VERIFICATION]]`:184-192`：四个独立客户端进程并发 claim 同一张卡，恰好一个赢；schema 6→7 在生产库副本（**103 张卡**，不是 102）上迁移，三列 + claim-owner 索引建好，迁移行 `revision 0`，首写盖 1，`expectedRevision: 0` 被拒。
- [[VERIFICATION]]`:321-326`：跨进程 CAS 自动化测试的最新结论。
- **没有任何一处实测或自动化测试涉及跨卡 owner 不变量，也没有涉及「回滚覆盖并发编辑」**。这两块是未被验证过的区域。

## 二、三个子项定性（本设计最重要的产出）

### 子项 1：`expectedUpdatedAt` 式 CAS —— **不需要做**

**Taskfold 已有严格更强的等价机制，且 `expectedUpdatedAt` 正是 57a8484 主动废弃掉的东西。**

证据链：

1. 提交 `57a8484` 的信息第四条原文：**「幂等键改用 claim token，`expectedUpdatedAt` 全链路改名 `expectedRevision`」**。也就是说 Taskfold 曾经就是 `expectedUpdatedAt`（fork 自上游），是**有意换掉的**。
2. `src/contract/index.ts:508-514` 的 `revision` 字段注释写明了理由原文：
   > Monotonic write counter. … Unlike `updatedAt` it never collides within a millisecond and never changes without an actual write.
3. 上游自己也承认 `updatedAt` 的毫秒碰撞问题：`store-core.ts:208-211` 回滚时必须写 `updatedAt: Math.max(Date.now(), current.updatedAt + 1)` 来人工保证单调。
4. Taskfold 的 `updatedAt` 会被 `moveMilestone`/`moveProject` 这类**直接 `store.register` 的路径**改动（`store-projects.ts:715`、`:784`），若把它当并发 token，语义会和 `revision` 不同步。

**明确反对**引入 `expectedUpdatedAt`：那正是"叠两层不兼容的并发控制"的教科书样本——两个 token 各自单调但互不同步，调用方无法判断该传哪个。**禁止。**

**唯一的真实缺口不是机制缺失，而是既有能力未接线**：`store.update()` 早就支持 `options.expectedRevision`，但 `taskfold.cards.update` 网关方法不透传（`gateway-workspace-methods.ts:69-90`），所以操作员编辑是 last-writer-wins。上游对应的 `workboard.cards.update` 透传 `expectedUpdatedAt`（`gateway-workspace-methods.ts:87-101`）并把冲突做成结构化错误让浏览器 rebase 草稿（`browser/lib/workboard/mutations.ts:88-100`）。→ 归为**子项 1 的小尾巴**，见 Step 4，**选做**。

### 子项 2：补偿回滚 —— **部分需要做（只做三路归并 + CAS 回滚，不引入 journal 框架）**

#### 2.1 上游 `store-compensation.ts` 究竟是什么（需求文档描述有误）

它**不是**"失败时回滚多步变更中已创建/更新的卡片"那种事务补偿。它是一个**单卡三路归并（three-way merge）逆补丁计算器**，纯数据变换，零 store 依赖：

- `invertWorkboardCardMutation(before, after, current)` → 一个"撤销 `after`→`before` 这次改动、但**保留第三方在此期间对 `current` 做的并发改动**"的卡片状态。
- `rollbackValue` 三条核心规则：`before === after` → 保留 `current`（本次没动，不碰）；`current === after` → 回到 `before`（没人动过，安全回滚）；否则逐层下钻（record 逐 key、带 `id` 的数组按 stable id 归并 + `insertRestoredValues` 恢复位置）。
- `invertWorkboardWorkspaceMutation` 是特化：workspace 与 workspaceAccess 视作一个宿主拥有的整体单元，宿主同字段编辑整体胜出，不做混合（`store-compensation.ts:159-161` 注释）。

**多步回滚**在另一处——`store-core.ts` 的 `withCardCompensation` + `compensationJournal`（`:137-167`）：记 `{before, after}` 序列，失败时 `toReversed()` 逐条逆放（`before` 缺失 → `rollbackCreatedCard` 删卡；否则 `rollbackUpdatedCard` 三路归并 + CAS 重试 3 次）。三个调用点：`create`（`store-core.ts:494`）、`linkCards`（`:1023`）、`decompose`（`store-workflow.ts:553`）。另有独立路径 `compensateWorkspaceMutation`（`store-core.ts:188`）供 `dispatcher-workspace.ts:81` 调用。

#### 2.2 Taskfold 的事务边界

`grep BEGIN|transaction(|immediate|exclusive` 结论：`runTransaction`（`BEGIN IMMEDIATE`）**只包住单卡的一次持久化**，四个用法——`register`（`:1528`）、`compareAndSwap`（`:1541`）、`delete`（`:1561`）、attachment delete（`:2078`）。`store-core.ts` / `store-workflow.ts` / `store-projects.ts` 里**完全没有** `BEGIN`。

**所以：Taskfold 的多步变更本来就不在一个 SQLite 事务里。** 上游的补偿机制不是为它自己的某个特殊约束存在的——它就是为"没有跨卡事务"这件事存在的，**Taskfold 有完全相同的问题**。原本设想的"如果本来就在一个事务里就不用照搬"这条出路不成立。

#### 2.3 但 Taskfold 已有手搓补偿三处

| 位置 | 触发 | 回滚动作 |
|---|---|---|
| `store-core.ts:424-441` | `create` 的 `setCardRequirementDirect` 失败 | `store.delete(card.id)` + `removeReferencesToCard(card.id)` |
| `store-core.ts:572-588` | `createDirect` 的父卡链接失败 | 同上 |
| `store-workflow.ts:740-823` | `decompose` 任一步失败 | `existingCardIds` / `reusedChildSnapshots` 快照；catch 里逆序删新建子卡、`store.register` 还原复用子卡、`store.register` 还原父卡 |

与上游的差距是**质量差距，不是有无差距**：

- 三处都用**整卡覆盖（`store.register`）还原快照**，不做三路归并、不带 CAS → 回滚窗口内的并发编辑被静默覆盖。上游的 `rollbackUpdatedCard` 用 `registerIfUpdatedAt` + 三路归并正是为此。
- `linkCards()`（`store-core.ts:1099-1107`）**完全没有补偿**（上游有）。
- 补偿里调 `deleteDirect` 会连带删订阅/附件，不可逆。

#### 2.4 两处更严重的无补偿整卡覆盖回滚（真实 bug 类，不是理论风险）

- `card-execution.ts:405-409`：run 启动失败 → `store.update(latest.id, { workspace: previousWorkspace ?? source.sourceWorkspace })`，**不传 `expectedRevision`**。
- `dispatcher.ts:503-511`：同类 → `store.update(card.id, { workspace: sourceWorkspace })`，同样不传。

窗口是"materialize worktree → 起 subagent 失败"之间（创建 git worktree + 起 subagent，秒级到十秒级）。期间 UI/agent 对同卡的任何编辑都会被这次回滚整卡覆盖。上游 `dispatcher-compensation.test.ts` 的两个用例正是这个场景（并发改 `notes` / 并发改 `workspace`）。

#### 2.5 定性判断

**不照搬** `withCardCompensation` + `compensationJournal`。理由：

- (a) Taskfold 只有 4 个多步写入点，其中 3 个已各自手搓且语义更贴自己的模型（`reusedChildSnapshots` 处理幂等键复用，上游无此概念）。引入 journal 是把已能工作的东西重写一遍，动核心写路径换不到新的正确性。
- (b) journal 的 `recordCardMutation` 要挂进 `updateCard` 每一次持久化，是**最高风险**的核心写路径改动。
- (c) `withCardCompensation` 的可重入判断（`if (this.compensationJournal) return await run()`）与 Taskfold 已有的 `enqueueMutation` 嵌套语义需要重新对齐，收益不匹配。

**要做的**：只取上游的**纯函数层**（零依赖、可逐行移植）+ 一个 store 方法，把现有 5 处回滚从"整卡覆盖"升级为"三路归并 + CAS"。**追加**，不改 `updateCard` 签名，不动 `enqueueMutation`。

#### 3.3 这是 Taskfold 自己引入的回归

- 提交 `14d698b`（2026-07-29，**早于 `57a8484` 三个提交**）删掉了 `pendingFlowboardDispatches` WeakMap，注释换成"每次 start 通过数据库 CAS 提交 claim，所以一张卡不会被 claim 两次"。
- 被删掉的那段注释原文：
  > `// Board filters must share their store's owner-capacity snapshot; otherwise simultaneous passes can claim different cards for the same active worker.`
- **上游 `dispatcher.ts:288-291` 至今原文保留这段注释和这个锁**。
- per-card revision CAS 保护的是"**同一张卡**不被 claim 两次"；它**不保护**"同一个 owner 不同时持有**两张不同的卡**"这个跨卡不变量。两个并发 dispatch pass（不同 `boardId` 过滤，或两个 Gateway 进程）各自 `list()` 快照后，各选中同 owner 的**不同**卡，两个 `claim` 的 CAS 都会成功。
- 上游用**三层**守：进程内 dispatch 串行（`pendingWorkboardDispatches`）+ per-card CAS + `claimIfOwnerAvailable` 事务内跨卡断言。Taskfold 只剩中间一层。

#### 3.4 第二处差距：claim 路径覆盖不全

Taskfold 的 owner slot 检查**只在 dispatcher 里**。绕过它的路径：

- `store.claim()` ← `taskfold_claim` agent 工具、`taskfold.cards.claim` 网关方法
- `store.claimExecution()` ← `taskfold.cards.execution.start` 网关方法（UI 的"开始执行"）

上游把 `ownerSlot` 放在 `updateCard` 的 options 里、由 `claimOnce` 统一传（`store-workflow.ts:156`），所以所有 claim 路径都受管。

#### 3.5 定性

**部分需要做**。谓词、slot owner 解析、5 分钟宽限期、内存聚合、`claim_owner_id` 列、索引都已有；缺的只有两样：(a) 把跨卡 owner 不变量搬进 `BEGIN IMMEDIATE` 事务；(b) 让两条直接 claim 路径也受管。

## 三、需求文档第 8 项的两处误读（顺带更正）

### 3.1 `runOperation` 不是互斥队列，也不是数据库事务

读完上游 `store-runtime.ts` 全文的结论：`runOperation` 是基于 `AsyncLocalStorage` 的**优雅关闭准入门**。

- `close()` 后新进来的操作抛 `"workboard store is closed."`；但已在 `runOperation` 作用域内的**嵌套**调用（`operationScope.getStore()?.active`）仍放行，以免多步操作在中途被拒（`store-runtime.ts:29-31`）。
- `close()` 循环 `while (this.operations.size > 0) await Promise.allSettled(this.operations)` 直到集合空，才 `closePersistence?.()`——避免 `node:sqlite` 的同步 `db.close()` 打断在飞的写（`:43-49` 注释原文）。
- **真正的互斥是 `enqueueMutation`（`store-runtime.ts:143-153`），和 Taskfold 的 `store-core.ts:214-222` 逐字节等价。**
- 粒度：`runOperation` 是全局、per-store-instance 的准入计数，**没有** per-card / per-board 粒度。它不参与并发控制。
- 与 SQLite 事务/WAL 的配合：**完全不参与**。事务在 `sqlite-store.ts` 的 `runSqliteImmediateTransactionSync`（等价 Taskfold 的 `runTransaction`），WAL/`busy_timeout` 由 pragma 层负责。

→ `runOperation` 的唯一增量是**关闭期安全**，这是一个与并发控制无关的独立问题。Taskfold 当前 `close()`（`sqlite-store.ts:2132-2135`）确实直接 `db.close()` 不等在飞写完，是一个真实但低频（仅进程退出/测试 teardown）的小缺口。**不属于本项范围，另记**（见 7.5）。这一项与 [[15.7-会话生命周期设计]] 步骤 6 是同一个缺口的两面，宜合并处理。

### 3.2 `store-compensation.ts` 不是多卡事务回滚

见 2.1。它是单卡三路归并；多卡 journal 在 `store-core.ts`。

## 四、方案

### 4.0 总原则：**不叠层。owner slot 是现有 CAS 的谓词扩展，不是第二层。**

`compareAndSwap` 本来就是"在 `BEGIN IMMEDIATE` 里先验后写"。owner slot 只是在**同一个事务**里多加一条前置断言——把 CAS 的准入谓词从「revision 匹配」扩成「revision 匹配 ∧ owner 有空位」。**一个事务、一个准入决策点、两种可区分的拒绝原因。**

角色划分必须写进代码注释，避免后人误判：

- **事务内断言**：唯一的正确性保证，跨进程有效。
- `selectStartableCards` 的内存聚合：**降级为调度选择的启发式**（避免无谓 attempt、保持优先级/公平性/fallback 顺序），不再是正确性保证。
- `enqueueMutation`：进程内串行，与 CAS 分工而非叠层，现状不改。
- **明确不恢复 `pendingTaskfoldDispatches`**。恢复它会让"进程内够用、跨进程不够用"的错觉回来，且与 `14d698b` 的取舍方向相反。事务内断言覆盖它的全部用途且跨进程有效。

### 4.1 owner slot：API 形状

**`persistence-types.ts`**

```
export type TaskfoldCasOutcome = "updated" | "conflict" | "owner_busy";

compareAndSwap?(
  key: string,
  expectedRevision: number,
  value: T,
  options?: { ownerSlot?: { ownerId: string; now: number } },
): Promise<TaskfoldCasOutcome>;
```

**取舍：扩展同一个方法 + 三态返回值，而不是像上游那样新加一个 `claimIfOwnerAvailable` 方法。**

理由：上游分两个方法是因为它的 `registerIfUpdatedAt` 返回 `boolean` 而 owner 版要返回枚举，分开是为了不动前者的调用方。Taskfold 的 `compareAndSwap` 只有 **1 个实现**（`TaskfoldSqliteCardStore`）、**1 个包装**（`stampCardRevisions`）、**1 个调用方**（`persistCard`），扩宽返回值的成本是 0；而两个并行方法会让 `store-core.ts` 里出现两条并行持久化分支（上游 `store-core.ts:874-905` 那段 `if (ownerSlot) {...} else if (registerIfUpdatedAt) {...}` 是可读性负债）。

**`sqlite-store.ts` 的 `compareAndSwap`** —— revision 比对通过后、`insertCard` 之前，在**同一事务内**：

```sql
SELECT id, status, agent_id, execution_status, archived_at, claim_json, claim_owner_id
FROM taskfold_cards
WHERE id <> @key
  AND archived_at IS NULL
  AND (claim_owner_id IS NOT NULL OR status = 'running' OR execution_status = 'running')
```

再用**从 `store-constants.ts` 复用的同一个 JS 谓词**逐行判断 `consumesOwnerSlot && slotOwner === ownerId`，命中返回 `"owner_busy"`。

**取舍：窄投影扫 + JS 谓词复用，不做纯 SQL 谓词，不新增 `slot_owner_id` 镜像列。**

理由：

1. **消除 SQL/JS 谓词漂移**——这是本项最大的实现风险。两份必须永远一致的谓词实现是经典 bug 工厂。
2. 谓词需要 `status` / `execution_status` / `archived_at` / `claim.expiresAt` / `agent_id`，这些**全部是 `taskfold_cards` 的一级列**（`sqlite-store.ts:1160-1170`），不需要加载 7 张子表、不需要走 `readCard`。相比上游的 `SELECT *` + `loadCardChildRows(db)` 全量子表预加载，已经快 1–2 个数量级。
3. `WHERE` 粗筛后的候选行数 ≈ 当前活跃卡数（现网个位数）。现网 103 张卡，硬上限 `MAX_CARDS = 2000`（`store-constants.ts:8`）。
4. **不动 schema、不 bump `SCHEMA_VERSION`（保持 8）、现网 103 张卡零迁移。**

为什么不能只用现有的 `taskfold_cards_claim_owner_idx`：`resolveDispatchOwner` 在无活跃 claim 时回落到 `card.agentId`，再回落到 `DEFAULT_DISPATCH_OWNER = "taskfold-dispatcher"`（`dispatcher.ts:30`）。也就是说 **slot owner 来自 `agent_id` 的卡，`claim_owner_id` 是 NULL**，纯 `claim_owner_id = @ownerId` 的索引查找会漏掉它们。这是设计时最容易踩的坑。

**明确不做** `slot_owner_id` 镜像列（`COALESCE(claim_owner_id, agent_id, 'taskfold-dispatcher')`）。它能把查询变成纯索引查找，但代价是第三个必须与 JS 保持同步的派生列（已有 `claim_owner_id` 一个），收益在 2000 卡上限下测不出来。若将来放宽 `MAX_CARDS` 或引入多 Gateway 常态并发，再评估——那时才需要 `ensureColumn` + `SCHEMA_VERSION` 9 + 回填（可照用 `revision 0` 的"懒迁移、首写盖章"思路）。

**保留** `taskfold_cards_claim_owner_idx`——虽然本方案的查询用不上它（`WHERE` 起头是 `id <> @key`），删它无收益，且它在未来任何 `claim_owner_id` 键控查询里立刻有用。但**必须在注释里更正**它当前"未被使用"的事实，别让下一个人以为聚合已经走索引了。

**`store-core.ts`**

- 新增 `export class TaskfoldOwnerBusyError extends Error`（携带 `cardId` 与 `ownerId`）。
- `protected updateCard(id, patch, options)` 的 `options` 加 `ownerSlot?: { ownerId: string; now: number }`。**非破坏性**（新可选字段）。
- `persistCard(card, expectedRevision, ownerSlot?)` 映射三态：`"conflict"` → `TaskfoldRevisionConflictError`；`"owner_busy"` → `TaskfoldOwnerBusyError`。
- `stampCardRevisions`（`:105-123`）的 `compareAndSwap` 转发**必须同步扩展第四个参数**。
- `retryOnRevisionConflict`（`:822-834`）**不改**——它只捕 `TaskfoldRevisionConflictError`，`TaskfoldOwnerBusyError` 自然穿透。**这一点很关键**：owner busy 是确定性拒绝，若被当成 revision 冲突重试，会把一次即时失败变成 3 倍延迟后的同一个失败。
- **`update()` 的公共签名不变**。`ownerSlot` 只存在于 `protected updateCard` 上。理由：owner slot 是 claim 准入语义，不是通用编辑语义；暴露到 `update()` 会诱使调用方在非 claim 场景滥用。

**`store-workflow.ts`**

- `claimOnce`（`:255`）的最终 `updateCard`（`:328` 那次带 `expectedRevision: claimable.revision`）加 `ownerSlot: { ownerId, now }`。紧随其后的 `updateCard(card.id, { status, agentId })`（`:344-351`）**不加**——槽位已经拿到了。
- `claimExecution`（`:75`）的 `updateCard`（`:128-138`）加 `ownerSlot: { ownerId, now }`。
- 两者签名不变。

**`store-constants.ts`（前置重构）**

把 `dispatcher.ts` 的 `consumesOwnerSlot` / `resolveDispatchOwner` / `cardHasActiveClaim` / `cardIsArchived` 提过来，导出 `taskfoldCardConsumesOwnerSlot(card, now)` / `taskfoldCardSlotOwner(card, now?)`（对齐上游命名）。`dispatcher.ts` 与 `sqlite-store.ts` 共用同一份。

**这必须是独立一步、独立跑测试**：`dispatcher.ts:259` 的 `claim?.ownerId ?? resolveDispatchOwner(card, now)` 与上游 `workboardCardSlotOwner(card)`（不传 `now`）不完全同形，提取时极易无意改变行为。

### 4.4 补偿：API 形状

**新文件 `src/backend/src/store-compensation.ts`**（纯函数，零 store 依赖，可从上游逐行移植）：

```
invertTaskfoldCardMutation(before, after, current): TaskfoldCard
invertTaskfoldWorkspaceMutation(before, after, current): TaskfoldCard
sameTaskfoldCardState(left, right): boolean
```

移植时**三处必改**：

1. 上游 `invertWorkboardCardMutation` 结尾 `{ ...merged, id: current.id, updatedAt: current.updatedAt }`；Taskfold 要保留 `id` + `revision`（`revision` 随后会被 `stampCardRevisions` 覆盖，保留只为语义清晰与类型完整）。
2. 上游 `sameWorkboardCardState` 只剔除 `updatedAt` 比较；Taskfold 版**必须同时剔除 `updatedAt` 和 `revision`**。**这是移植最容易漏的一点**——漏了会导致 `sameTaskfoldCardState` 永远返回 false，`rollbackUpdatedCard` 永远走满 3 次 CAS 然后抛错。
3. `hasOnlyStableIds` 的隐式契约：不满足时 `rollbackValue` 整体 `return current`，即**静默放弃该字段的回滚，不报错**。已核查 `TaskfoldMetadata`（`src/contract/index.ts:468-486`）的全部数组字段：
   - 带 `id`：`attempts`、`comments`、`links`、`proof`、`artifacts`、`attachments`、`workerLogs`、`notifications`、`events`、`sourceReferences` ✓
   - **不带 `id`：`diagnostics`（`TaskfoldDiagnostic` 按 `kind` 键控，`src/contract/index.ts:300-307`）**、`labels: string[]`（纯字符串）

   → `diagnostics` 与 `labels` 将永不回滚。`labels` 可接受；`diagnostics` 需要在设计里明确接受（diagnostics 本身是派生的、每轮 dispatch 重算，不回滚无害），并写一个测试钉住这个**有意的**行为，防止被当 bug 修。

**`store-core.ts` 新增**：

```
async compensateWorkspaceMutation(before: TaskfoldCard, after: TaskfoldCard): Promise<void>
```

public（dispatcher / card-execution 要调）。内部 `enqueueMutation` + 最多 3 次「读 `current` → `invert` → `persistCard(merged, current.revision)`」循环；`current` 不存在则直接返回；`sameTaskfoldCardState(current, merged)` 则无需写；3 次都冲突抛 `Error(\`card changed repeatedly during compensation: ${id}\`)`。用 `expectedRevision` 而非 `expectedUpdatedAt`。

### §六 第 8 条「用例 A 会失败」不成立

设计预期「并发改 `notes` 后被 workspace 回滚覆盖」在现状下会红，**实测不会**。原因：`updateCard()` 在写之前会重新 `this.get(id)` 拿最新卡片做 patch 合并，只有被 patch 命中的字段（这里是 `workspace`）会被覆盖，`notes` 这类未涉及字段天然保留最新值。

真正会红的是**用例 B（并发改 `workspace`）**，已贴修复前失败信息确认精确复现。两条都保留为回归测试：A 锁定「不相关字段永不丢失」这条不变量，B 验证修复本身。

### `linkCards` 单边链接：复现成功，已修

§4.4 标为选做、要求「先写复现测试，能复现再修」。复现成立：spy `updateCard` 让写 child 那半边失败后，父卡留下悬空的 `child`-type link、子卡完全没有 `parent`-type link。已用 `compensateCardMutation` 补上。

### decompose 回滚的一处归因陷阱（设计未提及）

按直觉在 catch 时再 fetch `after` 会**把回滚窗口里的并发编辑误判成自己这步的改动**进而覆盖掉。正确做法是在循环内逐次即时捕获 `parentAfter`/`reusedChildAfter`，把归因窗口收紧到「这一步操作自己的写」。三路归并的正确性依赖 `after` 必须是「我写完那一刻的状态」，不是「出错那一刻的状态」。

### 分层边界（本次新增的约束，设计未写）

`store-compensation.ts` 保持零 store 依赖、零 I/O；落盘集中在 `store-core.ts` 的 `compensateCardMutation()`。这是为 [[16-文件存储改造]] 预留——存储换成 Markdown 文件后纯函数层原样保留，只有 CAS 那层重做。已写进源码顶部注释。

另注意：`decompose` 与 `linkCardsDirect` 直接调 `compensateCardMutation` 而**不**包 `enqueueMutation`（它们本身已在调用方的 `enqueueMutation` 内，再包一层会死锁）；只有供外部调用的 `compensateWorkspaceMutation` 才包。

### 6.2 一个必须写进设计的结构性事实

**owner slot 在 memory keyed store 上完全不生效**（`persistCard` 走 `register` 回退分支）。上游有同样的问题（`dispatcher-ownership.test.ts` 用 `createMemoryStore()`，所以它那些 owner slot 测试其实靠的是 `pendingWorkboardDispatches` + `enqueueMutation`，不是 `claimIfOwnerAvailable`）。

后果：**"生产行为"与"大多数测试环境行为"不一致**。

→ **owner slot 的所有新增测试必须建在 `createTaskfoldSqliteStores` 上，用两个 store 指向同一 db 文件模拟两个 Gateway**（照 `test/card-revision.test.ts:27-39` 的 `openSharedDatabase()` 模式）。这一条要写进 `test/` 里相关 helper 的注释。见分叉 1。
   > ⚠️ **与 [[16-文件存储改造]] 分叉 A1 冲突，2026-09-18 六路复核后一并修订**：[[16-文件存储改造]] 已定案放弃多进程假设（A1：认定单 Gateway 进程独占，靠进程内 `enqueueMutation` 串行化），文件后端不会有第二个 `createTaskfoldSqliteStores`/`openSharedDatabase()` 可用。**上一段"必须建在 `createTaskfoldSqliteStores` 上"的要求作废**——照 A1 定案后的新范本改为：单进程内共享同一底层 store 的双 store 模拟（例如 `test/card-execution-compensation.test.ts` 的 `openSharedCardStore()`：两个 `TaskfoldStore` 共享同一个底层 store，天然适配单进程假设），断言"两条互不相识的 mutation queue 面对同一份持久化 revision，只能有一个 CAS 成功"，而不是依赖真实跨进程/跨数据库连接。后续 owner slot 落地时，本节及 6.3 的测试设计需按此范本重写，不得再照抄本条已作废的模式建测试。

### 6.3 需要新增的测试

借鉴上游 `dispatcher.races.test.ts` / `dispatcher-ownership.test.ts` / `dispatcher-compensation.test.ts` 的用例形状，但 **owner slot 相关的必须跑在 sqlite store 上**。

**owner slot（Step 1）**

1. **⭐ 跨进程 owner slot**（对应上游 `keeps one worker slot across 25 concurrent board dispatches`，升级为真跨进程）：一个 db 文件、两个 `createTaskfoldSqliteStores` → 两个 `TaskfoldStore`（无共享 `enqueueMutation`）；同 `agentId` 的两张 ready 卡分属两个 board；两个 store 各跑一次 `dispatchAndStartTaskfoldCards({ boardId })`；断言恰好 1 个 `started`、另一个进 `startFailures` 且文案含 owner busy、DB 里只有 1 张 `running`。**现状下会失败——先写它、确认它红、再实现。这是本设计最重要的一个测试。**
2. **同进程双 board dispatch**（对应上游 `serializes concurrent board dispatches for the same worker`）：单 store，spy `store.list()` 强制两个 pass 都在对方 claim 之前取到快照。断言同上。
3. **直接 claim 路径**：同 owner 已持有一张 active 卡时，`store.claim(otherId, { ownerId })` 抛 `TaskfoldOwnerBusyError`；`store.claimExecution(otherId, { ownerId, expectedRevision })` 同。**现状下也会失败。**
4. **owner busy 不被 `retryOnRevisionConflict` 重试**：spy 计 `compareAndSwap` 调用次数，断言 = 1。
5. **5 分钟宽限期三态**（对应上游 `does not let an expired review claim consume worker capacity`）：claim 未过期 → 占槽；过期但在 `CLAIM_RECLAIM_MS` 内 → **仍占槽**；超过宽限期 → 释放槽位。
6. **⭐ `stampCardRevisions` 转发 `ownerSlot`**：直接对 sqlite card store 调 `compareAndSwap(key, rev, value, { ownerSlot })` 断言返回 `"owner_busy"`；再经 `TaskfoldStore` 调 claim 断言同样被拒。**专门钉住 Step 1 那个"漏转发则静默失效"的风险点。**
7. **`agent_id` 回落分支**：slot owner 来自 `agent_id`（`claim_owner_id IS NULL`）的活跃卡也占槽。**这一条覆盖 4.1 里指出的"纯 `claim_owner_id` 索引查找会漏掉"的坑。**

**补偿（Step 2/3）**

8. **⭐ 并发编辑不被 workspace 回滚覆盖**（对应上游 `dispatcher-compensation.test.ts`）：一个 db 文件、两个 store（dispatch store + host store）；`subagent.run` 里让 host store 并发改 `notes`（用例 A）或改 `workspace`（用例 B），然后抛错；断言回滚后 `notes` 是 host 写的值（A），`workspace` 是 host 写的值（B）。**现状下 A 会失败**（notes 被整卡覆盖）。
9. **补偿 CAS 耗尽**：spy 让 `compareAndSwap` 持续返回 `"conflict"`，断言 3 次后抛 `card changed repeatedly during compensation`。
10. **`decompose` 回滚保留并发编辑**：decompose 中途失败且期间有对父卡的并发编辑。
11. **纯函数单测 `invertTaskfoldCardMutation`**：`before===after` 保留 `current`；`current===after` 回到 `before`；stable-id 数组增/删/改/位置恢复；`sameTaskfoldCardState` 排除 `updatedAt` **和** `revision`；**`diagnostics`（无 `id`）与 `labels`（纯字符串）不回滚是有意行为**。

## 七、风险与未确证项

1. **⚠ `DEFAULT_DISPATCH_OWNER` 的语义变成强制——最可能导致"上线后调度停摆"的一项。**
   所有 `agentId` 为空的卡共享同一个默认 owner 槽位 `"taskfold-dispatcher"`。现状 `selectStartableCards` 已是这个语义，但它只是**启发式**（可被绕过）；Step 1 后它变成**事务级强制**。若现网有多张无 `agentId` 的卡同时活跃，上线后它们会互相阻塞。
   **未确证，实施前必须查一次生产库**：

   ```sql
   SELECT count(*) FROM taskfold_cards
   WHERE agent_id IS NULL AND archived_at IS NULL
     AND (status='running' OR execution_status='running' OR claim_owner_id IS NOT NULL);
   ```

   若 > 1，先决定：放宽默认 owner 的槽位数（见分叉 2）还是给卡补 `agentId`。

2. **SQL/JS 谓词漂移（已缓解，但仍是首要长期风险）。** 本方案靠"复用同一个 JS 谓词函数"消除，代价是事务内要做一次窄投影扫。若将来有人"优化"成纯 SQL 谓词，漂移风险立刻回来。→ 在 `sqlite-store.ts` 的 `compareAndSwap` 里写明这条禁令与理由。

3. **`BEGIN IMMEDIATE` 内的扫描时长 = 全局写锁持有时长。** 现网 103 张卡、窄投影、无子表加载，量级可忽略。但 `MAX_CARDS = 2000` 是硬上限，`busyTimeoutMs = 5000`。**未实测**：2000 卡时这个扫描在事务内的耗时。→ Step 1 顺手加一个 2000 卡基准测试，断言的是"并发 claim 不触发 `SQLITE_BUSY`"，不是具体毫秒数。

4. **owner slot 在 memory store 上不生效**，导致大多数现有测试对它无感知。见 6.2 与分叉 1。

5. **上游 `runOperation`（优雅关闭）未纳入本设计。** Taskfold 的 `close()`（`sqlite-store.ts:2132-2135`）直接 `db.close()`，不等在飞的写。`node:sqlite` 的 `DatabaseSync` 是同步的，单次 `runTransaction` 不会被打断；但 `store-core.ts` 的一次 `updateCard` 跨多个 await，中间 `db` 被关会抛。影响面：进程退出与测试 teardown。**未确证是否在实际中触发过。** → 与 [[15.7-会话生命周期设计]] 步骤 6（`store-lifecycle` 等价物）是同一缺口的两面，宜合并处理；若 `npm test` 出现过偶发 teardown 报错，优先怀疑这里。

6. **需求文档第 8 项对上游的两处描述有误**，已在本文第三节更正。若其它文档引用了那两句，需一并更正。

7. **`linkCards` 是否真的会留下单边链接，未确证**（上游给它加了补偿，Taskfold 没有）。→ 先写复现测试，能复现再修。

8. **`invertTaskfoldCardMutation` 移植的正确性。** 上游这套 `rollbackValue` 有相当的隐式契约（`ABSENT` 哨兵、`hasOnlyStableIds` 的**全量**要求、`insertRestoredValues` 的位置恢复）。Taskfold 卡片结构与上游高度同构但多了 `kind` / `milestoneId` / `revision` / `delivery` / `sourceReferences` / requirement 层级。数组字段的 `id` 情况已在 4.4 核查完毕；但 `delivery`（对象）与 `sourceReferences`（带 `position` 的数组）的归并行为**未逐字段验证**。

9. ~~**Step 4 的 `readPatch` 陷阱**若漏处理，`expectedRevision` 会被当成 card 字段进入 patch（可能被 `normalizeMetadata` 静默丢弃，也可能不）。低概率但静默。~~ **已消解**：实施时核实 `updateCard` 是逐字段白名单赋值，`expectedRevision` 没有字段位可落，当前不会现形；剔除函数已作为防御性措施实施（`07aed26`），见 §4.5 更正后的说明。

## 八、待定分叉点

### 分叉 1：memory store 上 owner slot 是否生效？

- **路 A（推荐）**：不生效，靠 sqlite-based 测试覆盖 + helper 注释说明。
  代价：测试环境与生产行为不一致，新人容易踩；owner slot 的覆盖率完全依赖那 7 个新增测试。
- 路 B：给测试的 `keyedStore<PersistedTaskfoldCard>()` helper 实现 `compareAndSwap` + ownerSlot。
  代价：一批现有测试突然从 `register` 分支切到 CAS 分支，预计 3–8 个用例需要改断言（`test/project-store.test.ts`、`test/card-execution.test.ts`、`test/reconciler.test.ts` 都用 memory store）；收益是所有测试都覆盖 owner slot。

**待定。**

### 分叉 2：`DEFAULT_DISPATCH_OWNER` 的槽位是否也是 1？

- **路 A（推荐，对齐现状与上游）**：是 1。
  代价：现网若有多张无 `agentId` 的活跃卡，Step 1 上线后会互相阻塞。**先查库（风险 1）。**
- 路 B：默认 owner 不参与 owner slot（`ownerId === DEFAULT_DISPATCH_OWNER` 时跳过断言）。
  代价：与 `selectStartableCards` 现状和上游都不一致；无 `agentId` 的卡失去容量保护，可能同时起 N 个 subagent。

**待定（取决于查库结果）。**

### 分叉 3：子项 1 的尾巴（`cards.update` 透传 CAS）做到哪一层？

- **路 A（推荐）**：只做网关透传 + 结构化冲突错误（Step 4），UI 暂不接线。
  代价：能力可用但当前无人用。收益：给 [[15-上游2026.9.4差异评估]] 第 9 项（Control UI 原生化）预留好接口。
- 路 B：不做。
  代价：操作员编辑继续 last-writer-wins。考虑到 Taskfold 是单人工具、UI 卡片编辑面只有 delivery 六个字段，风险确实低。
- **路 C（明确反对）**：连 UI 一起做。
  代价：要把 revision 带进 `ui/src/main.ts` 的表单状态，而第 9 项马上要把整个 `ui/` 重写成 `browser/`（已定、下一步就做），现在做等于白做。

**待定（A 或 B）。**
