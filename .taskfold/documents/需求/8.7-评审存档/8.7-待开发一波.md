# 8.7 OpenClaw ACP 执行编排方案

> **文档状态**：需求与实施方案存档。2026-07-30 修订为官方 OpenClaw ACP 路径；
> 本文件保留为第 1 至第 3 期实施基线，顺序清单见
> [`实施清单-第1至3期.md`](实施清单-第1至3期.md)。
>
> **交付范围**：一个前置 Spike + 五期交付，见 §9。本次不包含运行时代码与配置的实际改动。
>
> **核心决定**：Taskfold 直接使用 OpenClaw 公共 ACP Runtime SDK 与官方
> `@openclaw/acpx`；不以第三方 `openclaw-code-agent`、LLM Bridge 或文本工具解析作为
> 编码执行主路径。

## 0. 决策与文档关系

### 0.1 已定决策

1. **官方执行契约**：Taskfold 的编码执行后端为 OpenClaw ACP Runtime。Runner 优先通过公开模块
   `openclaw/plugin-sdk/acp-runtime` 的 `getAcpSessionManager()` 调用
   `initializeSession`、`runTurn`、`getSessionStatus`、`cancelSession`、`closeSession` 和
   `reconcilePendingSessionIdentities`。不得另建 ACP session metadata、runtime handle 缓存、
   per-session queue 或通用恢复器；低层 backend 仅用于 `doctor()` 预检与必要诊断。
2. **官方 runtime**：`@openclaw/acpx` 是生产运行时依赖；缺失、禁用、`doctor` 失败或版本不在
   支持范围时，拒绝启动，不降级到旧 subagent 路径。
3. **多 CLI 策略**：Claude Code 为第 1 期唯一阻塞级 harness；Codex 在第 5 期单独验证后开放；
   OpenCode 仅实验性支持，不阻塞主路径发布。Profile 使用 ACP harness id，而非在 Taskfold 中
   解析某个 CLI 的私有输出。
4. **Taskfold 是控制面**：Card、run、审批、审计、并发槽、worktree 租约、Git 安全和项目 UI
   属于 Taskfold。OpenClaw ACP 负责外部 harness 的会话、turn、流式事件、取消和 runtime
   清理。编码 harness 负责模型、登录、原生工具及其自身会话历史。
5. **不让 LLM 处于控制路径**：状态投影来自 ACP 结构化 handle、turn event、status 和
   terminal result。LLM 只可生成计划摘要、失败摘要与 review 摘要，摘要不参与状态迁移、
   审批、合并、PR 或权限判定。
6. **不复制 transcript**：Taskfold 只持久化外部引用、事件摘要、审计和必要产物。原始会话仍在
   ACP/harness 一侧。
7. **单 repo 单 mutable run 起步**：第 1、2 期每仓库只允许一个写入型 run 和一个隔离
   worktree；第 3 期完成 `writeScope` 与并发槽后才允许受控并行。

### 0.3 不再成立的旧假设

- 不再创建 OpenClaw 编排 Agent（Bridge），不依赖可信聊天投递路由、`:cron:` sessionKey
  豁免或 wake 回调。
- 不再调用或解析 `agent_launch`、`agent_respond`、`agent_output`、`agent_sessions`、
  `agent_merge`、`agent_pr` 等第三方工具。
- 不再读取 `code-agent-sessions.json` 等第三方私有状态文件。
- 不再把“批准计划”映射为第三方 `approve=true` 或 `bypassPermissions`。Taskfold 的计划审批是
  自己的工作流门，未经审计的用户操作绝不能替 runtime 放权。

### 0.4 官方能力复用边界

OpenClaw 已实现 ACP session runtime 和 Workboard 的通用 Card 运行上下文；Taskfold 不重复实现
下列能力：

1. **ACP 会话运行层**：OpenClaw `AcpSessionManager` 是 ACP session metadata、runtime handle、
   单 session turn queue、状态、取消、关闭和启动身份对账的唯一所有者。
2. **通用 Card 运行记录**：Workboard 的 `execution`、attempt、event、comment、proof、
   artifact、attachment、claim 和 worker log 是 Card 侧的有限运行上下文。Taskfold 可向这些字段
   写可裁剪 UI 投影，但不把它们当作审计或 run 真相。
3. **原始会话与 transcript**：ACP/harness 仍是原始事件和对话历史的权威来源。Taskfold 只保存
   session 外部引用、结构化里程碑、脱敏摘要和审计事实。
4. **worktree 原语**：优先复用 OpenClaw runtime/Workboard 的 managed-worktree API；Taskfold
   只定义仓库准入、租约、基线、配额、回收确认和并发策略，不再另造通用 shell worktree 后端。

Taskfold 仍必须拥有 `taskfold_runs`、append-only audit、GSD 映射、人工审批、Git 安全策略、
`waitingForHuman`、`external_state_unknown`、并发槽和项目级 Runs 视图。它们不属于 ACP 或
Workboard 的通用会话运行职责。

## 1. 目标与边界

Taskfold 将开发执行建模为可排队、可观察、可暂停、可恢复和可复盘的异步 run；它不是第二个
编码 agent，也不是通用终端驾驶舱。

```text
Taskfold Card / UI / run ledger
  -> Taskfold ACP Runner
    -> OpenClaw 公共 ACP Runtime SDK
      -> 官方 @openclaw/acpx
        -> Claude Code / Codex / OpenCode
```

| 层级 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| Taskfold Card / UI / run ledger | Card 状态、用户操作、审批、审计、队列、并发、安全策略、worktree 租约 | 解析特定 CLI 的私有协议或保存完整 transcript |
| Taskfold ACP Runner | 调用官方 ACP Runtime、关联 handle、消费结构化事件、同步状态、取消和关闭 | 决定产品或工程审批、自动合并、自动完成 Card |
| `@openclaw/acpx` | 启动/恢复 ACP harness、runtime 生命周期、adapter 进程清理、背景运行时能力 | Taskfold 的工作项、依赖、审计、Git 策略 |
| Claude Code / Codex / OpenCode | 分析、修改、测试、原生工具、模型与供应商会话 | Taskfold Card 生命周期、并发槽与审批记录 |

**不做的事**：

- 不将 Kandev、Kanbots、dev-3.0 或任何外部控制台嵌入 Taskfold。
- 不在 M1-M3 实现 Docker、SSH、远程 executor 或 tmux 驾驶舱。
- 不把普通 OpenClaw `sessions_spawn` 的 LLM tool call 当作 Taskfold 的控制 API。
- 不让 ACP 的可选 `plan` event 或任意 harness 文本自动改变 Card 状态。

## 2. ACP Runner 契约

### 2.1 公开 API 与版本边界

Taskfold 只依赖 OpenClaw 已公开导出的：

```ts
import {
  getAcpSessionManager,
  requireAcpRuntimeBackend,
  readAcpSessionEntry,
} from "openclaw/plugin-sdk/acp-runtime";
```

Runner 在每次启动前调用 backend `doctor()`。运行时先取得一次
`getAcpSessionManager()`，并只通过下列结构化 manager 接口交互；不得在 Taskfold 侧复制其
session handle、队列或状态机。

| Taskfold 动作 | OpenClaw ACP manager 调用 | 规则 |
| --- | --- | --- |
| 创建或恢复会话 | `initializeSession(...)` | `sessionKey` 由 Taskfold 生成且稳定；`cwd` 必须为受租约保护的 worktree。 |
| 开始一个 turn | `runTurn(...)` | 每个 turn 有 Taskfold `requestId` 幂等键；通过 `onEvent` 接收结构化事件。 |
| 发送追问或返工要求 | `runTurn({ mode: "steer" })` | 仅对当前 Card 已关联且仍有效的 `sessionKey` 生效。 |
| 查询外部状态 | `getSessionStatus(...)` | 只读；用于重启恢复和轮询兜底。 |
| 中止当前 turn | `cancelSession(...)` | 用户操作；必须记录 actor、原因与结果。 |
| 关闭会话 | `closeSession(...)` | 用户确认或清理策略触发；是否丢弃持久状态必须显式。 |
| 新建而非恢复 | `closeSession({ discardPersistentState: true, clearMeta: true })` 后 `initializeSession(...)` | 仅在 harness 不支持恢复或用户明确新开会话时使用。 |

`runTurn` 的 `text_delta`、`status`、`tool_call`、`done`、`error` event 和 manager 写入的
session status 是 run 投影的事实来源。未知 event tag 可以作为展示摘要保存，但不能驱动破坏性状态
迁移。

### 2.2 外部关联与会话寻址

Taskfold 生成自己的 `runId`、`requestId` 和 ACP `sessionKey`。`sessionKey` 使用稳定 ASCII
命名，例如 `agent:taskfold:acp:<runId>`；它不是用户可编辑标题，也不通过 name 模糊寻址。

每个 ACP 会话引用至少保存：

| 字段 | 含义 |
| --- | --- |
| `backend` | 固定为 `openclaw-acp` |
| `acpBackend` | 当前 runtime backend，例如 `acpx` |
| `harnessId` | `claude` / `codex` / `opencode` 等 ACP target id |
| `sessionKey` | OpenClaw ACP session key，是 Taskfold 的主要外部寻址键 |
| `backendSessionId` | harness 暴露时保存；仅作展示、恢复诊断和终端接管候选 |
| `acpxRecordId` / `agentSessionId` | runtime 提供时保存，不以缺失为错误 |
| `cwd` / `worktreeLeaseId` | Taskfold 分配的隔离目录与其租约 |
| `runtimeVersion` / `pluginVersion` | 启动时记录，用于升级后的兼容性诊断 |

任何 API 调用均以已保存的 handle 为输入；禁止以展示名称、最近 session、CLI 输出正则或 LLM
推断重新定位会话。

### 2.3 Profile 与 harness 能力

Profile 是版本化的执行配置，不是另一套任务模型。每个 Profile 至少含：

```text
id, version, harnessId, model?, thinking?, permissionProfile,
systemPromptTemplate, mutable, requiresPlanApproval,
writeScope, maxConcurrent, timeout, budget, allowedWorkspaceRoots
```

- `harnessId` 必须在 `acp.allowedAgents` 与 Taskfold allowlist 中同时允许。
- `model`、能力和权限配置不得假定跨 harness 可移植。
- `permissionProfile` 必须适合非交互编码 run；Taskfold 不会自动点击 harness 的原生权限提示。
- `requiresPlanApproval` 是 **Taskfold 策略**。若 profile 要求先计划，首个 turn 只请求计划；
  用户批准的证据写入审计后才允许发送实现 turn。
- `mutable=false` 的 planner、tester、reviewer 不能取得写入型 worktree 租约。

ACP 的 `plan` tag 可以改善 UI 展示，但其存在性、内容与语义因 harness 而异。计划是否可审批，
只能由 Taskfold 已保存的计划文本、内容哈希、版本和人工审计记录决定。

## 3. 单 Card 生命周期

### 3.1 启动

```text
Card ready
  -> Taskfold 执行启动前校验
  -> revision CAS 写入 launching
  -> 领取 repository / branch / writeScope 并发槽
  -> 创建隔离 worktree 与租约
  -> ACP Runner initializeSession(cwd=worktree)
  -> ACP Runner runTurn(plan 或 execute)
  -> 持久化 handle、event 摘要、审计记录
  -> Card running 或 waitingForHuman
```

启动的 CAS 幂等键为 `cardId + profileId + revision`。CAS 失败时不创建 worktree、不调用
`initializeSession`。若关联持久化失败，Runner 立即 `closeSession(...)`，释放并发槽和 worktree
租约，并记录失败。

新 Card 必须有：

```text
automation.executionPath: "openclaw-acp" | "legacy-subagent"
```

值在创建时确定，改写需要显式人工操作和审计。所有旧 dispatch、claim、CLI、dashboard action
和 tool 入口必须拒绝 `openclaw-acp` Card，不能使其回退到旧 `runtime.subagent.run` 路径。

### 3.2 人工决策

| 用户操作 | Taskfold 的确定性行为 |
| --- | --- |
| 查看计划 | 展示原文或附件、内容哈希、版本、产生时间和 harness 能力。 |
| 批准计划 | 写 `plan_approved` 审计事件，绑定 `runId + planHash + planVersion + actor`，再允许下一个实现 turn。 |
| 要求修改 | 写 `plan_changes_requested` 审计事件，并以 `mode: "steer"` 发送用户原文。下一份计划必须有不同版本或哈希。 |
| 拒绝计划 | 写 `plan_rejected`，Card 进入 `blocked`；不自动 cancel 其他无关 run。 |
| 回复/追问 | 用当前 handle 发起 `mode: "steer"` turn。 |
| 主动终止 | `cancel` 当前 turn；如用户明确关闭会话，再 `close`。 |
| 退回修改 | 优先复用当前 handle；backend 不支持恢复时，创建新 ACP session，并把原会话和上下文摘要加入会话链。 |
| 合并、PR、丢弃 worktree | 均为 Taskfold 的显式 Git 操作，必须二次确认，不由 harness 或 ACP event 自动触发。 |

Card 成功编码只进入 `review`，永不自动 `done`、自动合并或自动创建 PR。

### 3.3 状态映射

| ACP / Taskfold 事实 | Card 状态 | UI 行为 |
| --- | --- | --- |
| CAS 已成功、尚未拿到 handle | `launching` | 禁用除取消外的执行动作。 |
| active turn 或 runtime 可查询 | `running` | 展示 harness、耗时、最近事件和成本口径。 |
| 已审计划、用户追问、预算耗尽、权限或环境问题 | `running` + `waitingForHuman` | 在 Card 与项目级 Runs 视图显著显示原因。 |
| turn `completed` 且验收产物齐全 | `review` | 展示变更、测试、review 与 worktree 摘要。 |
| turn cancelled、runtime failure、人工拒绝、协议违规 | `blocked` | 保留诊断、审计和恢复入口。 |
| status 连续无法确认 | `running` + `external_state_unknown` | 只允许刷新、查看、取消或强制解绑，禁止批准、合并、PR。 |
| 合并/PR/清理失败 | `review` + `waitingForHuman` | 展示冲突或失败原因；不自动派生新 agent run。 |

`waitingForHuman` 是合法稳定态，不是超时。`external_state_unknown` 有自动恢复、指数退避和人工
强制解绑出口，见 §7。

## 4. Worktree、Git 与权限边界

### 4.1 worktree 所有权

ACP Runtime 接收 `cwd`，而 OpenClaw 已提供 managed-worktree 原语；两者都不替 Taskfold
定义看板级 Git 策略。因此：

1. **Taskfold Git Adapter** 优先调用官方 worktree API 创建或取得隔离 worktree，并将 `cwd`
   传给 ACP；不得再造一套通用的 shell worktree 生命周期实现。
2. Taskfold 保存 worktree lease、实际 `baseCommit`、源分支、路径摘要和清理状态；ACP/harness
   不拥有 Card 的 worktree 生命周期。
3. tester/reviewer 需要独立环境时，Taskfold 用 `git worktree add --detach` 从已记录 commit
   创建只读快照。测试前后检查受跟踪文件 diff；非预期修改即阻塞。
4. Card 归档、删除或完成前必须决定：合并、创建 PR、丢弃或“留待人工处理”。不能静默删除
   worktree。

### 4.2 Git 安全

默认策略：

- 主仓库 dirty 时拒绝启动；可通过项目级显式配置放宽，但合并前仍必须二次检查。
- 启动前记录仓库根、HEAD、当前分支、dirty 状态、submodule 状态和 `baseCommit`。
- 只允许 merge commit；默认 `push=false`、`deleteBranch=false`。推送和 PR 是独立人工动作。
- 合并前验证 worktree 的提交基线、目标 base 分支和允许分支白名单。
- 目标目录不得包含 Taskfold 的 SQLite、凭据或 plugin 数据目录。

### 4.3 权限

Taskfold 不以 prompt 充当权限系统：

- `allowedWorkspaceRoots`、workspace 白名单、Profile `mutable` 和 ACP permission profile 必须
  在启动前由代码校验。
- 用户批准“计划”不等于扩大 ACP/harness 的全局权限；实际允许的工具与文件范围来自已启动
  session 的 permission profile。
- 原生权限请求无法在 Taskfold 中可靠表示时，run 必须进入 `waitingForHuman` 或被拒绝启动，
  不能自动批准。
- 所有来自 harness 的文本经统一脱敏后才写 Card、审计或附件。

## 5. 持久化与审计

### 5.1 数据落点

run 级事实不得塞进有上限的 Card metadata。新增或定稿以下独立表：

```text
taskfold_runs
  id, card_id, profile_id, backend, acp_backend, harness_id,
  session_key, backend_session_id, acpx_record_id, agent_session_id,
  worktree_lease_id, source_branch, base_commit, write_scope,
  status, awaiting_reason, external_status, last_synced_at,
  started_at, ended_at, cost_usd, duration_ms, summary

taskfold_run_events
  id, run_id, seq, kind, summary, detail_json, created_at

taskfold_audit_events
  id, seq, card_id, run_id, kind, actor_type, actor_id,
  detail_json, prev_hash, created_at
```

`taskfold_audit_events` 只 INSERT，不 UPDATE/DELETE。Card 上只保留可裁剪投影，不能作为审计
真相。

Workboard/Card 的 `execution`、attempt、event、comment、proof、artifact 和 attachment 仅作为
这些表的有界 UI 投影。不要把每个 `text_delta` 写入两边；只投影最近状态、关键里程碑、可操作
错误和已脱敏的产物摘要。

`runs.backend` 的标准值为 `openclaw-acp`；`host_ref_kind` 为 `acp_session`，
`host_ref_id` 为 `sessionKey`。若 harness 提供可恢复会话 id，另写
`resumable_session_id`，但 UI 必须明确它是“已实测支持”而不是通用承诺。

### 5.2 会话链与审计覆盖

一张 Card 可有多次 ACP session：计划重开、退回修改、profile 切换或人工恢复失败后重试都会
产生新引用。每次关联都写入 run/session 链，不用单一 `codeAgentSessionId` 覆盖历史。

审计至少覆盖：CAS 准入、worktree 创建、会话创建/恢复、每次用户回复、计划审批/修改/拒绝、
取消、关闭、同步失败、强制解绑、合并、PR、清理、路径变更和协议违规。

## 6. Profile、依赖与并发

### 6.1 writeScope

`writeScope` 为仓库相对 glob 列表，启动时规范化为确定性字符串：

- 统一分隔符、排序、去重与排除项。
- 任一方声明 `**` 视为全仓独占。
- lockfile、生成文件和共享配置的策略必须显式声明。
- 无法精确表达的跨目录重构必须使用 `**`。
- mutable run 未声明 `writeScope` 时拒绝启动。

并发键为 `repository + baseBranch + writeScope`。第 3 期新增并发槽表，以唯一索引和同事务
CAS 领取槽位；重叠范围串行，非重叠范围才可并行。

### 6.2 角色

| Profile | `mutable` | 默认执行方式 |
| --- | --- | --- |
| planner | 否 | 只生成计划、验收和 `writeScope`。 |
| implementer | 是 | 独立 worktree；可要求 Taskfold 计划审批。 |
| tester | 否 | 独立只读快照或只读 diff。 |
| reviewer | 否 | 独立只读快照或只读 diff。 |
| integrator | 否 | 汇总风险与 Git 建议，不能自动合并。 |

父子 Card 的依赖满足语义必须显式定案：建议“父 Card 到 `review` 或 `done` 可满足下游的
执行依赖”，但人工最终验收仍只在 `done`。不得让现有“父必须 `done`”门禁阻塞
planner → implementer → tester → reviewer 链。

### 6.3 预算

成本账本按 Card、父 Card、项目和全局四级累计。ACP/harness 未提供成本时标记“口径不完整”，
不得按零计算。预算耗尽时停止新 run 与新 turn，但不杀掉正在运行的 turn；Card 进入
`waitingForHuman`。

## 7. 恢复、reconciliation 与失败处理

### 7.1 启动前校验

| # | 校验项 |
| --- | --- |
| 1 | `@openclaw/acpx` 已安装、启用，且 ACP backend `doctor()` 成功。 |
| 2 | 当前 OpenClaw 与 ACP runtime 版本在 Taskfold 支持范围内。 |
| 3 | harness id 在 OpenClaw 和 Taskfold Profile allowlist 中允许。 |
| 4 | 对应 CLI 在 Gateway host 的 `PATH` 中可执行，供应商登录有效。 |
| 5 | 目标目录是授权 Git 仓库，且不包含 Taskfold 数据或凭据目录。 |
| 6 | HEAD、分支、dirty、submodule 和实际 `baseCommit` 已持久化。 |
| 7 | worktree 配额、并发槽、预算、依赖和 `writeScope` 合法。 |
| 8 | Profile 的 workspace、网络和权限配置满足当前 run，且非交互权限语义已实测。 |
| 9 | Card 的 `executionPath` 为 `openclaw-acp`，且旧入口拒绝分支已生效。 |
| 10 | OpenCode 仅在实验性开关与其专属 smoke test 均通过时允许启动。 |

任一校验失败必须拒绝启动，且不得创建 worktree 或 ACP session。

### 7.2 同步与判活

Taskfold 的控制回路不能依赖旧 worker heartbeat：

1. `lastSyncedAt + externalStatus + active turn` 是 ACP 路径的存活证据。
2. turn event 触发即时投影；`getStatus(handle)` 是固定周期轮询兜底。UI 刷新不得触发 LLM。
3. `waitingForHuman` 时禁用 abandoned 判定；等人工不是失联。
4. 连续 N 次 status 查询失败后写 `external_state_unknown`，采用指数退避；成功后自动恢复。
5. `lifecycle.ts`、`reconciler.ts`、`store.dispatch` 必须按 `executionPath` 分支，且旧
   worktree cleanup 永远不得删除 Taskfold ACP worktree lease。
6. Gateway 或 Taskfold 重启后，从 `taskfold_runs` 的 handle 字段恢复，调用 `getStatus` 对账；
   对账前禁止重新 `ensureSession`。

### 7.3 失败出口

| 失败 | 处理 |
| --- | --- |
| runtime/harness 不可用 | 拒绝启动或 `blocked`，保存 doctor 与错误摘要。 |
| `startTurn` 返回失败 | 记录 terminal result；若 session 仍可查询，允许用户续接或关闭。 |
| 取消失败 | 显示“取消未确认”，继续轮询；不得伪称已终止。 |
| `external_state_unknown` | 禁止批准、合并、PR；允许刷新、取消和强制解绑。 |
| 强制解绑 | 留存外部引用与审计，释放 Taskfold 调度关系；不自动删除磁盘 worktree。 |
| worktree/Git 清理失败 | 保持 `review` 或 `blocked` + 需处理，列出路径和人工处理命令。 |

## 8. UI 与公开接口

所有动作均通过 Taskfold Gateway 方法进入同一服务层；浏览器不得直接调用
`sessions.steer`、`chat.abort` 或任意 ACP runtime。

| UI 动作 | Gateway 方法 | 二次确认 |
| --- | --- | --- |
| 同步 | `taskfold.acp.sync` | 否 |
| 回复/追问 | `taskfold.acp.steer` | 否 |
| 批准计划 | `taskfold.acp.approvePlan` | 是 |
| 要求修改 / 拒绝计划 | `taskfold.acp.requestChanges` / `rejectPlan` | 拒绝需确认 |
| 终止 turn / 关闭会话 | `taskfold.acp.cancel` / `close` | 是 |
| 退回修改 | `taskfold.acp.sendBack` | 是 |
| 查看 worktree | `taskfold.runs.worktreeStatus` | 否 |
| 合并 / PR / 丢弃 | `taskfold.runs.merge` / `createPr` / `discardWorktree` | 是 |
| 强制解绑 | `taskfold.acp.unbind` | 是 |

项目级 Runs 视图至少展示：Card、Profile/harness、session、worktree、需处理原因、最后同步、
成本与状态。需处理计数必须在项目页可见，不依赖进入 Card 详情。

## 9. 分期与验收

### 第 0 期：官方 ACP Spike

不写产品功能，只留下可复现证据：

1. 安装并启用 `@openclaw/acpx`，`doctor()` 成功。
2. 在临时 Git worktree 中对 Claude 依次验证 `ensureSession`、`startTurn` 的 event/result、
   `getStatus`、`cancel`、`close` 和重启后的恢复。
3. 验证 Taskfold 插件可以直接导入公开 ACP SDK；不调用 LLM、第三方 Bridge 或私有状态文件。
4. 验证 `cwd`、权限 profile、项目 MCP 与项目 skills 的实际加载顺序。
5. 记录真实 handle、event payload、版本、命令和失败语义到 `VERIFICATION.md`，并固化为
   host contract test。

Gate：Claude ACP 会话能从 Taskfold 的直接 runtime 调用启动、产生结构化 event、被取消和关闭；
重启后能按持久化 handle 对账。任一项失败，暂停产品实现并评估官方 CLI backend 或裸 CLI
adapter，不能偷偷回到第三方插件。

### 第 1 期：单 Card 最小闭环

范围：`implementer` + Claude、单 repo 单 mutable run、无并行、无多角色。

- `executionPath` 与六处旧路径拒绝分支。
- revision CAS、worktree lease、官方 ACP Runner、run/audit 表、脱敏 pipeline。
- 启动、计划审批、steer、取消、同步、`review` 投影与重启恢复。
- `waitingForHuman` 控制回路改造。

Gate：计划 → 人工批准 → 执行 → `review`；等待人工 2 小时不被判死；双击只产生一个
session；旧 dispatch 不产生 claim、旧 worktree 或 subagent run；每个人工动作均有审计 actor。

### 第 2 期：人工出口与 Git 安全

- 合并、PR、丢弃、退回修改与强制解绑。
- dirty/base/submodule 校验、worktree 配额、三方盘点和清理失败状态。
- `external_state_unknown` 完整恢复闭环。

Gate：主仓 dirty 拒绝启动；Git 冲突不产生未登记 agent run；三方盘点能列出孤儿；
unknown 能自动恢复或人工解绑后重新启动。

### 第 3 期：并发与 writeScope

- writeScope 规范、并发槽表、项目/仓库上限、预算四级汇总。

Gate：不重叠范围可并行、重叠范围串行、槽位能在正常结束和失联回收时释放。

### 第 4 期：多角色 Profile 与父子调度

- Profile 表与版本、依赖语义、父子汇总、tester/reviewer 快照、评论和审计视图。

Gate：parent 在 `review` 时下游可启动；测试副产物不被误判；必需子 Card 的阻塞能正确汇总。

### 第 5 期：多 harness

- Codex：单独通过同等 Spike 后开放。
- OpenCode：只在实验性开关下开放，失败与能力限制明确显示。

全期通用 Gate：既有 Taskfold tool、CLI、slash command、Gateway 方法和自动化测试全部回归；
每个实机验证记录 OpenClaw、`@openclaw/acpx`、harness 和 Taskfold 版本。
