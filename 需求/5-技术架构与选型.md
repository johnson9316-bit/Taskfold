# 技术架构与选型

> **2026-07-28 架构前提修正：taskfold 是 OpenClaw 插件。** M1 完整复制官方 Workboard 功能层，并以其代码结构、插件 API 和开发规范为准。本文残留的“独立应用”“`taskfold serve`”与独立 adapter 方案均为历史背景，不是当前实施要求。
>
> ⚠️ **决策变更（2026-09-24）**：「taskfold 是 OpenClaw 插件」这一架构前提已被 [[18-多宿主架构]] 推翻——Taskfold 改为多宿主工具，OpenClaw 降为其中一个适配层，Gateway 不再是必需组件。但本文历史背景部分提到的旧版「独立应用 / `taskfold serve` HTTP 服务」方案**仍未被采纳**：18 明确否掉常驻守护进程做唯一写入者，新方案是 `@taskfold/core` 纯 Node 库在每个宿主进程内加载，不是重启旧的独立服务路线。原表述保留作历史记录。

### 后端语言：已定 TypeScript + Node

**旧结论（v0.1–v0.7）：Python，因为「Hermes 插件的后端入口就是 `plugin_api.py`，宿主强制」。**

**这个理由随 Hermes 退场一起消失了。** 原文写的是「只要还要做插件形态，后端必须是 Python」——现在唯一的插件形态是 OpenClaw，而 **OpenClaw 只支持 JS/TS**。整条论证链断了，结论必须重算。

#### 重算：七条论据，六条指向 TypeScript

| # | 论据 | 指向 |
|---|------|------|
| 1 | **唯一宿主 OpenClaw 只认 JS/TS** —— 插件入口是 `definePluginEntry`，`openclaw/plugin-sdk/*` subpath 导入。Python 只能当 sidecar 子进程 | **TS** |
| 2 | **分发是 npm 包** —— npm 包里塞 Python 依赖是分发地狱：用户得自己有 python3 + 正确版本 + 装依赖。TS 就是 `npm i` | **TS** |
| 3 | **OpenClaw 公共 ACP Runtime 是 TS 插件 API**（[[8.7-待开发一波]]）—— 执行调度层需直接调用 ACP backend，Python 侧不具备同等插件集成面 | **TS** |
| 4 | **gsd-core 本身是 TypeScript** —— 转 TS 后 `vendor/gsd-core/` 可**原生 import**，`gsd-tools.cjs` 直接 `require`，subprocess 层整个消失（[[5-技术架构与选型]] 简化） | **TS** |
| 5 | **前端必须是 TS** —— Hermes SDK 白拿 React 的路没了，前端要自己写（[[5-技术架构与选型]]）。同语言意味着 domain 类型定义**前后端共享一份**，不用维护两套 schema | **TS** |
| 6 | **将来 VS Code 扩展 in-process** —— [[6-OpenClaw集成]] 原本要为 VS Code 写 Python sidecar，转 TS 后这个成本归零 | **TS** |
| 7 | 现有 Python 代码资产 | Python，但**只有约 400 行**（`db.py` 318 + `config.py` 80 + `md_store`），且是最机械的 CRUD。重写是几小时的事，不是沉没成本 |

> ⚠️ **决策变更（2026-09-24）**：第 1 条论据「唯一宿主 OpenClaw 只认 JS/TS」的前提已被 [[18-多宿主架构]] 推翻——OpenClaw 不再是唯一宿主，还有 VS Code、以后的 dsh、pi。但结论不变：18 仍选 TypeScript + Node 作为 `@taskfold/core` 的实现语言（第六条论据「将来 VS Code 扩展 in-process」已预见此方向）。原表述保留作历史记录。

#### 已关闭的 Python + sidecar 路线（保留作决策记录）

| 代价 | 严重度 |
|----------------------|-------|
| OpenClaw 插件仍必须有个 TS 壳（进程管理 + iframe + 路由代理） | 中——躲不掉，只是薄 |
| npm 包分发要求用户自备 Python 环境 | **高——这是采纳率杀手** |
| 不能直接使用 OpenClaw 公共 ACP Runtime，执行调度层就得自行承担会话协议、事件归集、取消/关闭与 harness 兼容 | **高——白扔掉 [[8.7-待开发一波]] 的 ACP 能力** |
| gsd-core 仍走 subprocess，跨语言传状态 | 中 |
| 前后端两套类型定义 | 中 |

> **2026-07-28 已确认：采用 TypeScript + Node。** 这个决策已关闭 Python + sidecar 路线；现有 Python 代码仅保留设计参考。它决定 gsd-core 集成、执行调度复用和未来 VS Code 适配三处的写法。

#### 已定后的具体选型

| 项 | 选择 | 理由 |
|----|------|------|
| 语言 / 运行时 | **TypeScript + Node**（版本下限跟随 OpenClaw 要求，**待确认**） | 宿主决定 |
| 路由 / 服务 | **沿用 Workboard 的 OpenClaw 插件路由与服务模式** | M1 不另建独立 HTTP 服务 |
| 数据库 | **SQLite**，驱动 `better-sqlite3`（含 FTS5、同步 API）或 Node 内建 `node:sqlite` | 前者稳妥且 FTS5 确定可用；后者零依赖但要看 Node 版本下限 |
| ORM | **不用 ORM**，手写 SQL（结论不变） | 表少、查询简单 |
| 全文检索 | **SQLite FTS5**（结论不变，仍封在 `search.ts` 后，[[5-技术架构与选型]]） | 内建 |
| 校验 | **Zod** | 前后端共享 schema，同时给出 TS 类型与运行时校验 |
| 配置 | YAML + JSON（结论不变） | |
| gsd-core | **原生 import**，不再 subprocess（[[5-技术架构与选型]] 改写） | 同语言的最大红利 |
| 打包 | **沿用 Workboard 插件的构建与打包方式** | 产物用于 OpenClaw 插件安装，不额外产出独立服务 |
| 第三方依赖 | **尽量少** —— native 模块尤其克制（`better-sqlite3` 需 prebuilt；若 OpenClaw 环境编译不过就退 `node:sqlite`） | in-process 跑在 Gateway 里，装不上就整个插件废掉 |

> **M1 不重开架构。** 先按 Workboard 原有目录、模块边界和插件规范完成完整复制与安装；GSD 数据和执行调度相关设计从 M2 再按需要增量加入。

### 前端：2026-07-28 改为复制 OpenClaw Workboard 功能层

此前的 M1 方案是 Vite + React + dnd-kit 自写看板。经源码、许可证和依赖边界验证后，该方案关闭：**采用 OpenClaw 官方 Workboard 的完整功能层作为 taskfold 的起点，在其上改造。**

Workboard 不是一个孤立的页面；它由三层组成：

1. `extensions/workboard/`：SQLite 存储、卡片/看板/评论/关联/诊断/调度/CLI 与 Gateway 方法。
2. `packages/workboard-contract/`：状态、卡片、执行与事件的共享 TypeScript 契约。
3. `ui/src/pages/workboard/`、`ui/src/lib/workboard/`、`ui/src/styles/workboard.css` 及其直接 UI 依赖：Lit 页面、状态机、筛选、详情与实时刷新。

**已定落法**：

- 复制上述完整功能层到 taskfold，保留 OpenClaw 的 MIT 版权与许可文本；记录上游 commit、同步日期和本地 patch。
- **保留 Lit + Vite + TypeScript**。把 UI 转写成 React 会损失复用价值，M1 不做 React、shadcn、Tailwind 或 dnd-kit 重写。
- 仅复制 Workboard 功能层，**不复制整个 OpenClaw 控制台**。保留 Workboard 对 OpenClaw 插件 API、Gateway、会话和权限模型的既有使用方式；M1 不以 adapter 替换它们。
- Workboard 的通用卡片/执行模型是 M1 的可运行基础；M2 再通过 GSD 映射层接入 `.planning/`，不得以 Workboard SQLite 覆盖 GSD 文件真相。

选型（M1 落地）：

| 项 | 选择 | 理由 |
|----|------|------|
| 构建 | **沿用 Workboard 既有构建** | 生成供 OpenClaw 插件加载的前端产物 |
| 框架 | **Lit + TypeScript** | Workboard 原生实现；不做无收益的框架迁移 |
| 看板功能 | **完整复制 Workboard 功能层** | 卡片、看板、筛选、详情、评论、关联、状态、SQLite、实时刷新与诊断均保留；产品改造从 M2 开始 |
| 实时 | **沿用 Workboard live-refresh 语义** | M1 不另建 SSE、轮询或 WebSocket 替代层 |
| 路由 / 宿主 | **OpenClaw 插件 API** | 不复制聊天、会话、Agent 管理等 OpenClaw 控制台功能 |

> **关键约束**：这是“复制并持续改造一个 MIT 功能子树”，不是把 `@openclaw/workboard` 作为黑盒依赖，也不是 fork 整个 OpenClaw。taskfold 的核心、数据真相和执行安全边界仍由本项目定义。

> **关键约束不变：产物必须自包含，不能有运行时 CDN 依赖。** OpenClaw 的 sandboxed frame 有 CSP，外链大概率被拦（[[6-OpenClaw集成]] 待实测）。

**依赖红线**（违反需重新决策）：不引 Postgres / Redis / 消息队列 / Elasticsearch。taskfold 必须能在一台笔记本上零配置跑起来。

> ⚠️ v0.8 对「独立后台进程」这条红线开一个**例外**：执行调度层（[[4-执行调度与AI]]）本质上要管理长驻子进程（会话）。这不违反红线的精神——它不是「为了跑 taskfold 而必须常驻的基础设施」，而是**业务本体**。区别在于：没有它 taskfold 就没有功能；而 Redis 只是为了让别的东西快一点。

**⚠️ 2026-07-28 三次修正**：v0.6 的 Hermes Kanban 复制路线已随 Hermes 退场作废；但随后确认 OpenClaw 官方仓库包含 MIT 许可的完整 Workboard 功能层。因此“看板 UI 没有可抄的同构对象、必须自写”的 v0.8 结论也作废，改为完整复制 Workboard 并保留其插件宿主依赖。

v0.6 的推理仍然有效：上表项目全是**独立应用**，跨架构抠组件是伪快路。当前 taskfold 是 OpenClaw 插件，M1 的代码来源只采用同宿主、同插件模型的 Workboard。

这意味着上表项目的**架构冲突消失了一半**：不再有 IIFE 注入的形态障碍，剩下的障碍只是它们各自的技术栈（Redux-Saga / Sails / PHP / Go）与重型依赖。

但结论仍然是不 fork，理由从「架构冲突」换成下面三条（见本节末）。**唯一变化是 Planka 从「只看效果」升级为「可读代码的候选」**——它是 MIT + React，形态上首次与 taskfold 对齐。

v0.8 分工：

| 用途 | 抄谁 | 说明 |
|------|------|------|
| **看板 UI / 卡片 / 状态 / SQLite / 刷新** | **OpenClaw Workboard 完整功能层** | 已定完整复制；保持 Lit 与既有 Gateway/app context 使用方式 |
| 看板交互与组件划分**参考** | **Planka**（MIT + React，可读代码） | 仅作补充参考，不作为代码基线 |
| 流程引擎与自动化动作**设计** | Kanboard | **读设计，不抄代码**（PHP + jQuery） |
| 交互手感参考 | Linear | 看效果 |
| 数据模型参考 | Plane | **只读文档**（AGPL，[[5-技术架构与选型]]） |
| **执行调度 / CLI 会话管理** | **不抄——用 OpenClaw 生态**（[[4-执行调度与AI]]） | 这是 v0.8 最大的「不用自己写」 |

**结论：仍然不 fork 整个应用。** 理由（v0.8 重述，架构冲突不再是主因）：

1. **省错了地方** —— fork 省下的是那 80% 的表单 CRUD，而这**恰恰不是差异化，反而是包袱**；taskfold 的价值在 **GSD 流程层 + 执行调度层**（[[4-执行调度与AI]]），fork 在这两块**完全帮不上忙**，还得先花时间拆掉它原有的实体模型。GSD 的 phase / plan / wave 塞不进 Planka 的 board/list/card 三层。
2. **重型依赖** —— Plane 要 Postgres + Redis + 两个微服务；Planka 要 Postgres。违反 [[5-技术架构与选型]] 依赖红线。
3. **License** —— Plane 是 AGPL-3.0。即便本项目全开源，混入其代码也会强制整个项目转 AGPL（[[5-技术架构与选型]]）。

**该抄什么**：

- **代码**：**OpenClaw Workboard 完整功能层**（MIT，2026-07-28 已定为 M1 基线）；Planka（MIT + React）只保留为交互参考
- **现成能力**：**OpenClaw 公共 ACP Runtime + `@openclaw/acpx`**（[[8.7-待开发一波]]）—— 这是 v0.8 真正的「白拿」，且比抄任何看板代码值钱
- **模型**：Plane 的实体划分（Projects / Cycles / Modules / Issues）——**只读文档**
- **设计**：Kanboard 的自动化动作模型、Linear 的键盘优先交互、Focalboard 的多视图切换

### 已停止的独立软件预留（历史记录）

原则：**现在花小钱，避免以后花大钱**。以下每条的「现在成本」多在小时量级，「以后补」多在周量级。

| # | 预留项 | 现在怎么做 | 不做的话以后要付什么 |
|---|--------|-----------|-------------------|
| 1 | **双对外契约：HTTP + MCP** | core 暴露 `createApp()`（HTTP，v0.7 前写作 `get_router()`）与一个 MCP server。**localhost HTTP 是主契约** | 每个新宿主都要重做一遍集成；agent 工具层 O(n) 重复 |
| 2 | ~~前端双产物~~ **单一静态站** | ⚠️ **v0.8 简化**：Hermes 退场后 IIFE 产物取消，Vite 只出 `web/dist` 一份，OpenClaw 与独立形态共用（[[5-技术架构与选型]]、[[6-OpenClaw集成]]） | 独立版前端从零搭 |
| 3 | **清除宿主概念** | core 不得出现 `HERMES_HOME` 或 OpenClaw 路径；改用 `TASKFOLD_HOME`，宿主路径由 adapter 注入 | 全局替换 + 配置迁移 |
| 4 | **执行者标识** | `events` / `comments` 使用 `actor_type + actor_id`，区分本机所有者、agent 与系统 | 人机操作混在一起，审计与度量失真 |
| 5 | **本地访问边界** | 旧独立形态方案只监听 loopback；OpenClaw adapter 仅传递宿主上下文，不同步用户体系 | 本机控制端口可能被意外暴露；未来再加访问控制会散落各处 |
| 6 | **DB 可移植** | SQL 保持 ANSI 风格，不用 SQLite 特有语法；连接层留 `Database` 抽象 | Postgres 迁移＝全量重写查询 |
| 7 | **全文检索隔离** | FTS5 **是 SQLite 独有的**，必须封在 `search` 模块接口后 | 换库时检索功能整体报废 |
| 8 | **正文存储抽象** | `BodyStore` 接口，默认 `MarkdownBodyStore`；将来可换 DB 存储 + MD 导出 | MD 路径硬编码渗入 service |
| 9 | **★ ACP Runner**（v0.8 权重大升） | **v0.8 起它是执行调度层的核心接口**：`ensureSession / startTurn / observe / cancel / close`，背后默认是 OpenClaw ACP Runtime + `@openclaw/acpx`；官方 CLI backend 或裸 CLI 仅为经 Spike 批准的 fallback（[[8.7-待开发一波]]） | core 与宿主 agent API 焊死；**换执行后端等于重写调度层** |
| 10 | **配置来源抽象** | 配置读写走 `ConfigStore`，不直接读宿主目录 | 独立版无配置落点 |

> 本节不再是 M1 要求。M1 以复制的 Workboard 代码和规范为准；其中的抽象仅在 M2 确有 GSD 扩展需求时重新评估。
>
> `ACP Runner`、GSD 映射和执行调度均不再是 M1 要求；M4 开工前以复制的 Workboard 代码为基础完成 ACP Spike。

**已取消的独立形态最小交付**（历史记录，不是 M1 验收）：

```bash
taskfold serve --port 8080        # 已取消：不依赖任何宿主
# 浏览器打开 http://127.0.0.1:8080 → 旧方案，不再实施
```

### License 与推广（v0.6 定案：**全开源，暂不商业收费**）

**决策：`LICENSE` 保持现有 MIT 不变。** 与 gsd-core（MIT）一致，生态最顺，双向取用无障碍。

v0.4 曾建议 Apache-2.0 + DCO，目的是保留商业化选项；既已确定暂不收费，那层复杂度不必背。

> 事实澄清：**MIT 不妨碍你以后卖自己的代码**。放弃的是排他性（别人也能拿去卖），不是收费权。

| 项 | 结论 |
|----|------|
| **开源协议** | **MIT**（保持不变） |
| 贡献者协议 | 可选。若在意日后改协议的权利，加 DCO（`Signed-off-by`）即可，门槛低 |
| **gsd-core 代码** | ✅ MIT，**可自由取用**，义务仅为保留版权声明（放 `THIRD-PARTY-NOTICES`） |
| **Plane / Wekan 代码** | ❌ AGPL-3.0，**一行不抄，只读文档**（[[5-技术架构与选型]]）。即便自己全开源，混入 AGPL 也会强制整个项目转 AGPL |
| 其他参考项目 | 取用代码前先查协议（[[5-技术架构与选型]] 表） |
| 商标 / 域名 | 建议尽早占位：GitHub org、PyPI、npm、域名 |

**推广（「打广告」）—— 可以，License 管代码分发条款，不管宣传。** 三条实际注意事项：

1. **署名义务** —— 取用 gsd-core 代码须保留其版权声明与 MIT 许可文本。
2. **不得暗示官方背书** —— MIT **不授予商标权**。可以说「GSD 流程的看板」「为 GSD 打造」「兼容 GSD」；**不要**做成看起来像 open-gsd 官方产品（勿用其 logo / 命名风格 / 自称 official）。
3. **最有效的推广是上游联动** —— gsd-core 有 CONTRIBUTING.md 与社区 Discord。开 issue 申请进生态列表 / 提 PR，比自行吆喝有效得多，也顺带把「非官方但被认可」的关系说清楚。

### 参考代码的合法边界（v0.5 新增）

**常见误解：「本项目也是开源的，抄过来没问题」——错。开源 ≠ 协议兼容。**

AGPL-3.0 是 copyleft（传染性），且方向单向：

- Apache-2.0 / MIT 代码 → 可以进 AGPL 项目 ✅
- **AGPL 代码 → 不能进 MIT / Apache 项目** ❌

复制 Plane 代码进 taskfold 的后果不是「没事」，而是**整个 taskfold 必须转为 AGPL-3.0**；随后网络条款生效——任何人将其作为网络服务提供都须公开整个作品源码。**[[5-技术架构与选型]] 的商业版路线当场归零。**

**「看完自己重写」也不安全。** 行业认可的 clean room 要求：两组人、其中一组从未接触过源码、全部通信可审计。个人边看边写达不到该标准；在有充分接触史的前提下，「完全重写」不是有效抗辩。

风险分级（工程实践口径，非法律意见）：

| 做法 | 风险 | 是否可行 |
|------|------|---------|
| 读文档 / API 文档 / 数据模型说明 | 无 | ✅ |
| 读代码理解思路，隔期后以不同架构自行实现 | 低 | ⚠️ 可接受 |
| 对照代码逐段改写 | 高——构成派生作品 | ❌ |
| 复制粘贴 | 明确违规 | ❌ |

**操作规程**：

1. 需要抄代码时，**只从 MIT / Apache / BSD 项目抄**（[[5-技术架构与选型]] 已标注），并保留原版权声明与 NOTICE。
2. AGPL 项目（Plane / Wekan）**只读文档**。若确已阅读其某模块代码，近期不要动 taskfold 的同一模块。
3. 引入任何第三方片段时，在提交信息中注明来源与协议，便于日后审计。
4. **AI 生成代码同理**——若提示词中粘贴了 AGPL 代码，产出同样受污染。

### gsd-core 内化方式（v0.6 定案：**vendor，不是外部依赖**）

**决策：把 gsd-core 的逻辑收进本仓库，taskfold 独占状态写权。**

MIT 允许自由取用，因此不必把 gsd-core 当外部安装依赖。内化之后 taskfold 是唯一写入者，**不存在与外部进程争抢 lockfile 的问题**。

**两种内化路径**：

| 路径 | 做法 | 成本 | 结论 |
|------|------|------|------|
| **B1 vendor TS 原样** | 复制到 `vendor/gsd-core/`，锁版本 | 低——复制即可，无需重写 | ✅ **采纳** |
| B2 移植为其他语言 | 重写阶段循环与编排 | 高——跨语言是重写不是复制；且从此 GSD 正确性由自己负责 | ❌ 不做 |

**⚠️ v0.8：若采纳 [[5-技术架构与选型]] 的 TypeScript 决策，B1 大幅简化。**

| | Python core（v0.6 设想） | TS core（v0.8 建议） |
|---|---|---|
| 调用方式 | **subprocess** 起 `gsd-tools.cjs`，解析 stdout | **原生 import / require** |
| 状态传递 | 进程边界序列化，退出码语义要摸清 | 直接函数调用与返回值 |
| 错误处理 | 靠退出码 + stderr 猜 | 真异常，带栈 |
| 类型 | 无（跨进程） | **共享 TS 类型** |
| 调试 | 难 | 正常断点 |

⇒ **同语言把「集成」降级成「引用」。** 这是 [[5-技术架构与选型]] 转 TS 的第 4 条论据，也是最省力的一条。

**⚠️ 一个必须先验证的关键假设（v0.8 提出）**：

> 本文档一直假定 gsd-core 是一个「可调用的库 / CLI」。但从其自述（「no database, no server, no external dependencies」、状态全在 `.planning/` 的 MD 里、五阶段靠 fresh-context 子 agent 推进）看，**它更可能主要是一套给 Claude Code 用的 slash commands + agent 定义 + 提示词模板，外加一个 `gsd-tools.cjs` 状态工具**。

若如此，「内化」的真实含义要改写：

| 组成 | 内化方式 |
|------|---------|
| `gsd-tools.cjs`（状态读写、lockfile） | ✅ 真的是库，直接 import（TS 下零成本） |
| `.claude/commands/gsd-*.md`（slash commands） | **不是代码，是提示词** —— taskfold 要做的是把它们**安装到目标项目**，然后驱动 Claude CLI 执行（[[4-执行调度与AI]]） |
| agent 定义（researcher / planner / plan-checker / executor / verifier） | 同上，是 subagent 定义文件 |
| 阶段循环编排逻辑 | **它跑在 Claude 的会话里，不在 gsd-core 的进程里** |

**如果这个判断成立，那么 [[4-执行调度与AI]] 的执行调度层不是「GSD 内化」的补充，而恰恰是「GSD 内化」的唯一实现方式**——因为 GSD 循环本身就是由 agent 会话跑的，你不驱动会话就没有循环。这会让 [[3-需求与工作管理]] 里「⑥ 与 M2 同期」的判断进一步加强为「⑥ 就是 M2」。

> **这是 M2 之前必须读源码确认的第一件事**（[[5-技术架构与选型]] 待落实清单第 0 项）。判断错了会导致整个 M2 的设计方向错。

**vendor 的真实代价与对策**：

| 代价 | 对策 |
|------|------|
| 上游修复 / 改进不会自动流入 | 保持 vendored 副本为**干净子树**；在 `vendor/gsd-core/UPSTREAM` 记录上游 commit SHA 与同步日期，便于日后 diff / rebase |
| 本地改动与上游冲突 | 本地修改集中在薄适配层，尽量不改 vendored 文件本体；必须改时单独记录 patch |
| 署名义务（MIT） | 保留其 `LICENSE`；根目录加 `THIRD-PARTY-NOTICES`（[[5-技术架构与选型]]） |

**语言结论（⚠️ v0.8 已变）**：

> v0.6 曾写「B1 下 GSD 逻辑以 TS 运行、Python 侧 subprocess 驱动，**Python core 的结论不变**」。
> 那个结论的前提是「Hermes 强制 Python」。前提已消失（[[5-技术架构与选型]]），**gsd-core 是 TS 现在反过来成了转 TS 的论据之一**。

**待落实的技术细节**（M2 前需验证，第 0 项最关键）：

0. ⚠️ **gsd-core 到底是「库」还是「提示词包」**（见上文关键假设）—— 决定 M2 的整体设计方向
1. `gsd-tools.cjs` 的完整命令与退出码语义 —— 查 `docs/COMMANDS.md`
2. `config.json` 的 schema —— 查 `docs/CONFIGURATION.md`
3. `STATE.md` / `CONTEXT.md` 的确切字段（README 与 ARCHITECTURE 未给出完整 schema，**须读源码确认**）
4. 多个 `.planning/` 的发现机制：taskfold 如何知道要聚合哪些 repo（建议配置一个 workspace 根目录列表）
5. `.planning/` 被外部修改（用户直接跑了 GSD 命令）后的变更检测 —— 文件 mtime 轮询或 watch。**即便内化，仍要假设文件会被外部改动**：用户可能同时装着官方 gsd-core
6. **（v0.8 新增）** gsd-core 的 slash commands / agent 定义如何安装进目标项目，是否与用户自己的 `.claude/` 配置冲突
7. **（v0.8 新增）** gsd-core 的归档逻辑是否会清理 phase 目录下的未知子目录（决定 [[4-执行调度与AI]] 的 `runs/` 能否放在 `.planning/` 里）
