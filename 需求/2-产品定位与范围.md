# 产品定位与范围

> 跨主题请从 [[README]] 进入；发现矛盾时以 [[1-规划评审]] 为准。

**taskfold** —— **面向个人开发者的 OpenClaw 看板插件；M2 先完成通用项目看板，M4 起扩展为 GSD 工作控制台与执行调度层**。

> ⚠️ **决策变更（2026-09-24）**：「唯一形态是 OpenClaw 插件」已被 [[18-多宿主架构]] 推翻——Taskfold 改为多宿主工具（OpenClaw、VS Code，以后还有 dsh、pi），OpenClaw 降为适配层之一，Gateway 不再是必需组件。原表述保留作历史记录。

> **核心逻辑是 GSD 流程，看板只是载体。**
> 上游：[open-gsd/gsd-core](https://github.com/open-gsd/gsd-core)（MIT，TypeScript）—— GSD = **Git. Ship. Done.**，一套 spec-driven 的五阶段开发框架。

一句话差异化：

> gsd-core 明确声明「**No database, no server, no external dependencies**」，状态全在 `.planning/` 的 MD + JSON 里，**且完全没有 UI**。
> **taskfold 填的正是它主动不做的那一块。**

### taskfold 的价值边界

| gsd-core 已有 | gsd-core 没有 = **taskfold 的价值** |
|--------------|--------------------------------|
| 五阶段循环、编排、meta-prompting、fresh-context 子 agent | **可视化** —— 一个 UI 都没有 |
| `.planning/` 文件状态、lockfile 原子写 | **跨项目聚合** —— 每 repo 一份 `.planning/`，10 个 repo 就是 10 份孤岛 |
| `STATE.md` 里的 metrics 字段 | **度量图表** —— 无历史、无 CFD、无燃尽 |
| 单人 + agent 的工作流 | **个人工作全景** —— 跨项目汇总、当前待办、阶段 / 阻塞与 agent run 的可视化 |
| `REQUIREMENTS.md` 平铺文档 | **需求池 / 优先级排序 / 缺陷跟踪 / 个人当前重点** |
| 阶段循环由人在终端里逐步喊命令推进 | **执行调度**（v0.8 新增）—— 多会话排队、可观察、可接管、可复盘；每日巡检（[[4-执行调度与AI]]） |

> 这个差异化比「local-first + AI」硬得多，并且**彻底回答了「为什么不用 Plane」**：Plane 根本不认识 GSD 的阶段与产物。

五条设计主线：

1. **GSD 流程为骨架** —— 内建工作流就是 GSD 的阶段循环，不是通用 kanban 套一层壳（[[3-需求与工作管理]]、[[3-需求与工作管理]]）。
2. **本地优先（local-first）** —— 数据落在本机 `.planning/`，无云依赖，Git 可版本化。
3. **AI 一等公民** —— 需求拆解、优先级建议、验收标准生成、进展播报，内建而非外挂。
4. **★ 调度而非执行**（v0.8 新增）—— taskfold **自己不写代码**，只把开发执行变成可排队 / 可观察 / 可验证 / 可接管的异步流程；真实执行者是经 OpenClaw 公共 ACP Runtime 与 `@openclaw/acpx` 启动的 Claude Code、Codex、OpenCode 等专业 harness（[[8.7-待开发一波]]）。
5. **OpenClaw 插件** —— taskfold 在 OpenClaw 内运行和分发；M1 完整复制 Workboard，M2 在同一插件中补齐多项目、项目设置和项目资料，M4 再叠加 GSD 流程与执行调度（[[6-OpenClaw集成]]）。

### 形态与分发路线（2026-07-28 修正：**OpenClaw 插件**）

**taskfold 的当前形态与可预见终局都是 OpenClaw 插件。** 它不提供独立 Web 应用或独立服务；所有 UI、数据和后续执行能力均通过 OpenClaw 插件生命周期运行。

```
OpenClaw
  └── taskfold 插件
        ├── M1：复制的 Workboard 完整功能层
        ├── M2：多项目、项目设置与项目资料
        └── M4+：GSD 投影、执行调度、流程、AI 与度量
```

M1 用 OpenClaw 标准插件安装方式分发：本机开发可链接本地目录，其他用户可从 Git 仓库安装。完整命令和验收见 [[6-OpenClaw集成]]。

> Hermes 相关实现已退场。M1 不另行设计看板前端或独立服务，而是复制并保留 OpenClaw Workboard 的既有插件模式。

> ⚠️ **决策变更（2026-09-24）**：本节「taskfold 的当前形态与可预见终局都是 OpenClaw 插件」「所有 UI、数据和后续执行能力均通过 OpenClaw 插件生命周期运行」，以及上文设计主线第 5 条「OpenClaw 插件」，均已被 [[18-多宿主架构]] 推翻。新定案：`@taskfold/core` 是纯 Node 库，在 OpenClaw、VS Code 等每个宿主进程内加载；OpenClaw 插件是其中一个适配层，不再是唯一形态或终局。原表述保留作历史记录。

### 目标用户

| 层级 | 场景 | 优先级 |
|------|------|--------|
| 个人 / 独立开发者 | 一个开发者管理个人研发、GSD 阶段与 agent 执行 | **唯一 P0**（M1-M4） |
| 小团队（2-10 人） | 共享项目、协作迭代与分工 | 暂不承诺；需先补共享部署、同步与权限模型 |
| 中型团队及以上 | 发布计划、审批、跨团队协作 | 不做 |

### 上游依赖与设计参考

**上游（唯一的真依赖）**：

- **[gsd-core](https://github.com/open-gsd/gsd-core)** —— **MIT / TypeScript**。taskfold 的流程内核与状态真相来源。集成方式见 [[5-技术架构与选型]]。
  - 协议 MIT ⇒ **代码可自由取用**，义务仅为保留版权声明（[[5-技术架构与选型]]）。
  - **v0.6 起改为 vendor 内化**（复制入 `vendor/gsd-core/`），不是外部安装依赖。
    > ⚠️ 此处原写「不 fork、不 vendor 其内部实现，写操作走其 CLI」——那是 v0.5 的口径，**v0.6 已推翻**（[[5-技术架构与选型]]），本行 v0.8 才补正。仍然成立的部分是：**尽量不改 vendored 文件本体**，改动集中在薄适配层，便于日后同步上游。

**设计参考**（借鉴模型与交互，不引入为依赖；技术栈选型调研见 [[5-技术架构与选型]]）：

- **TAPD** —— 补 GSD 空缺的部分：需求分级、缺陷跟踪、优先级排序、轻量计划。**注意主从关系：GSD 模型为主，TAPD 概念只用于填空**（[[3-需求与工作管理]]）。
- **Linear** —— 极简敏捷的操作手感：键盘优先、Cycle 自动滚动、无冗余字段。**交互体验主参考**。
- **Plane** —— 开源 Jira 替代中采用最广，其 Projects / Cycles / Modules / Issues 模型值得直接借鉴。同时是**最直接的竞品**（已有 AI 能力与原生 MCP server）。
- **Kanboard** —— 极轻量 PHP 看板，其「自动化动作（automatic actions）+ 插件系统 + WIP 限制」的设计最贴近 taskfold 的规划。
- **GitHub Projects** —— 自定义字段 + 多视图（表格 / 看板 / 路线图）的轻量模型。

### AI 工作流对标（仅思路参考，**不引入为依赖**）

| 项目 | 借鉴什么 | 明确不做什么 |
|------|---------|-------------|
| **n8n** | 「触发器 → 条件 → 动作」三段式规则模型（用于 [[4-执行调度与AI]] 的 YAML 自动化） | 不集成 n8n；不做可视化节点画布 |
| **Dify** | 提示词编排与变量注入的组织方式 | 不集成 Dify；不做 LLM 网关 |

> 说明：taskfold **不自带模型调用循环**。它在 OpenClaw 插件中复用宿主的 agent 与 Skills；这些能力不属于 M1（[[14-OpenClaw技能策略]]）。
>
> ⚠️ **v0.8 区分两种「AI 执行」，别混**：
> - **AI 辅助管理**（[[4-执行调度与AI]]：澄清、拆解、排序、播报）—— 短请求，一次问答，用宿主 agent 或最小 LLM 调用即可
> - **AI 执行开发**（[[4-执行调度与AI]]：驱动 Claude CLI 写代码）—— 长会话、多轮、要文件工具与 Git，**必须走专业开发 CLI，不是普通 LLM 调用**
>
> 这两者的运行时要求差一个量级。`ACP Runner` 主要为后者设计。

### 明确不做

写在这里是为了防止范围膨胀，后续要做需要重新决策：

- ❌ 可视化工作流编排画布
- ❌ 甘特图、资源工时管理、成本核算
- ❌ 与 TAPD 功能一对一对齐
- ❌ 多人协作、成员分工、权限、团队容量与 Sprint 管理（未来若做小团队版，须重新立项）
- ❌ 引入 Redis / 消息队列 / Elasticsearch 等重型依赖（见 [[5-技术架构与选型]] 依赖红线）
- ❌ 独立 Web 应用、`taskfold serve` 或第二套插件外运行时

> ⚠️ **决策变更（2026-09-24）**：「不做……第二套插件外运行时」已被 [[18-多宿主架构]] 部分推翻——VS Code 扩展本身就是插件之外的第二个宿主运行时（以后还有 dsh、pi）。「不做独立 Web 应用 / `taskfold serve`」仍然成立（18 第六节仍否掉常驻守护进程做唯一写入者，只保留作以后的升级路径）。原表述保留作历史记录。

**v0.8 新增四条「不自己造」**（对应「充分利用 OpenClaw 生态」）：

- ❌ **不自己写 agent 运行时 / LLM 调用循环** —— 用 Claude CLI 等现成开发 agent（[[4-执行调度与AI]]）
- ❌ **不自己写会话管理器**（PTY、流式解析、resume）—— 用 OpenClaw 公共 ACP Runtime + `@openclaw/acpx`（[[8.7-待开发一波]]）
- ❌ **不自己存会话 transcript 副本** —— 宿主已存两份，只存 `host_ref_kind + host_ref_id` 与可选可恢复会话指针（[[4-执行调度与AI]]）
- ❌ **不自己写定时器** —— 用 OpenClaw 的 cron（[[4-执行调度与AI]]）

> 这四条是有代价的：**换来的是对 OpenClaw 上游变更的依赖**（[[9-风险与取舍]] 已列）。对策是只依赖公开 ACP Runtime API、锁定兼容版本、以 `ACP Runner` 隔离调用，并保留官方 CLI backend / 裸 CLI adapter 的评估退路，而不是一开始就自己造。

**不再预留独立服务形态**：企业权限、多租户和自建账号体系均不纳入当前路线图；若未来重新考虑，必须作为新的产品形态单独决策。
