# 上游 workboard 2026.9.4 对齐清单

## 背景

Taskfold 是 OpenClaw 内置 `workboard` 扩展在 2026-07-28（upstream commit `78d6c6c`，对应 `openclaw@2026.7.1-2`）的 fork，见 `UPSTREAM.md`。此后独立演进、从不合并上游。本机 OpenClaw 已升级到 `2026.9.4`，本文档评估上游 `workboard` 在此期间的变化，判断哪些值得 Taskfold 取用。

**已定**：不合并上游代码，只挑值得要的机制照着写。Taskfold 的 `dist/index.js`（651.6K）与 42 个源文件规模已远超 stock `workboard`（`dist/index.js` 60.3K）。manifest 工具面对比显示 stock 的 35 个工具 Taskfold 全部具备，另有 8 个自有扩展，功能层面无需追赶。

**2026-09-18：9 项差异已评估并确认要做**，见下方「二、已确认要做的清单」。其中**第 9 项（Control UI 迁移到宿主原生注入）已定为下一步要做的项**，见该项内的交接说明。`openclaw plugins validate` 适配已评估后决定不做，理由见「三、评估过但不做」。

**2026-09-18：同一天排查过程中发现并已修复一个独立的生产 bug**——Control UI 在 2026.9.4 上完全无法连接（`1008 protocol mismatch`），根因和修复记在 `VERIFICATION.md`「Control UI could never connect on OpenClaw 2026.9.4」一节，不在本文档重复。这个根因是第 9 项「Control UI 迁移到宿主原生注入」的额外确证动机，已在该项下补充说明。

### 从本清单摘出的独立待办

**`store-lifecycle` 等价物（关库安全）**。清单第 7 项原文把上游的 `store-lifecycle.ts` 归进了「会话生命周期两阶段落地」，但 [[15.7-会话生命周期设计]] §10 勘误查明它与 `prepared/accepted/failed` 三段式**毫无代码关系**——它是 `api.lifecycle.registerRuntimeLifecycle` 的关库注册，插件 disable/restart 时先停 service 再 `store.close()`。

Taskfold 今天完全没有等价物：`TaskfoldStore` 没暴露 `close()`（`store.ts:307 openSqlite()` 直接丢掉了 `createTaskfoldSqliteStores()` 返回的 `close`），`sqlite-store.ts` 的 `close()` 直接 `db.close()` 不等在飞的写完。影响面是进程退出与测试 teardown；[[15.8-并发与补偿设计]] §七 风险 5 从另一个角度记了同一个缺口。

**未确证是否在实际中触发过**。若 `npm test` 出现偶发 teardown 报错，优先怀疑这里。实施要点见 15.7 §7 步骤 6（注意 SDK 差异：`dispose` 字段只存在于 2026.9.4，2026.7.1-2 只有 `cleanup`——devDep 已升到 2026.9.4，两者现在都可用）。

这是一个真实但低频的独立缺口，不属于「同步上游 kanban」的范围，故从本清单摘出单独记录，不混进第 7 项。

### 信任门：评估任何上游机制的第一道筛子

`runtime.gateway.request` 对 Taskfold **永久不可用**，这已经咬过三次，值得固化成一条筛选规则。

宿主侧：`canTrustedOfficialPluginRequestScopes`（`~/.nvm/.../openclaw/dist/server-plugins-BgRb-rux.mjs:84-89`）只认 `pluginOrigin === "bundled"` 或 `trustedOfficialInstall === true`；`dispatchTrustedPluginGatewayMethod`（`:446`）第一句就是这个校验；`runtime.gateway.request`（`:528`）的实现直接就是它，**没有旁路**。Taskfold 实测 `origin="config"`（`plugins.load.paths` 本地路径加载）、`trustedOfficialInstall` 非 true。

三次记录：

1. `b7abc5c`（2026-07-29）：服务端对账依赖 `sessions.list`，实机 100% 空转，一天 173 条 warning、零卡片被对账 → 改为本地证据判活。
2. 第 7 项路线 A：整体替换上游 `lifecycle-sync` 的三个否决理由之一（[[15.7-会话生命周期设计]] §3.1）。
3. 第 6 项：上游触发 cron 的唯一调用点走这道门 → 整项不可行。

**规则：以后评估任何上游机制，第一件事是 grep 它的实现里有没有 `gateway.request`。有就直接判不可行，不要往下设计。** 这不是"等 SDK 更新"能解决的——`bundled` 只给随 openclaw 分发的插件，`trustedOfficialInstall` 只给从官方 npm/ClawHub 正式安装的插件，Taskfold 当前的分发方式从架构上就拿不到。只有 Taskfold 走上官方分发路径后，这一类机制才重新进入可选范围（届时第 6 项与第 7 项路线 A 都值得重新评估）。

顺带一个反向推论：**hook 不走这道门**（`api.on("subagent_ended", …)` 一直在正常工作），所以"宿主事件 → 插件"方向的机制都是可用的；不可用的只有"插件主动调宿主 gateway 方法"这一个方向。

## 二、已确认要做的清单

按工作量从小到大排列，均已用真实源码核对了改动点，可以直接作为实现依据。

### 1. 子表索引补齐（很小，零风险）

**现状**：`taskfold_card_events`、`taskfold_card_attempts`、`taskfold_card_comments`、`taskfold_card_links`、`taskfold_card_proof`、`taskfold_card_artifacts`、`taskfold_card_notifications`、`taskfold_worker_logs` 这 8 张子表没有按 `(card_id, ordinal)` 的索引；上游 `3a9d69d` 对同名的 8 张表加了这个索引。

**改动点**：`src/backend/src/sqlite-store.ts` 的 `ensureTaskfoldSchema()`（454 行起）里现有的 `CREATE INDEX IF NOT EXISTS` 块（492-495 行附近）追加 8 条同构索引，用 `IF NOT EXISTS` 保持幂等。可以顺手把 `SCHEMA_VERSION`（38 行，当前 `8`）bump 到 `9` 留一条迁移记录，跟现有的 schema-6/7/8 演进惯例一致；但因为索引创建本身幂等，不 bump 也不影响正确性。

### 2. 归档但未终态诊断（小）

**现状**：`computeCardDiagnostics()`（`src/backend/src/store-card-helpers.ts:426`）第 427-429 行对任何 `archivedAt` 非空的卡片直接 `return []`——一张已归档但状态还没到终态（比如卡在 `running`/`ready`）的卡片不产生任何诊断，dispatch 端也是静默跳过、不报错。上游对应加了 `archived_but_active` 诊断种类。

**改动点**：在 427 行的早退分支之前插入判断——若 `archivedAt` 存在且 `status` 不是终态，先产出一条新诊断再返回；新增的诊断种类要加进 `src/contract/index.ts:74` 的 `TASKFOLD_DIAGNOSTIC_KINDS` 枚举（现有六种：`stranded_ready`/`running_without_heartbeat`/`blocked_too_long`/`repeated_failures`/`missing_proof`/`orphaned_session`）。

### 3. manifest 补 `cliCommands`/`doctorContract`（很小，不影响运行时行为）

**现状**：`openclaw.plugin.json` 缺这两段（`categories` 已在上一轮补上）。运行时功能已经正常（`openclaw plugins inspect taskfold` 已能正确显示 `Commands: taskfold`），只是 manifest 里没有静态声明。

**改动点**：

- `cliCommands`：照抄 `src/backend/index.ts` 里 `TASKFOLD_CLI_OPTIONS.descriptors` 的内容，写成：
  ```json
  "cliCommands": [
    { "name": "taskfold", "description": "Manage Taskfold cards and worker dispatch", "hasSubcommands": true }
  ]
  ```
- `doctorContract`：`src/backend/doctor-contract-api.ts:176` 已有迁移标识 `taskfold-28-kv-to-sqlite`，直接照抄：
  ```json
  "doctorContract": { "stateMigrations": [{ "id": "taskfold-28-kv-to-sqlite" }] }
  ```

两段都不依赖 `openclaw plugins build`（该命令目前只支持声明式 `defineToolPlugin()` 插件，Taskfold 走不通，见「三、评估过但不做」），需要手写进 manifest。

### 4. 执行引擎放开为自由字符串（中，是约束放宽不是缺陷修复）

**现状**：`src/contract/index.ts:16` 的 `TASKFOLD_EXECUTION_ENGINES = ["codex", "claude"] as const` 是固定枚举；上游已放开为自由字符串，`engine`/`model` 字段也改为可选。

**改动点**：把这个常量放开为 `string`（或去掉枚举约束，改成非空字符串校验），并全文检索 `TASKFOLD_EXECUTION_ENGINES`/`TaskfoldExecutionEngine` 的引用点一并放开——具体引用点未逐一列出，需要实现时全文检索确认，尤其注意有没有依赖这个枚举做穷尽性检查（`switch` 完整性）的地方。

### 5. 会话捕获 captureSession（中，全新能力）

**现状**：Taskfold 全代码库没有对应实现——无法把一个已经在跑的 session 直接变成一张卡片。

**改动点**：参照上游 `tpm/openclaw-3a9d69d-workboard-source/extensions/workboard/src/store-core.ts:641` 的 `captureSession(input)` 实现，和 `src/gateway-workspace-methods.ts:64` 的网关方法注册模式，在 Taskfold 对应的 `store-core.ts` 里加同构 store 方法，并在 `gateway-project-methods.ts`（或新建一个 workspace 专用的网关方法文件）里注册 `taskfold.cards.captureSession`。按 `sessionKey` 幂等——同一 `sessionKey` 第二次调用应复用/续接已有卡片而非重复建卡（上游 `store.test.ts` 484/512/516/569 行有对应测试用例可参考）。是否需要额外暴露一个 `taskfold_capture_session` agent 工具，还是像上游一样只做网关方法（供 Control UI/CLI 调用），留待实现时定。

### 6. 板级自动化联动（中偏大，新字段 + 新 service + 跨插件调用）

**现状**：Taskfold 没有 `automationJobId` 字段，卡片完成时也没有触发外部自动化的机制。

**改动点**：参照上游 `tpm/openclaw-3a9d69d-workboard-source/extensions/workboard/src/automation-nudge.ts`：

- 给 `taskfold_boards` 加 `automation_job_id` 列（走 `sqlite-store.ts` 现有的 `ensureColumn()` 惯例）。
- `taskfold_board_create`/board 更新相关工具加对应可选参数。
- 新建一个 service（仿照 `src/backend/index.ts:55`/`:60` 的 `api.registerService(createTaskfoldChangeEventService(...))` 模式），在卡片完成事件时以 60 秒防抖调用宿主的 `cron.run`——实现前需要先确认 Taskfold 当前依赖的 openclaw 插件 SDK 版本是否已经暴露等价的 `api.runtime.gateway`/cron 调用点。

### 7. 会话生命周期两阶段落地（大，架构级，先设计后动代码）

**现状**：Taskfold 用 `reconciler.ts`（本地证据判活，提交 `b7abc5c`：「对账数据源重设计：改用本地证据判定 run 存活」）；上游用 `lifecycle-sync.ts` + `store-lifecycle.ts` + `session-link.ts` 的显式 `prepared → accepted → failed` 状态机 + 每 60 秒定时扫描（30 分钟无活动标记 stale）。

**改动点**：这不是加一个函数能完成的活。两条路线都已经在生产环境跑，需要先读完 `tpm/openclaw-3a9d69d-workboard-source/extensions/workboard/src/{lifecycle-sync,store-lifecycle,session-link}.ts` 三个文件，和 Taskfold 现有 `reconciler.ts`/`dispatcher.ts` 里判活的全部路径做一次架构级对比，再决定是整体替换、两条判活路径并存，还是只把"prepared/accepted/failed 三段式状态"这一层盖在现有判活逻辑之上。建议实现前先出一版设计小结。

### 8. 乐观并发 + 补偿回滚 + owner slot（大，核心写路径改造）

### 9. Control UI 从「自建 iframe SPA」迁移到「宿主原生注入」（大，架构级 UI 改造）—— 已定，下一步就做
