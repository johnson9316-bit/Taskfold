# 上游 workboard 2026.9.4 差异评估

## 背景

Taskfold 是 OpenClaw 内置 `workboard` 扩展在 2026-07-28（upstream commit `78d6c6c`，对应 `openclaw@2026.7.1-2`）的 fork，见 `UPSTREAM.md`。此后独立演进、从不合并上游。本机 OpenClaw 已升级到 `2026.9.4`，本文档评估上游 `workboard` 在此期间的变化，判断哪些值得 Taskfold 取用。

**已定**：不合并上游代码。Taskfold 的 `dist/index.js`（651.6K）与 42 个源文件（`store-*` 系列单文件 30–70K）规模已远超 stock `workboard`（`dist/index.js` 60.3K，加两个共享 chunk）。manifest 工具面对比显示 stock 的 35 个工具 Taskfold 全部具备，另有 8 个自有扩展（Taskfold 43 个 vs stock 35 个），dashboard 的 `dataBindings` / `actionVerbs` 也无 stock 独有项。功能层面无需追赶，**评估聚焦宿主契约层面的缺口**与上游值得借鉴的架构决策。

## 对比方法（2026-09-18 更新：已改用真实源码）

**第一版**（本节以下内容曾经的方法）是静态对比两版 `openclaw.plugin.json`、`runtime-api.d.ts`/`api.d.ts`、`package.json`，并对两版打包产物（`index.js` 及其依赖的共享 chunk）做字符串级 grep 对比——因为当时机器上只有 npm 安装的压缩产物，没有源码。**这个基线选错了**：npm 里装的旧版是 `openclaw@2026.7.1-2`，而 Taskfold 实际 fork 的是 `UPSTREAM.md` 记载的 commit `78d6c6c`——已核实这两者不是同一个点（`78d6c6c` 快照里已经有 `2026.7.1-2` 压缩产物里没有的机制，见下方「已撤回的结论」）。用错误基线得出的几条"上游新增能力"实际是"fork 时就有、Taskfold 一直原样保留"，被误判成了缺口。

`openclaw` 仓库本身是公开的 MIT 项目（`github.com/openclaw/openclaw`），第二版改用**真实 TypeScript 源码**做对比，两份快照都已拉取到本仓库 `tpm/`（被 `.gitignore` 排除，不进版本库）：

| 快照目录 | 对应版本 | 用途 |
| --- | --- | --- |
| `tpm/openclaw-78d6c6c-workboard-source/` | commit `78d6c6c`，`UPSTREAM.md` 记载的 fork 点 | Taskfold 真正的起点基线 |
| `tpm/openclaw-3a9d69d-workboard-source/` | tag `v2026.9.4`，commit `3a9d69d`（与本机 `openclaw --version` 输出的构建号一致） | 本机当前运行的版本 |

## 一、宿主契约缺口（Taskfold 自身需要补的）

### 缺口 1（2026-09-18 更新：已查明根因，结论反转）：`openclaw plugins validate` 失败

```
$ OPENCLAW_DEBUG=1 openclaw plugins validate
[openclaw] Reason: plugin entry does not expose tool or feature authoring metadata: ./dist/index.js
[openclaw] Stack: ... at loadToolPlugin (.../plugins-authoring-command-Dgab1p7G.mjs:428:23)
```

**旧结论**（"`src/backend/index.ts:31` 只处理了 `cli-metadata` 一种模式，没适配新的 tool/feature 元数据模式，需要修入口注册逻辑"）**是猜测，已被实际堆栈证伪**。

带堆栈重跑后定位到宿主源码 `loadToolPlugin`（`plugins-authoring-command-Dgab1p7G.mjs:427`）：它调用 `getToolPluginMetadata(entry)`，这个函数来自 `openclaw/plugin-sdk/tool-plugin`，只认**用 `defineToolPlugin()` 声明的插件**——一种全新的、纯声明式的插件写法（工具作为静态数组随 `id`/`name`/`configSchema` 一起在模块加载时声明，不再靠 `register(api)` 里命令式调用 `api.registerTool()`）。`defineToolPlugin()` 生成的入口对象上会挂一个隐藏 Symbol（`toolPluginMetadataSymbol`）带着这份静态元数据；`getToolPluginMetadata` 找不到这个 Symbol 就返回 `undefined`，`validate`/`build` 直接报错——这就是眼前这条报错的全部原因。

**Taskfold 和 stock `workboard` 用的都是旧的命令式 `definePluginEntry({..., register(api) {...}})` 写法**（已用真实源码核对：`3a9d69d` 版 `extensions/workboard/index.ts` 完全没有 `registrationMode` 字样，`register()` 里直接无条件 `WorkboardStore.openSqlite()`、注册 Control UI/gateway 方法/CLI/service，没有任何早退分支）。用 GitHub 代码搜索确认，整个 `openclaw/openclaw` 仓库目前**只有 `extensions/llm-task/index.ts` 一个扩展用了 `defineToolPlugin()`**——这是一个新引入、目前只服务于"纯工具、无 gateway 方法/Control UI/CLI/service"这类极简插件的写法，`defineToolPlugin` 的类型签名（`DefineToolPluginOptions`）里也确实没有声明 gateway 方法、Control UI descriptor、CLI、service 这些字段的位置。

**结论反转**：`openclaw plugins validate`/`plugins build` 这两个命令目前只支持 `defineToolPlugin()` 声明式写法，**stock `workboard` 自己大概率也过不了**（未直接验证，因为它是内置 bundled 扩展，没有独立目录可指给 `validate` 跑；但源码路径完全等价，没有理由结果不同）。这不是 Taskfold 落后于上游的地方，是宿主这两个 CLI 命令本身还没覆盖到 `workboard` 这一档的复杂插件。**不建议为了让 `validate` 通过而重写 Taskfold 的注册方式**——`defineToolPlugin` 现在的类型定义装不下 Taskfold 已有的 gateway 方法/Control UI/CLI/service，勉强套用会是一次伤筋动骨的架构倒退，性价比很低。缺口 2 里 `controlUi`/`cliCommands`/`doctorContract` 三段 manifest 声明**不依赖这条路径**，可以手写补全（`cliCommands`/`doctorContract` 已有等价的运行时数据可以照抄），不受此项阻塞。

### 缺口 2：manifest 缺 4 个 stock 已声明的顶层段

对比 stock 2026.9.4 与 Taskfold 的 `openclaw.plugin.json`：

| 键 | stock 的值 | Taskfold 现状 |
| --- | --- | --- |
| `categories` | `["tools"]` | **已修复**（本次改动，见 `openclaw.plugin.json`） |
| `cliCommands` | `[{name:"workboard", description:"...", hasSubcommands:true}]` | **缺失** —— 代码里 `src/backend/index.ts` 的 `TASKFOLD_CLI_OPTIONS.descriptors` 已有同构数据，只是没进 manifest。可观察后果：`openclaw plugins inspect workboard` 有 `Commands: workboard` 行，`inspect taskfold` 此前没有；本次启用后实测**运行时已能正常显示 `Commands: taskfold`**（说明命令注册本身工作正常，缺的只是 manifest 静态声明，不影响功能） |
| `doctorContract` | `{stateMigrations:[{id:"workboard-28-kv-to-sqlite"}]}` | **缺失** —— 有 `doctor-contract-api.ts` 但迁移标识未声明在 manifest 里（stock 2026.9.4 把它从代码判断挪到了 manifest 静态声明，见下方「packaging」条目） |
| `controlUi` | `{entry:"dist/control-ui/<hash>/index.js", styles:[...]}` | **缺失** —— 见下方 UI 架构条目 |

### 缺口 3（UI 架构，待评估，工作量最大）：Control UI 从「自建 iframe SPA」到「宿主原生注入」

**已确证的差异**：

- 旧版（2026.7.1，即 fork 点）stock `workboard` **完全没有 UI**（无 `assets/`、无 `dist/control-ui/`）。Taskfold 现在的 `ui/dist/` 独立 Vite SPA + iframe 嵌入方案，在 fork 时点是**唯一选项**，不是绕开了什么。
- 新版 stock `workboard` 新增了一个 858K 的 **Lit** 应用，通过 manifest 的 `controlUi.entry`/`controlUi.styles` 声明，由宿主原生注入（非 iframe）。`package.json` 新增 `openclaw.controlUi: "./browser/index.ts"` 与 `openclaw.assetScripts`（一个共享的 `build-plugin-control-ui.mts` 脚本负责构建并回写 `openclaw.plugin.json` 的 `controlUi` 段）。
- Taskfold 现状的代价记在 README `## Control UI Security`：需要用户手动设置 `gateway.controlUi.embedSandbox: "trusted"` 才能让 iframe 正常工作。改用宿主原生注入理论上能同时去掉这个安全妥协配置项和 iframe 的沙箱开销。

**待验证 / 未评估的部分**：

- 宿主原生 `controlUi` 注入对插件代码的具体要求（是否要求用 Lit、是否兼容当前的其他前端技术栈）——本次未读 `browser/index.ts` 之外的宿主侧注入实现。
- 迁移工作量：`ui/dist/assets/` 现有十几个语言包 chunk（`zh-CN`、`ja-JP`、`ko`、`fr` 等 i18n bundle），迁移到宿主注入模式后这套多语言资源如何搬运未评估。

**结论**：**待验证**，建议单独立项做 spike，不在本次范围内。

## 二、上游新增能力（供参考，非缺口）

以下按「新基线」（`78d6c6c` fork 点 → `3a9d69d`/`v2026.9.4` 真实源码 diff）重新核实。**A、B 两条与旧版结论相反——它们不是上游新增的，是 fork 点就有、Taskfold 一直原样保留至今的机制**，已撤回旧结论。D 拆成两半：claim token 比较那部分也已撤回，CAS/补偿/owner slot 的主体部分维持「真实缺口」。

### A.（已撤回：不是缺口）工作区沙箱访问控制

**旧结论**："待验证，两者设计差异未逐行比对，值得评估参考"——**错误，已撤回**。

逐行核对结果：`extensions/workboard/src/workspace-access.ts` 在 `78d6c6c` 快照里**不存在**，是 `3a9d69d` 才新增的文件（416 行）；但 Taskfold 的 `src/backend/src/workspace-access.ts`（454 行）从 `0b722b6`（2026-07-28，最初的 bootstrap 提交）起就已存在，跟上游这份新文件做 `Workboard→Taskfold` 文本替换后逐行 diff，**导出函数名、顺序、签名几乎一一对应**（`resolveWorkboardAgentWorkspace`/`canonicalizeWorkboardWorkspaceAccess`/`intersectWorkboardWorkspaceAccess`/`assertWorkboardWorkspaceMutationAccess`/`guardWorkboardToolsForWorkspaceAccess` 等 17 个导出，Taskfold 全部具备同名同构版本）。差异只有：Taskfold 用本地 `../../contract/index.js` 而非共享包 `@openclaw/workboard-contract`；用本地内联的 `readRecord` 而非宿主 `asOptionalRecord`；`prepareSandboxWorkspaceAuthority` 参数做了可选化+降级处理；`TASKFOLD_TOOL_NAMES` 比上游多 8 个项目/里程碑/文档相关工具。

**这份文件是 2026-07-28 就随 bootstrap 提交一起进来的，但 `UPSTREAM.md` 记载的 fork commit `78d6c6c` 里没有它**——说明当时实际取用的上游快照比 `78d6c6c` 更新，或这份文件是后续手工移植的，具体哪种未继续深挖（不影响结论）。**结论：Taskfold 已经具备这套设计，无需再评估或移植，第一节缺口列表和这里都不再需要跟踪此项。**

### B.（已撤回：不是缺口）变更事件轮询

**旧结论**："机制类似但规模小得多，上游的 `PRAGMA data_version` 探测可能值得借鉴"——**错误，已撤回**。

`78d6c6c` 快照的 `extensions/workboard/src/change-events.ts` 内容跟 `3a9d69d` 版本**逐字节等价**（只有内部一个 `unsubscribe` 变量的有无差异），二者都已经是「`store.subscribeChanges` 订阅 + 每 1000ms 轮询 `store.reconcileExternalChanges()`」的设计，`PRAGMA data_version` 探测在 fork 点就有。Taskfold 的 `src/backend/src/change-events.ts` 与 `src/backend/src/sqlite-store.ts:2113` 已经是这套机制的原样移植（`TASKFOLD_EXTERNAL_CHANGE_CHECK_MS = 1000`，同样调用 `store.reconcileExternalChanges()`，`PRAGMA data_version` 已在用）。**结论：Taskfold 已经具备，无需借鉴。**

### C. 会话生命周期两阶段落地（prepared → accepted/failed）—— 仍是真实差异，维持原判

`3a9d69d` 新增 `src/lifecycle-sync.ts`、`src/session-link.ts`、`src/store-lifecycle.ts`（`78d6c6c` 里都不存在，确认是 fork 后新加）。`WorkboardLaunchState` 判别联合类型 + `prepareExecutionLaunch`/`acceptExecutionLaunch`/`failPreparedLaunch` 三段式，修复「dispatch 与 session 启动之间崩溃」的空洞；`createWorkboardLifecycleService` 每 60 秒扫描会话状态，30 分钟无活动标记 stale。

已确认 Taskfold 代码库里**没有** `prepareExecutionLaunch`/`acceptExecutionLaunch`/`LaunchState` 等对应字样（全文 grep 零命中）。这与提交 `b7abc5c`（「对账数据源重设计：改用本地证据判定 run 存活」）解决的是同一类问题，但走的是不同路线——本地证据判活 vs 显式两阶段状态机+定时扫描。**结论：这是本文档里唯一一条「两边都已实际部署、需要架构对比取舍」的项，值得重点评估，具体对比留待后续。**

### D. 存储正确性：拆成两半

**D1（已撤回）claim token 常数时间比较**：Taskfold 的 `store-card-helpers.ts:362`、`store-workflow.ts:66`、`tools.ts:24` **均已使用** `safeEqualSecret`（从 `openclaw/plugin-sdk/security-runtime` 导入），跟上游做法一致。上次回复里把这个当"可直接搬的一行改动"推荐给用户是错的，已经做了，不用再动。

**D2（维持缺口）乐观并发 + 补偿 + owner slot**：已确认 Taskfold 全代码库搜索 `runOperation`/`registerIfUpdatedAt`/`OwnerAvailable`/`compensat`/`rollback` **零命中**——`expectedUpdatedAt` 式 CAS、失败补偿回滚（`compensateWorkspaceMutation`）、owner slot（`claimIfOwnerAvailable`，防一个 owner 同时持有两张 active 卡片，5 分钟宽限期）这三样在 `3a9d69d` 的 `store-runtime.ts`/`store-compensation.ts`（均为 fork 后新增文件）里，Taskfold 确实没有对应实现。**结论：这是真实缺口，维持原判，值得评估。**
