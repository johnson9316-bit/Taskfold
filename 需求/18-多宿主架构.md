# 18 多宿主架构

> **已定（2026-09-24）。** Taskfold 从「OpenClaw 插件」转为**多宿主工具**：OpenClaw、VS Code 先行，以后还有 DeepSeek harness（dsh）、pi。OpenClaw 降为适配层之一，**Gateway 不再是必需组件**。
>
> 跨主题请从 [[README]] 进入。本文推翻 [[16-文件存储改造]] 的分叉 A1（放弃多进程假设），并改写 [[2-产品定位与范围]]、[[5-技术架构与选型]] 中「唯一形态是 OpenClaw 插件」的表述。存储格式、目录、revision CAS 等 16 的其余定案不变。
>
> 依据是 2026-09-24 的四路只读调研：后端与 OpenClaw 的耦合、前端与宿主的耦合、VS Code 现有看板扩展、开源文件型看板加文件锁选型。结论摘要见第八节。

## 一、结论先行

| 项 | 定案 |
|---|---|
| 真相源 | `.taskfold/*.md`（沿用 16：Markdown + frontmatter，纳入 Git） |
| 核心 | `@taskfold/core`，纯 Node 库，**每个宿主进程在进程内加载、直接写文件**；不引入常驻守护进程 |
| 一致性 | 跨进程文件锁（`proper-lockfile`，两层）+ 按内容 hash 的 revision CAS + 写临时文件后 rename |
| AI 写入契约 | **只做 CLI**（`--json` + skill 文档），**不做 MCP** |
| VS Code 首版 | WebviewPanel 看板，复用现有 Lit 组件，**可编辑卡片**，不派活 |
| 执行能力 | 这一阶段看板不派活；OpenClaw 现有执行功能原样保留，以后再接 OpenClaw/dsh 派活 |
| 包结构 | npm workspaces monorepo：`core` / `cli` / `openclaw` / `vscode` |
| worktree 写入 | 一律写**主 checkout** 的 `.taskfold/`，用 `git rev-parse --git-common-dir` 定位 |
| 抢锁失败 | 最多等约 2 秒，超时返回 `LOCKED` |
| 实施顺序 | core（带锁）→ CLI → OpenClaw 插件改调 core → VS Code 扩展 |

## 二、架构

```
.taskfold/*.md                     ← 唯一真相
      │
@taskfold/core                     ← 读写、CAS、两层锁、外部变更感知
      │
 ┌────┼──────────────┬───────────────────┐
CLI              OpenClaw 插件         VS Code 扩展
 │               (工具+面板+执行)      (WebviewPanel + 进程内 core)
Claude Code / Codex / pi / dsh …（经 shell 调用）
```

四类写入最终都落到同一个 core、同一套锁：

1. 人在看板上写（OpenClaw 面板或 VS Code Webview），进程内调用 core。
2. 人手工改文件、`git checkout`/`pull`：不经过锁，由内容 hash CAS 加外部变更感知接住（16 的 R4）。
3. AI 通过 CLI 写入。
4. Gateway 的机器写入（`subagent_ended` 回写、reconciler、claim 心跳），经 OpenClaw 适配层进程内调用 core。

## 三、core：从 `src/backend/` 抽出

### 3.1 可搬范围

- **原样搬**：store 各层（`store-core` → `enrichment` → `promote` → `workflow` → `notifications` → `projects`）、`normalizers`、`inputs`、`automation`、`change-tracker`、全部 `file-store-*`、`markdown-*-format`、`card-lookup`、`card-redaction`、`session-link`、`worker-prompt`、`persistence-types.ts`、`project-document-*`。其中 `project-document-reader.ts:9` 依赖 `workspace-access`，要先拆开。
- **只借了 SDK 纯工具函数，换本地实现**：`store-workflow.ts:13-15`、`store-card-helpers.ts:17-18`、`store-constants.ts:3-5`、`store-compensation.ts:3`、`file-store-paths.ts:6,41`（`resolveStateDir` 改为由调用方注入）。
- **留在 OpenClaw 适配层**：`index.ts`、`gateway*.ts`、`tools*.ts`、`command.ts`、`cli.ts`（现有的 OpenClaw CLI 子命令）、`card-execution.ts`、`dispatcher*.ts`、`reconciler.ts`、`lifecycle.ts`、`workspace-access.ts`、`change-events.ts`。

### 3.2 执行状态这次不拆

执行状态机（claim、heartbeat、launch、finish、reclaim）和卡片状态机写在同一个类里（`store-workflow.ts:192-800,1000`），`store.ts:88-200` 还有 `dispatch()`。**这次原样搬进 core**，CLI 和 VS Code 不暴露这些方法。OpenClaw 适配层照常调用，自动走同一套锁。拆分留到以后接执行时再做。

### 3.3 必须改掉的单进程假设

以下 7 处在多进程下都会失效，改成加锁是 core 的主要工作量：

| 位置 | 现状 | 改法 |
|---|---|---|
| `file-store-atomic.ts:5-17`、`file-store-cards.ts:239-265` | CAS 的原子性只靠读和写之间全是同步调用（注释写明依赖 A1） | 卡锁内完成 CAS |
| `file-store-card-id.ts:30` 起、`file-store-cards.ts:273-278` | 扫描取最大值再用 O_EXCL 创建，两个进程会抢同一个 ID | 全局锁内分配 ID |
| `file-store-change-cursor.ts:73-92` | `reserveFileChangeRevisions` 先读后追加，没有锁 | 全局锁内预留 |
| `store-core.ts:156,241-248` | `enqueueMutation` 是进程内 Promise 队列 | 保留作进程内串行，跨进程由锁兜底 |
| `store-core.ts:922` | 后端没实现 CAS 时退回只靠内存队列 | `compareAndSwap` 改为**必选** |
| `store-change-tracker.ts:18,85-127`、`store-core.ts:216-238` | 变更事件总线是内存 listener | 改由 ChangeSource 端口驱动（见 3.5） |
| `file-store-reconcile.ts:114,145` | 内存哈希表加 `noteOwnWrite` 自写标记 | 改为按 core 返回的 revision 识别自己的写入 |

另有 `change-events.ts:4,18` 的 1 秒轮询和 `store-workflow.ts:91-92` 的进程级 instanceId，前者并入 ChangeSource，后者保留（多进程下每个进程各有一个 instanceId，语义不变）。

### 3.4 锁设计

- **库**：`proper-lockfile`。纯 JS，三个宿主都不用处理原生 ABI；Backlog.md 在生产中用的就是它。
- **两层锁**（照搬 Backlog.md）：
  - 全局锁：只管 ID 分配、新建卡片、revision 预留、跨卡操作。
  - 卡锁：每张卡一把，保护这张卡的读-改-写。锁目标是卡片文件本身。
  - 跨卡操作先按 ID 排序再依次加锁，避免死锁。
- **写入流程**：拿卡锁 → 重读 → 按**内容 hash** 比对 revision → 写临时文件 → rename → 放锁。用内容 hash 而不用 mtime，是因为人手工编辑和 `git checkout` 不经过锁。
- **锁文件位置**：放在主 checkout 的 `.taskfold/.locks/`，并加入 gitignore。
- **抢锁失败**：最多等约 2 秒，超时返回错误码 `LOCKED`。
- **所有宿主的 `stale`/`update` 参数必须统一**，写死在 core 里。`proper-lockfile` 的 README 明确说参数不一致的情况检测不到。
- **进程被挂起超过 stale 时间**（比如 VS Code 调试断点），锁会被别人抢走，必须处理 `onCompromised`：放弃这次写入，按冲突上报。

### 3.5 需要新写的端口（粗估）

1. **StorageBackend**：由 `TaskfoldBackendStores`（`store.ts:57-73`）、`TaskfoldKeyedStore`（`persistence-types.ts:42-64`）收紧而来，CAS 改为必选。
2. **MutationLock**：两层锁，取代同步原子性假设。
3. **ChangeSource**：外部变更感知，由各宿主驱动（`fs.watch` 或 VS Code FileSystemWatcher），watcher 事件只当刷新提示，另配定期全量重读；要能识别 rename 事件。
4. **PathResolver**：定位主 checkout 与 `.taskfold/`，取代 `resolveStateDir`。
5. **WorkspaceAccess**：路径安全判断（`canonicalPath`、`isPathInside`）。
6. **Clock / IdGenerator**：可选，`store*.ts` 里有 73 处 `Date.now()`。
7. **ExecutionHooks**：在 OpenClaw 适配层实现，core 只暴露状态迁移。

### 3.6 worktree

`.taskfold/` 纳入 Git，所以每个 worktree 都有一份卡片副本（16 的 R1）。定案：**任何宿主在任何 worktree 里运行，都通过 `git rev-parse --git-common-dir` 找到主 checkout，读写主 checkout 的 `.taskfold/`**，全局锁也放在那里。worktree 里那份副本视为过期快照，不读不写。

## 四、CLI

照 Backlog.md、kanban-md 验证过的做法：

- `--json` 输出统一为 `{schemaVersion, kind, ...}`；错误返回稳定错误码（`CONFLICT`、`LOCKED`、`NOT_FOUND`…）、非零退出码，stderr 输出结构化 JSON。
- stdout 不是 TTY 时自动切成纯文本输出。是否加省 token 的 `--compact`，实施时再定。
- 每个命令的 `--help` 带参数说明、读写对象和示例。
- 修改参数以**字段级增量**为主（如 `--status`、`--append-notes`）；只有整体替换正文时才要求带 `--expect-revision`。
- 给 AI 的指引：往 AGENTS.md / CLAUDE.md 注入一段**短的、带版本号**的标记块（如 `<!-- TASKFOLD GUIDELINES START/END -->`），详细用法让 AI 按需跑 `taskfold instructions` 获取；skill 文档版本跟 CLI 对齐。标记块里写明「不要直接编辑 `.taskfold/` 下的 md 文件，一律走 CLI」。
- 命令行框架沿用仓库已有的 `commander`。

## 五、VS Code 扩展

- **界面形态**：看板用 **WebviewPanel**，放在编辑器区域。**不用 CustomEditor**：它的撤销、dirty、保存模型绑在单个文件上，每卡一个文件的看板套不进去；它「先缓冲后落盘」的模型也和多写入者冲突。调研里凡是用 CustomEditor 的实现，存储全是单文件。
- **前端复用**：前端所有读写都集中在 `browser/project-host.ts`，经 `browser/host.ts:23` 的 `request(method, params)` 调用。把 `host.ts` 抽成 host 接口（`request`、`subscribe`、`connected`、`locale`、`confirm`、能力开关），另写 VS Code 入口和主题映射 CSS，前端大约改 5 处。**不另写一套看板**：那相当于重写 `project-view.ts` 2763 行中的大部分，并长期和现有版本不一致。
- **数据通路**：Webview ⇄ postMessage（判别联合类型，双向都有类型定义）⇄ 扩展进程，扩展进程内把 method 名映射到 core。`changes.wait` 长轮询改成 ChangeSource 推送。
- **首版隐藏**：执行相关的 `renderExecutionSection`（`project-view.ts:1926`）、`renderExecutionStartModal`（`:2393`），`project-host.ts:865-1035` 的 execution 方法，以及 `sessions.steer`、`chat.abort`，用能力开关隐藏。
- **正文编辑**：主要在看板里编辑（复用现有卡片详情表单，每次提交是一次原子写）；另加一个按钮，用 VS Code 原生编辑器打开对应的 md 文件作为备用。
- **冲突处理**：CAS 失败时弹「Reload / Overwrite / View Diff」三选一（借鉴 `ysamlan/vscode-backlog-md`）。**拖拽也要走 CAS**，这是那个扩展漏掉的地方。
- **排序**：拖拽只改被拖动的那张卡，可参考 fractional-indexing 的做法。现有卡片的排序字段如何表示，实施时核实。
- **需要替换的浏览器 API**：`window.confirm`（`project-host.ts:454,841,1003`）改用 host 提供的方法；语言设置的 `localStorage`（`i18n/lib/translate.ts:68,88`）改为跟随 `vscode.env.language` 或用 `vscode.setState`；主题变量映射到 `--vscode-*`。

## 六、被否掉的路线

下一个接手的人不要再走这几条：

| 路线 | 否掉的原因 |
|---|---|
| VS Code 做纯 Gateway 客户端 | Gateway 只存在于 OpenClaw，多宿主下不能是必需组件 |
| MCP 作为 AI 写入契约 | 要宿主支持才能用；CLI 所有能跑 shell 的 agent 都能用。草创阶段两者只留一个 |
| MCP 转发给 Gateway | 同上，且要求 Gateway 在线 |
| 常驻守护进程 `taskfold serve` 做唯一写入者 | 要管进程的启动、端口、崩溃恢复，多宿主下不值；**保留作以后的升级路径** |
| 照抄 Backlog.md 的「无 CAS、直接覆盖原文件」 | Taskfold 有 Gateway 高频机器写入，16 已定保留 revision CAS |
| VS Code 用 CustomEditor / CustomTextEditor | 见第五节 |
| VS Code 另写一套轻量看板 | 见第五节 |
| 整板全量保存 | 多写入者下必然互相覆盖 |
| 按 mtime 判断变更 | 秒级粒度、同秒两次写会漏；人手工编辑不经过锁 |
| 原生锁库（`fs-ext`、`fs-native-extensions`） | 要和 VS Code/Electron 的 ABI 对齐，三个宿主各编一遍 |
| 每个 worktree 各写各的 `.taskfold/` | 合并冲突变多，主仓库看板看不到 agent 的改动 |

## 七、实施拆分

1. **core**：建 npm workspaces 结构；抽出 core；实现两层锁与必选 CAS，逐项改掉 3.3 的 7 处单进程假设；PathResolver 实现主 checkout 定位。完成判据：两个进程并发写同一张卡、并发新建卡片的测试，**先证明它在旧实现上会红**。
2. **CLI**：按第四节实现卡片的增删改查与状态流转，附 skill 文档与 `taskfold instructions`。完成判据：`--json` 输出与错误码有契约测试。
3. **OpenClaw 插件改调 core**：工具、网关方法、执行调度全部改为依赖 core 包；现有功能不回退。完成判据：现有单测全绿，本机 Gateway 实际加载后面板可用（验证方法见 `AGENTS.md`）。
4. **VS Code 扩展**：抽 host 接口、写 VS Code 入口和主题 CSS、扩展进程接 core、冲突三选一。完成判据：在 VS Code 中拖卡、编辑正文，同时用 CLI 改同一张卡，能正确弹冲突。
