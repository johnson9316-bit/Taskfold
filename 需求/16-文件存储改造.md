## 一、结论先行：这件事比预想便宜，但有一个真决策

**便宜的原因——业务层根本不知道 SQLite 存在。**

全仓库所有 SQL 只出现在 `src/backend/src/sqlite-store.ts` 一个文件里。其余 12 个 `store-*.ts`、`dispatcher.ts`、`card-execution.ts`、`reconciler.ts` 全部只调用 `src/backend/src/persistence-types.ts:42-64` 定义的 KV 接口：

```
register / lookup / delete / entries / compareAndSwap? / registerIfAbsent?
```

没有任何业务代码发出 `.prepare()` 或 `db.exec()`。**换存储后端 = 用同一接口重写一个文件**，接口边界已经干净。

**更便宜的原因——关系型能力实际上一个都没用上：**

| 本以为要处理的 | 实际情况 | 证据 |
|---|---|---|
| 复杂 JOIN | 全库唯一 1 处 JOIN，在附件读取 | `sqlite-store.ts:2068-2074` |
| 聚合查询 | **零 `GROUP BY`** | 全文 grep 无命中 |
| SQL 排序 | `SELECT ... ORDER BY` 的结果被上层用 JS 重排了一遍，等于白做 | `sqlite-store.ts:1596` vs `store-card-helpers.ts:36-44` |
| 分页 | 没有。`cards.list` 只收 `boardId`，返回整板全部卡片 | `gateway.ts:128-138` |
| 索引优化 | `claim_owner_id` 索引建了，生产代码**从未查过**（唯一读点在测试里） | `sqlite-store.ts:486,493-494` |
| 行数上限 | `MAX_CARDS=2000` 只在**从未被调用**的 `TaskfoldStore.open()` 路径生效，生产路径无上限 | `store-constants.ts:8`；`store.ts:271-305` 零调用点 |

`list()` 现在的真实行为（`store-core.ts:278-289`）：`entries()` 全表读出**全部**卡片连同 13 张子表 → JS 里按 `boardId` 过滤 → `toSorted()` 重排。**没有缓存层。** 这套读路径换成"扫目录读文件"在语义上是等价的。

> **一句话**：现在这个 SQLite 是一个昂贵的 KV 存储，外加下面三样真正用到的东西。

**贵的地方——SQLite 目前不可白嫖地顶着三件事：**

| 机制 | 现在靠什么 | 文件系统有无对等原语 |
|---|---|---|
| 跨进程 CAS（防重复认领） | `compareAndSwap` 在 `BEGIN IMMEDIATE` 里**先拿写锁再读 revision**（`sqlite-store.ts:1531-1551`，注释原文说明此顺序） | ❌ 无。只能用锁文件模拟 |
| change cursor 跨重启单调 | `{epoch, revision}`：epoch 是库级 UUID（`ensureChangeEpoch`，`:528-545`，`INSERT OR IGNORE` 处理并发首创）；revision 用**事务内 `SELECT`+`UPSERT` 预留 10000 区块**（`reserveChangeRevisions`，`:554-569`；`store-change-tracker.ts:9`） | ❌ 无。"读当前值+原子写回更大值"需要额外设计 |
| 外部变更感知 | `PRAGMA data_version` 每秒轮询（`change-events.ts`），发现别的进程提交过就本地广播 | ❌ 无对应原语，要换 mtime 轮询 / `fs.watch` |

外加一个**整卡原子写**：`insertCard()`（`sqlite-store.ts:1155-1519`）在一个 `BEGIN IMMEDIATE` 事务里 UPSERT 主表 + "先删后插"重写 13 张子表。

**而这三件事全部锚定在同一个前提上——"可能有两个 Gateway 进程共享同一个库"。**

代码里为这个前提做了明确防护（`sqlite-store.ts:1540,1558` 与 `change-events.ts:16` 的注释直接写 "another Gateway process"；`test/card-revision.test.ts` 有 `openSharedDatabase()` 双进程用例；`VERIFICATION.md` 记录过四个客户端并发 claim 恰好一个赢的实测）。但**部署现状是单 Gateway 进程**（systemd user service，`127.0.0.1:18789`，loopback-only，`AGENTS.md:13`）。

> **这个前提要不要保留，是本次改造唯一真正的架构决策。** 保留，就得把上面三样在文件系统上重建一遍；放弃，进程内 `enqueueMutation` 队列（`store-core.ts:236-244`）已经够用，工作量至少减半。
>
> **已定：放弃（分叉 A1，见 5.1）。** 但请连带读 R4——兼容 Backlog.md 从另一个方向引回了外部写入者，跨进程感知不能全丢。

## 二、现状里已经不原子的地方（迁移不会让它更糟）

这些是**现存事实**，不是迁移引入的风险。列出来是为了避免把它们误记到迁移账上：

1. **附件是两次独立写 + 手工补偿，本来就不是事务**：`addAttachment()`（`store-enrichment.ts:144-181`）先写 blob 表，再 `updateCard()` 写卡片子表，失败时 `catch` 里手动 `delete()` 回滚。
2. **board / milestone / document / subscription 各自独立 `register`，无跨实体事务**（`sqlite-store.ts:1605-1930`）。`archiveProject` / `deleteBoard` 不级联处理卡片，只做防御性拒绝（`store-projects.ts:466-483,1007-1018`）。
3. **两处无补偿的整卡覆盖回滚（真实 bug）**：`card-execution.ts` 与 `dispatcher.ts` 中 run 启动失败后的工作区回滚路径，`store.update()` **都没传 `expectedRevision`**。在"建 worktree → 起 subagent"这个秒级到十秒级窗口内的任何并发编辑，会被这次回滚整卡覆盖（静默的 last-writer-wins 丢数据）。[[15.8-并发与补偿设计]] 第 2.4 节已记录，2026-09-18 核对属实。
   > ⏳ **状态可能已变**：同日仓库工作区出现未提交的补偿实现（新增 `src/backend/src/store-compensation.ts` 三路归并层 + 三个 compensation 测试，并改动 `dispatcher.ts` / `store-core.ts` / `store-workflow.ts`），即 [[15.8-并发与补偿设计]] 子项 2 正在落地。**本条与分叉 F 在动工前须重新核对，不要照搬本文结论。** 原文给出的行号已因这批改动失效，故此处改为按函数与场景描述。
4. **owner 跨卡不变量缺失**：per-card CAS 只保证"同一张卡不被 claim 两次"，**不保证"同一个 owner 不会同时持有两张卡"**。上游 workboard 有 `claimIfOwnerAvailable`（事务内跨卡断言），Taskfold 没有。这是 commit `14d698b` 删掉 `pendingFlowboardDispatches` 跨卡锁引入的回归，[[15.8-并发与补偿设计]] 第 3 节、[[15.10-并发执行模型调查]] 4.3 已记录。

> **第 3、4 项若沿用"整卡覆盖"语义迁移，会原样带进文件方案。** 要不要趁这次一起修，见第五节分叉 F。

## 三、Backlog.md 给出的范本

它的价值在于**证明了这条路在真实项目里走得通**：214 个活跃任务文件、纯 Markdown、零数据库、自己 dogfood 自己开发。以下是核对源码后确认的关键手法。

| 手法 | 它怎么做的 | 证据 |
|---|---|---|
| **锁内重读** | 读-改-写的锁**拿到之后重新从磁盘读一次**再改。注释原文：只锁写会在两个写者交替释放/获取时丢更新，因为第二个写者基于第一个写之前的快照继续改 | `src/core/backlog.ts:2555-2589` |
| **两种锁策略** | 创建用**可重试**锁（`withCreateLock`，排队等 ID）；编辑用 **`retries:0` fail-fast** 锁（竞争就报错，让人或 agent 自己决定重试，绝不后台悄悄合并） | `src/file-system/operations.ts:614-632,637-650` |
| **批量锁排序** | 多任务批量编辑先按 ID 排序再依次加锁，避免死锁 | `operations.ts:687-696` |
| **零持久化索引** | 全仓库无 `.cache` / `.db`。每次进程重新 `Bun.Glob` 扫目录，并发 32 读+解析 | `operations.ts:941-993,231` |
| **进程内缓存按内容哈希** | 常驻进程（browser/MCP）缓存 `Map<path,{content,task}>`，**按文件内容字符串**而非 mtime 做 key；写操作后 epoch 自增强制失效 | `operations.ts:325-328,879-895,449` |
| **index-first, hydrate-later** | 跨分支扫描先用 `git ls-tree` 只拿文件名建轻索引（不读内容），选出 winner 后才 `git show` 拉正文 | `src/core/task-loader.ts:330-573,227-256` |
| **架构守卫测试** | 单任务命令的测试把所有跨分支方法 mock 成"被调用就抛错"，断言它们永不触碰全量扫描路径 | `src/test/local-task-command-performance.test.ts:28-49` |
| **正文哨兵分区** | `<!-- SECTION:PLAN:BEGIN/END -->` / `<!-- AC:BEGIN/END -->` 包裹每个逻辑字段，可安全增量更新单段而不破坏人工写的其它内容；整行匹配+深度计数，正文里**提到**标记文字不会被误判 | `src/markdown/structured-sections.ts:241-247,38-41,316-331` |
| **推送只作 invalidate 信号** | WebSocket 只发字符串 `"tasks-updated"`，**不带 diff**；前端收到后拉 REST 全量，本地按 id reconcile 复用旧引用 | `src/server/index.ts:349-364`；`src/web/utils/reconcile.ts:29-39` |
| **ID 冲突域显式定义** | 候选 ID 集合 = 本地 + 所有 git worktree + 本地所有分支 + `git fetch` 后的远程分支；锁放在 git common dir 下（多 worktree 共享一把） | `src/core/backlog.ts:1500-1514`；`src/test/remote-id-conflict.test.ts:1-63` |
| **事后修复工具兜底** | 承认"扫远程"不是 100% 保证，配 `backlog doctor --fix` 扫重复 ID、原子重命名、扫引用给复核报告 | `src/core/duplicate-task-repair.ts`；`src/cli.ts:5572-` |
| **ID 回收规则** | 归档（软删除）的 ID **可回收**，完成的 ID **永久保留** | `backlog/archive/readme.md` |

**它主动放弃的东西**（从 `MANIFESTO_zh.md` 与源码读出，对我们是风险提示）：

- **无跨文件原子事务**。单文件读-改-写在锁内串行，多文件操作靠排序加锁尽力而为，没有 WAL / 回滚日志。
- **并发编辑同一任务的默认结果是后来者直接报错**（fail fast），不静默覆盖、不自动 merge。
- **无复杂查询**。`search` 是内存 Fuse.js，每次集合变化整体 `rebuildFuse()`；`list --filter` 全量读进数组再 JS 过滤。
- **主动放弃 UUID**：坚持可读递增数字 ID，代价是自建一整套跨分支扫描 + 锁 + doctor 修复机制。
- **`--no-git` 模式下 git-index 校验全部失效**，并发保护退化为只剩 `proper-lockfile`。

> **一条明确的"不要抄"**：Backlog.md 没有 revision / CAS 字段，纯靠悲观锁。Taskfold 已经有 `expectedRevision`（`07aed26` 起网关层透传并返回结构化冲突）。两者解决的是**不同层**的问题——文件锁防"两个进程同时写同一文件"，`expectedRevision` 防"客户端拿着旧数据来改"。不必为了向 Backlog.md 看齐而退回悲观锁。

## 四、无需决策的机械部分

这些与分叉选择无关，是确定要做的工作：

1. **迁移的唯一改动面是 `sqlite-store.ts` 的替代实现**，业务层不动。新实现必须满足 `persistence-types.ts:42-64` 的同一份接口契约，并让 `test/change-wait.test.ts`、`test/cards-update-cas.test.ts`、`test/card-revision.test.ts` 全绿——这三个测试是 revision/cursor 语义最好的可执行规格。
2. **subscriptions 是纯机械搬迁**：各自独立、无跨实体事务、语义只有 `lookup/register/delete/entries`。（boards 拆为"注册表在插件目录 + 项目数据在 repo"，milestones 改 Markdown，二者不再是机械搬迁，见第六节。）
3. **`taskfold_project_documents` 的 `UNIQUE(board_id, document_key)` 用目录结构天然表达**：B2 下每个项目一个 `.taskfold/`，`board_id` 维度由目录本身承担，文件名即 `document_key`，不需要额外唯一性检查。
4. **附件 blob 从 SQLite BLOB 列改为独立文件**，卡片侧只存引用。现有两阶段写 + `catch` 补偿逻辑原样保留即可，风险不比现在高。
5. **`doctor` 命令必须扩展**：文件方案没有外键约束，"卡片引用了不存在的 milestone"这类问题只能靠体检发现。参照 Backlog.md 承认"防不住就修得了"的思路。
6. **旧库迁移器**：一次性读 SQLite 导出为目标文件布局。现网有 102 张卡（[[15.10-并发执行模型调查]] 已核实），数据量小，但不能像 v0.1 那样直接丢弃——这次是真实数据。迁移前自动备份 `.sqlite`，提供 `--dry-run` 对账。

## 五、分叉点定案

### 5.1 已定（2026-09-18）

| 分叉 | 结论 | 理由 |
|---|---|---|
| **A 多进程假设** | **A1 放弃**。认定单 Gateway 进程独占，靠进程内 `enqueueMutation`（`store-core.ts:236-244`）串行化 | 部署现状就是单进程；工作量减半。遇到问题再优化 |
| **B 数据落地** | **B2 `<repo>/.taskfold/` 并入库** | 数据跟着项目走，可 review、跟着 clone 走。符合业界 7/7 入库共识（[[17-规划文件目录规范调研]] 第四节） |
| **C 文件格式** | **C2 Markdown + frontmatter** | 人可读可手编、Git diff 友好、agent 可直接 `cat` |
| **C 附属：卡片 ID** | **改可读递增 `card-<n>`，UUID 保留为内部主键**。参照 Backlog.md | 现 cardId 是 `randomUUID()`（`store-core.ts:565`），直接当文件名则 C2「人可读」的价值废掉一半 |

**A1 依赖的"单写入者"只覆盖 Gateway 自己**：卡片状态由 Gateway 写（`subagent_ended` 事件、reconciler 扫描、claim 心跳）；agent 改卡片走工具与 Gateway RPC，**不直接写文件**——即便 agent 跑在 worktree 里，写入仍然经过 Gateway 这一个入口。A1 成立的依据在此，不只是"现在只跑了一个进程"。

> ⚠️ **但兼容档引入了第二个写入者**：`backlog` CLI 与人手工编辑都是预期中的合法写入，它们绕过 Gateway。A1 去掉的跨进程感知因此不能全丢，必须换一个形式补回来——**见 R4，这是第 1 期的必交付项**。

### 5.2 已定（2026-09-18 确认）

| 分叉 | 结论 | 理由 |
|---|---|---|
| **D 一致性策略** | **D1 保留 revision CAS** | 见下方说明。**这一条明确不抄 Backlog.md** |
| **E change cursor** | **E2 追加式变更日志** | 最接近现有 cursor 语义，客户端契约不动 |
| **F 已知 bug** | **F2 先原样迁移** | 迁移 diff 干净；bug 走 [[15.8-并发与补偿设计]] 自己的排期。⏳ **该排期似乎已在执行**（见第二节第 3 条的状态注），动工前须复核这两处的实际状态 |

**D 为什么不抄 Backlog.md**：它没有 revision 字段，纯靠悲观锁 + 锁内重读（`backlog.ts:2555-2589`）。但那是因为它从来没做过 CAS，不是因为悲观锁更好。Taskfold 在 `07aed26` 刚把 `expectedRevision` 透传打通到网关层并返回结构化冲突，退回悲观锁等于把刚做完的工作拆掉，且 UI 的冲突处理要跟着改——**这不是最少改动，是更多改动**。在 A1 单进程下，revision 校验几乎零成本：`stampCardRevisions()`（`store-core.ts:106-131`）是唯一的递增边界，写卡路径绕不过去，文件方案照搬即可。

**E 的第五选项**：Backlog.md 根本没有 cursor 概念——WebSocket 只发一个字符串 `"tasks-updated"`，不带 diff，客户端收到后拉 REST 全量再本地 reconcile（`server/index.ts:349-364`、`web/utils/reconcile.ts:29-39`）。这个模式天然免疫"漏发一条消息导致永久不同步"。**但它要改 `contract/index.ts:323-326` 的 cursor 契约和 `ui/src/main.ts:196-227` 的长轮询**，改动比 E2 大，故未采用。将来若 E2 的日志轮转变麻烦，这是现成的退路。

### 5.3 项目必须绑定本地仓库（2026-09-18 定）

**结论：不支持无本地仓库的项目。** 创建项目时必须指定 `kind` 为 `dir` 或 `worktree` 的 `defaultWorkspace`。

**现网代价为零**（2026-09-18 实测 `~/.openclaw/plugins/taskfold/taskfold.sqlite`）：

| 项目 | `defaultWorkspace` | 卡片数 |
|---|---|---|
| ProCloud | `dir` → `/home/john/src/lz/procloud` | 81 |
| Taskfold | `dir` → `/home/john/src/personal/Taskfold` | 21 |
| `default` | 无 | **0** |
| `fb-probe` | 无 | **0** |

装着全部 102 张卡的两个项目都已绑定本地仓库；两个没有 workspace 的都是空壳（上游默认 board 与探测遗留）。**迁移时直接丢弃这两个空项目。**

**这个约束换来的简化**：

- 项目数据目录解析只剩一条分支，不需要 `~/.openclaw/plugins/taskfold/projects/<projectId>/` 回落路径
- `card-execution.ts:118-125` 现有的两个错误分支（卡片级 scratch、项目级缺失）可合并为一个
- 不必定义"纯看板项目"这种第二形态

> **与上游的差异**：上游 workboard 的 board **不需要**任何本地目录——它的数据全在宿主 SQLite 里，`defaultWorkspace`（`packages/workboard-contract/src/index.ts:298`）只回答"agent 在哪跑"。Taskfold 走 B2 之后，这个字段同时要回答"数据存哪"，因此必须收紧为必填。这是本次改造**主动偏离上游**的一处，需在 [[15-上游2026.9.4差异评估]] 登记。

**项目数据目录解析规则**（`defaultWorkspace` 必为 `dir` 或 `worktree`）：

```

```

`worktree` 类型必须取 `sourcePath` 而非 `path`——`path` 指向临时 worktree，**数据放那里会随 worktree 一起被删**。

> **但这两个目录当前都是空规划**：执行账本属 M4、度量属 M9，现有代码均未实现（2026-09-18 全量 grep 确认）。本次实施只需为它们**留出位置**，不需要定格式，也不需要定备份方案。

**与 `.planning/` 的关系——本版本无关系**：GSD 缝合已整体推迟（[[1-规划评审]] 决策 6），`.taskfold/` 是本版本项目仓库里唯一的 taskfold 数据目录，不存在"两个数据目录的写入边界"问题。（`.planning/` 是 GSD Core 的第三方约定；Taskfold 现有的 `project-document-discovery.ts` 只把它当文档扫描的路径白名单，与本次改造无交集。）

### 6.2 兼容的强制约束：独有字段只能放正文，不能放 frontmatter

**已实测确认（2026-09-18，读 Backlog.md v1.52.0 源码）：**

| | 结论 | 证据 |
|---|---|---|
| **frontmatter** | ❌ **未知字段会被静默抹掉** | `serializeTask()` 的 `const frontmatter = {...}`（`src/markdown/serializer.ts:50-72`）是**白名单**，逐字段从 `Task` 类型对象构造。不在 `Task` 里的键一次写回就没了 |
| **正文** | ✅ **未知哨兵区块会被保留** | `updateStructuredSections()`（`src/markdown/structured-sections.ts:789-796`）只 `stripSectionInstances` 自己认识的 key，其余内容留在 `working` 里作为 tail 带过去；且 `serializeTask` 的正文基线是 `task.rawContent`，做增量更新而非重建 |

> **因此：`uuid` / `revision` / `boardId` / `position` / `execution` / `claim` / `delivery` 等 Taskfold 独有字段，一律放进 `<!-- SECTION:TASKFOLD:BEGIN/END -->` 区块。** 放进 frontmatter 的话，用户用一次 `backlog task edit` 就会把它们全部清空——而且没有任何报错。

这条是兼容档能成立的前提，不是风格偏好。第 1 期实现时须配一个回归测试：造一张带完整 Taskfold 字段的卡，用 `backlog` CLI 编辑一次，断言正文区块原样存活。

### 6.3 字段归属：两边都留，但重叠字段只存一份

**策略（2026-09-18 定）：两边的格式都保留，以后实际使用中再按需裁剪。** 这对互不重叠的字段完全成立，对重叠字段需要一条规则。

| 类别 | 数量 | 放哪 | 说明 |
|---|---|---|---|
| **Taskfold 独有** | 14 | `<!-- SECTION:TASKFOLD -->` 区块 | `kind` `notes` `sessionKey` `runId` `taskId` `sourceUrl` `execution` `delivery` `sourceReferences` `revision` `startedAt` `completedAt` `events` `metadata`（`contract/index.ts:530-561`） |
| **Backlog.md 独有** | 11 | frontmatter | `reporter` `due_date` `dependencies` `references` `documentation` `modified_files` `parent_task_id` `subtasks` `type` `project` `onStatusChange`。Taskfold 不使用但**原样保留**，不得在写回时丢弃 |
| **两边重叠** | 10 | frontmatter，**只存一份** | 见下表 |

**重叠字段一律采用 Backlog.md 的写法，Taskfold 在读写时做映射：**

| 概念 | Taskfold 内部 | 文件里（Backlog.md 写法） | 差异 |
|---|---|---|---|
| 标题 | `title` | `title` | 一致 |
| 标签 | `labels` | `labels` | 一致 |
| ID | `id`（UUID） | `id`（`card-42`）；UUID 移入 TASKFOLD 区块 | 格式 |
| 状态 | `status`（9 个 lowercase） | `status`；`config.yml` 配齐同样 9 个 | 值域 |
| 优先级 | `priority`（必填） | `priority`（可选） | 基数 |
| 里程碑 | `milestoneId` | `milestone` | 命名 |
| 负责人 | `agentId?`（单个） | `assignee[]`（数组，取首元素） | 命名 + 基数 |
| 创建时间 | `createdAt`（epoch 毫秒） | `created_date`（`'2026-09-18 10:23'`） | **格式** |
| 更新时间 | `updatedAt`（epoch 毫秒） | `updated_date`（同上） | **格式** |
| 排序 | `position`（REAL，如 1024.5） | `ordinal`（整数） | 命名 + 语义 |

> **为什么重叠字段不能两边各存一份**：`backlog task edit` 会更新 `created_date` 而**完全不碰** `createdAt`（它不认识这个键）；Taskfold 改则反过来。两个值会持续漂移，最终谁也无法判定哪个准。这正是 [[1-规划评审]] P0 表已经否决过的「双向权威」。
>
> 映射层只涉及这 10 个字段，是一层薄的读写转换，业务代码无感。**将来要撤掉 Backlog.md 兼容时，去掉映射层即可**——比清理两套已经漂移的数据干净得多。

**裁剪机制**：用户的策略是"用一段时间后一点点删"。为此在 `taskfold doctor` 里加一项**字段使用统计**（各字段的非空卡片数），给裁剪提供依据，而不是凭印象删。

## 七、卡片 ID 分配设计

选了可读递增 ID 就得有分配器。Backlog.md 为此写了一整套（跨分支扫描 + 锁 + doctor 修复），**Taskfold 的冲突域小得多，可以大幅简化**。

| 环节 | Backlog.md | Taskfold（A1 + B2 下） |
|---|---|---|
| 冲突域 | 本地 + 所有 worktree + 本地所有分支 + `git fetch` 后的远程分支 | **单个项目的 `.taskfold/cards/` + `archive/cards/`** |
| 分配算法 | `BigInt` 扫最大编号 +1（`prefix-config.ts:305-340`） | **同左：扫目录取最大 +1**，数量级小无需 BigInt。**不得用 `config.yml` 里的计数器**，理由见下 |
| 互斥 | `proper-lockfile`，锁放 git common dir（多 worktree 共享） | **不需要**。A1 下进程内 `enqueueMutation` 已串行化 |
| 兜底 | `backlog doctor --fix` 扫重复 ID、原子重命名 | `taskfold doctor` 加同款检查（第八节第 2 期） |
| ID 回收 | archive 可回收、completed 永久保留 | **不回收（已定）**：ID 只是展示层，UUID 才是主键，回收带来的复杂度不值得 |

> **为什么不能用计数器**：兼容档下 `backlog task create` 也会在同一个目录里建卡片，**它不知道也不会更新 Taskfold 的计数器**。用计数器必然撞号；扫目录则天然把两边创建的卡片都算进去。这是兼容档对 ID 分配的硬约束。

**改标题时重命名文件**（抄 Backlog.md），文件名标题段需 sanitize 掉路径非法字符。

**将来启用 worktree 执行时要补的**：把锁放到 git common dir 下（`<repo>/.git/taskfold/locks/`），冲突域扩展到所有 worktree。这两条 Backlog.md 有现成实现（`operations.ts:614-632`、`backlog.ts:1500-1514`）。见第九节风险 R1。

## 九、风险登记

### R1：worktree 里的卡片数据副本（已知，当前不触发）

**触发条件**：启用 worktree 执行（`materializeWorktree` 传 true，且卡片 `metadata.automation.workspace.kind === "worktree"`）。当前**默认 false**（`dispatcher.ts:444`；workspace 三种 kind 的定义见 `contract/index.ts:328-334`），所以现在不触发。

**表现**：`.taskfold/` 入库后会被 `git worktree add` 整个 checkout 一份到 worktree 里。agent 收尾若 `git add -A`，会把创建 worktree 那一刻的**过期卡片快照**一并提交；合并回主分支时与已变更 N 次的卡片状态冲突。

> ⚠️ **这不是并发写问题**（写入者只有 Gateway 一个），是 git 在机械复制被跟踪文件。

**Backlog.md 处理了什么、没处理什么**——不要误判：

| | |
|---|---|
| ✅ 它处理了 | ID 冲突域含所有 worktree（`backlog.ts:1500-1514`）；锁放 git common dir 多 worktree 共享（`operations.ts:614-632`）；跨分支读取时 `chooseWinners` 按 `most_progressed` 选赢家（`task-loader.ts:262-322`） |
| ❌ 它**没有**处理 | 合并冲突本身。它的 `backlog/` 同样入库、同样每个 worktree 一份副本，两个分支改同一个任务文件照样 `git merge` 冲突要人工解。它是**接受副本存在**再在读侧选赢家，不是消除副本 |

**三条现成解法**（触发时再选，不必现在定）：

1. worktree 创建后 sparse-checkout 排除 `.taskfold/` —— 需先验证宿主 `worktrees.create()` 是否支持
2. 改放 `<repo>/.git/taskfold/` —— common dir 天然单份共享，零冲突，代价是不入库
3. `.taskfold/` 加 gitignore —— 无冲突，但 worktree 里看不到卡片数据，也失去版本化

### R2：Git 历史被状态流水刷屏

卡片状态由机器高频写入（claim 心跳默认 TTL 30 分钟、reconciler 每 15 秒扫描）。入库后每次状态变更都是一次文件改动。**若将来启用自动提交，历史会被淹没**。Backlog.md 的应对是 `autoCommit` 默认 `false`，把提交时机交给人——建议照抄。

### R3 / R4：外部写入者绕过 revision 与 change cursor ★

**这是排错时发现的实质遗漏，不是边缘情况——它是"A1 单进程"与"兼容 Backlog.md"两个已定决策之间的直接冲突。**

A1 以"只有一个 Gateway 进程"为由，去掉了原来 `PRAGMA data_version` 每秒轮询的外部变更感知（`change-events.ts`）。但兼容档从另一个方向把外部写入者请了回来，而且是**预期中的正常用法**：

| 外部写入者 | 后果 |
|---|---|
| `backlog task edit` / `backlog task create` | 不更新 TASKFOLD 区块里的 `revision` → Taskfold 的 CAS **看不到这次修改**；不写 `changes.log` → **UI 不会刷新** |
| 人手工编辑 `.md` 文件 | 同上（原 R3） |
| `git checkout` 切分支、`git pull` | 整批卡片文件被替换，Taskfold 完全无感 |

**光靠 `doctor` 事后体检不够**——UI 不刷新是即时可见的功能缺陷，不是数据体检问题。

**必须补外部变更检测，两条路（第 1 期选一条落地）：**

1. **`fs.watch` 监听**（抄 Backlog.md 的 `ContentStore`，`content-store.ts:126-133,163-166`）：监听 `.taskfold/cards/` 与 `config.yml`，变化时重解析、重盖 `revision`、追加 `changes.log`。响应快，但平台差异需实测。
2. **mtime 轮询**：成本低、实现简单，代价是延迟。可作为 `fs.watch` 不可靠时的兜底。

**重盖 revision 是必须的**：`stampCardRevisions()`（`store-core.ts:106-131`）的语义是"每次持久化写入都递增"，外部写入没经过它。检测到外部变更后须由 Taskfold 补盖一次，否则 D1 的 CAS 会基于一个过期的 revision 做判断。

> 这条实际上把 A1 省下的工作量还回去了一部分——但省的是"跨进程写互斥"（复杂），补的是"外部读感知"（简单）。净收益仍然为正。

> ⚠️ **「UI 20 / 数据库 21」这条差异是基线的一部分，不是 bug**：UI 默认过滤归档卡。迁移后若这两个数字变成相等，说明归档过滤逻辑丢了。

**迁移后必须逐条对照的 UI 行为**：

1. 上表每一个数字与列名完全一致
2. 归档过滤：勾选"包含已归档"后项目数从 3 变 4

4. 长轮询刷新：改一张卡后另一个标签页自动更新（验证 E2 的 `changes.log` 接线）
5. **外部写入感知（R4）**：用 `backlog task edit` 改一张卡后，UI 应当自动刷新——**这是 R4 唯一的端到端验收手段**
6. 控制台无新增错误

**脚本落位**：这三个侦察脚本是一次性的，正式实现时应固化为仓库内的 e2e 测试，随第 1 期一起交付。
