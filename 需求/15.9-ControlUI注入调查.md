## Q1：`controlUi` 段的生成/校验是否强绑定 `defineToolPlugin()`

**结论：运行时契约不绑定；官方 CLI 工具链（`openclaw plugins build`/`validate`）绑定，但那是 CLI 命令自身把两件事捆在一起做的实现选择，不是 `controlUi` 能力本身的要求。Taskfold 可以完全绕开 `defineToolPlugin` 和 `openclaw plugins build`，自己产出符合契约的构建物。**

证据链：

1. 上游 `extensions/workboard/index.ts:2,21`（后端入口）用的是 `import { definePluginEntry } from "./api.js"` + `export default definePluginEntry({...})`——跟 Taskfold 现在的写法完全一样，**不是** `defineToolPlugin`。这确认 stock workboard 本身也没有切换到声明式写法。
2. 但 `extensions/workboard/browser/index.ts:1,15,17` 是完全独立的另一套注册体系：`import { defineControlUiPlugin } from "openclaw/plugin-sdk/control-ui"` + `export default defineControlUiPlugin({ id: "workboard", activate(host) {...} })`。`defineControlUiPlugin` 只关心前端入口的形状，与后端用什么方式注册无关。
3. `~/.nvm/versions/node/v24.21.0/lib/node_modules/openclaw/dist/plugins-authoring-command-Dgab1p7G.mjs:110-158`（region `src/cli/plugins-control-ui-build.ts`）里有函数 `buildPluginControlUi(params)`——这是 `openclaw plugins build` 内部实际调用的、构建 controlUi 产物的原语：
   - 用 esbuild 风格的 `buildPluginBundle({absWorkingDir, entryPoints, outdir, platform:"browser", target:"es2022", minify:true, tsconfigRaw:{experimentalDecorators:true,...}})` 打包 `params.source` 指向的入口文件；
   - 产物限制：只能是 `index.js`（必须）+ 可选 `index.css`，单文件 ≤4MiB，总量 ≤8MiB；
   - 对内容做 sha256，写到 `dist/control-ui/<hash>/`，返回 `{entry, styles}`；
   - **全程没有读取任何 `defineToolPlugin` 的元数据**，纯粹是"打包 + 写路径"。
4. 但 `runPluginsBuildCommand`（同文件 `:494-534`）和 `collectPluginsValidationResult`（`:535-577`）在调用 `buildPluginControlUi` **之前**，先无条件执行 `const { metadata } = await loadToolPlugin({ rootDir, entryPath })`（`:424-430`）。`loadToolPlugin` 里 `getToolPluginMetadata(entry)` 找不到声明式元数据就直接 `throw new Error("plugin entry does not expose tool or feature authoring metadata")`。也就是说：**`openclaw plugins build`/`validate` 这两个公开 CLI 命令确实因为自身实现顺序，要求后端入口必须是 `defineToolPlugin`/`defineFeaturePlugin`**，这与需求文档「三、评估过但不做」一节此前的结论完全吻合，且现在有了具体行号证据。
5. 宿主在**运行时加载插件**时如何处理 `controlUi` 字段，是完全独立的另一条代码路径，和上面的 CLI 完全无关：
   - `manifest-BRq2TbZH.mjs:814-830`（`normalizeManifestControlUi`）：只对 `openclaw.plugin.json` 里静态的 `controlUi.entry`/`styles` 字段做正则校验，不读取、不关心插件是用什么方式写的后端入口。
   - `control-ui-assets-Chx5wPxj.mjs:8-40`（`readPluginControlUiAssets`）：直接从插件 `rootDir` 磁盘读取 `entry` 所在目录下的 `.js`/`.mjs`/`.css` 文件（≤128 个，≤4MiB/个，≤8MiB 总量），不关心这些文件是被 esbuild、Vite 还是手写出来的。
   - `control-ui-plugin-assets-BR1PXkvy.mjs:37-100`（`snapshotBrowserBuild`/`refreshBrowserCatalog`）：以文件字节的 sha256 作为 revision，动态提供 HTTP 服务；同样不关心构建工具。

**给出的实操结论**：Taskfold 保持现有 `definePluginEntry`+`register(api)` 写法完全可以拿到原生注入能力，唯一代价是**不能用 `openclaw plugins build` 自动生成/校验 `controlUi` 段**（正如现在也不能用它生成 `contracts.tools` 一样），需要自己写一份等价的构建脚本，并像现在手工维护整份 `openclaw.plugin.json` 一样手工/脚本化维护 `controlUi` 字段。这不是新增的负担类别，只是把已经存在的"手工维护 manifest"范围扩大一点。

## Q2：宿主侧注入的确切契约

**契约来源**：`~/.nvm/versions/node/v24.21.0/lib/node_modules/openclaw/dist/plugin-sdk/control-ui.d.ts`（Taskfold 目前的 devDependency `openclaw@2026.7.1-2` 完全没有导出这个模块，见 Q5）。

- 产物形态：ESM 模块，默认导出一个满足 `ControlUiPlugin = { id: string; activate: (host: ControlUiHost) => void | ControlUiDisposer | Promise<void|ControlUiDisposer> }`（`control-ui.d.ts:259-264`）的对象。`defineControlUiPlugin(plugin)`（`:264`）从实际打包产物看几乎是恒等函数——上游打包后的 `dist/control-ui/07dd.../index.js`（878258 字节，用 `wc -c` 实测，和文档提到的"858K"量级吻合）尾部直接是 `var ryt={id:"workboard",activate(e){...}};export{ryt as default}`，看不到任何包裹逻辑。
- **不强制 Lit**：`ControlUiPlugin`/`ControlUiHost` 类型定义里没有任何 Lit/框架相关的字样；上游选 Lit 只是它自己的选择，产物里把 Lit **整份内联打包进去**（`grep -c "^import"` 结果为 0，即成品 zero external import；`grep "LitElement"` 命中 2 次，说明 Lit 源码被打进了这个文件本身，宿主并不提供全局 Lit）。因此 Taskfold 继续用 Lit（`package.json` 已依赖 `lit@^3.3.0`）没有任何障碍，但也没有"必须用 Lit"的强制要求，理论上换任何能编译成自包含 ESM 的框架都行。
- `host.request<T>(method, params)`（`control-ui.d.ts:212`）是核心数据通道，见 Q3。
- `ControlUiHost` 完整暴露的能力面（`control-ui.d.ts:199-262`）：`apiVersion`(固定为1)、`pluginId`、`signal`(AbortSignal，插件生命周期)、`basePath`、`locale`、`redact(text)`、`connection: {connected,canRead,canWrite,canGrant,canAdmin,assistantAgentId}`、`components: {mountDialog, mountAgentPicker, mountDashboard}`（宿主原生语义组件，插件可选用而不必自己实现弹窗等）、`request()`、`onEvent()`、`subscribe()`、`sessions: {rows,selectedKey,normalizeKey,refresh,observe,open,create,patch}`、`agents: {rows,selectedId,defaultId,scopeId,select,setScope,refresh}`、`navigation: {openPage,pageHref}`、`ui: {invalidate,registerPage,registerNavigation,registerPanel,registerAction,registerAccessory(:253),registerWidget,registerReplacement,selectReplacement}`。
- 权限/信任闸门（**这是本次调查里最关键的新发现，直接影响可行性判断**）：`~/.nvm/versions/node/v24.21.0/lib/node_modules/openclaw/dist/github-user-identity-D1LIz6kl.mjs:42-44`：
  ```js
  function isControlUiPluginAllowed(plugin) {
    return plugin.origin === "bundled" || getRuntimeConfigSnapshot()?.gateway?.controlUi?.experimental?.customPlugins === true;
  }
  ```
  同文件 `:41` 定义了拒绝时的提示语：`"Custom plugin UI is disabled. Enable Custom plugin UI in Settings > Labs, restart the Gateway, and reload this page."`。`schema-DbKC3IUo.mjs:823` 给出该开关的官方描述：*"Allow user-installed plugins to execute native JavaScript in the Control UI (default: false). Bundled plugin views remain available. Custom UI shares the signed-in operator's Gateway permissions; enable only for trusted plugins."*
  实测本机：`openclaw plugins inspect taskfold` 输出 `Origin: config`（不是 `bundled`）。`PluginOrigin` 类型（`~/.nvm/versions/node/v24.21.0/lib/node_modules/openclaw/dist/plugin-origin.types-DOQEvsWL.d.ts`）只有四个取值：`"bundled" | "global" | "workspace" | "config"`。**只有打包进 openclaw 核心本身（stock workboard 那种）才是 `bundled`；Taskfold 现在是 `config`，将来即便发布到 npm/ClawHub 也只会变成 `global`，永远拿不到 `bundled`，因此永远需要这个实验开关。**
- 资源响应头（`control-ui-plugin-assets-BR1PXkvy.mjs:219-224`）：`Content-Type`、`Content-Length`、`Cache-Control: private, no-cache`、`X-Content-Type-Options: nosniff`。没有观察到显式的 CSP 头（可能由宿主页面本身的 CSP 统一约束，本次未继续深挖，见「未能确证的问题」）。经验证据是上游产物零外部 import、Lit 全部内联，建议 Taskfold 照做（自包含 bundle），不要假设宿主会提供任何全局依赖（包括 Lit）。

## Q3：注入后的数据通道

**结论：彻底证实——原生注入下插件前端不再需要（也不应该）自己开 WebSocket，全部请求走宿主注入的 `host.request()`，复用宿主早已认证好的那条连接。**

- `extensions/workboard/browser/api/gateway.ts:1-16`：
  ```ts
  export type GatewayBrowserClient = {
    request: ControlUiHost["request"];
    addEventListener: (listener) => () => void;
  };
  export function createWorkboardClient(host: ControlUiHost): GatewayBrowserClient {
    return {
      request: host.request,                       // 第 11 行：直接引用，不是包装出新连接
      addEventListener: (listener) =>
        host.onEvent(WORKBOARD_CHANGED_EVENT, (payload) => listener({...})),
    };
  }
  ```
  这个"gateway client"总共 26 行，就是对 `host.request`/`host.onEvent` 的薄包装，没有任何 WebSocket、没有 `client.id`、没有身份/握手逻辑。
- 实际调用点（`grep -rn '\.request(\s*"' browser/`）证实业务代码直接用命名空间方法名调用，如 `browser/lib/workboard/mutations.ts:75/81/138/184/221/252/289` 的 `workboard.cards.update/create/comment/move/delete/archive/list`，以及 `browser/lib/workboard/execution.ts:160/171/182` 里跨插件命名空间的 `chat.abort`、`tasks.cancel`——`control-ui.d.ts:212` 注释原话："Native modules share the operator's authenticated Gateway authority. The Gateway enforces connection scopes, not a per-plugin RPC allowlist."，即插件不但能调自己的方法，还能调操作员权限范围内的任何宿主方法。
- 反向证实：VERIFICATION.md 里记录的 `1008 protocol mismatch` 故障，根因函数 `resolveControlUiBuildMismatch`（`message-handler-BBAGn2rf.mjs:2673`，调用点在 `:2833`）第一行判断条件就是 `params.clientId !== GATEWAY_CLIENT_IDS.CONTROL_UI`——**这个检查只发生在客户端自己发起 WS `connect` 且声明 `client.id === "openclaw-control-ui"` 的场景下**。原生注入的插件代码根本不会执行任何 `connect` 握手（它拿到的 `host` 对象背后是宿主壳自己那条已经连上的会话），这一整类"借用身份连接 / buildId 校验 / 1008 拒绝"的问题在架构上直接消失，不是被绕过而是从不发生。
- 对 `ui/src/gateway-client.ts`（405 行：ed25519 设备身份签名、`DeviceTokenStore`、`client.id: "openclaw-control-ui"`（第272行）、`buildId: "dev"`（第284行）、WS 重连逻辑）的处理意见：**整份文件在迁移后变成死代码，直接删除**，被等价于 workboard `browser/api/gateway.ts` 那样 26 行左右的薄包装取代（甚至可以内联进入口文件，不必单独立一个文件）。`client.id: "openclaw-control-ui"` 这个借用身份的做法可以彻底去掉——不是"改成另一个身份"，而是"根本不再需要任何身份，因为不再自己握手"。

## Q5：拦路的坑

1. **`files` 白名单与产物目录**：`package.json:24-26` 现有 `"files": ["dist/", "ui/dist/", ...]`。宿主运行时对 `openclaw.plugin.json` 的 `controlUi` 字段有硬编码正则校验（`manifest-BRq2TbZH.mjs:820`）：
   ```
   entry 必须匹配 ^dist\/(?:[\w-][\w.-]*\/)+[\w-][\w.-]*\.m?js$
   ```
   即**必须以字面量 `dist/` 开头，且至少嵌套一层子目录**（如 `dist/control-ui/index.js` 合法，`dist/index.js` 或 `ui/dist/index.js` 都不合法）。`styles`（`:826`）还必须和 `entry` 在同一目录（`assetPrefix = entry.slice(0, entry.lastIndexOf("/")+1)`）、≤16个、`.css`。**这意味着 controlUi 构建产物必须搬到顶层 `dist/` 目录下（与后端 esbuild 产物同级），不能继续放在 `ui/dist/` 下**。好消息是 `dist/` 已经在 `files` 白名单里，迁移完成后只需要把 `"ui/dist/"` 那一行删掉，不需要新增条目。

2. **`build:ui` 链路不必照抄上游脚本**：`package.json:37` 现有 `"build:ui": "vite build --config ui/vite.config.ts"`。上游 `assetScripts.build`（`extensions/workboard/package.json`）跑的是 `node --import ../../scripts/tsx.mjs ../../scripts/build-plugin-control-ui.mts`——`../../scripts/` 相对 `extensions/workboard/` 就是 openclaw **monorepo 根目录**的 `scripts/`，这是仓库内部工具，**不随 npm 包分发**（已确认：`~/.nvm/versions/node/v24.21.0/lib/node_modules/openclaw/scripts/` 目录里只有面向终端用户的安装脚本，没有这个文件；tpm 快照因为是 sparse checkout 只包含 `extensions/workboard/`，同样没有仓库根目录）。**Taskfold 拿不到、也不需要拿到这个脚本本身**——Q1 已经证实它调用的底层能力（`buildPluginControlUi`，`plugins-authoring-command-Dgab1p7G.mjs:110-158`）就是一个通用的 esbuild 打包 + 写回 manifest 的动作，跟 `defineToolPlugin` 无关。**可行性评估：完全可行**——Taskfold 可以用已有的 esbuild（`package.json:36` 打后端包已经在用）或继续用 Vite（`ui/vite.config.ts` 已有）写一份等价配置，产物落在 `dist/control-ui/`，用一个几十行的小脚本把 `{entry, styles}` 写进 `openclaw.plugin.json` 的 `controlUi` 字段，完全不需要 `openclaw plugins build`（该命令会先跑 `loadToolPlugin()` 校验 `defineToolPlugin`，对 `definePluginEntry` 风格的 Taskfold 必然失败，见 Q1 第4点）。

## 可行性判定

**有条件可行**，条件如下：

1. **必须让终端用户额外打开一个新的手动配置项**：`gateway.controlUi.experimental.customPlugins: true`（Settings > Labs > Custom plugin UI），并重启 Gateway、刷新浏览器标签页。这不是"去掉 embedSandbox 之后就不再需要任何手动配置"，而是**用一个全局性、影响面更大的实验开关，替换掉一个只影响 Taskfold 自己 iframe 的开关**。原因见 Q2：`isControlUiPluginAllowed()` 只放行 `origin==="bundled"`（即打包进 openclaw 核心本身的插件）或该实验开关打开的情况；本机实测 `openclaw plugins inspect taskfold` 的 `Origin` 是 `config`，不是 `bundled`，且这个结论不会因为 Taskfold 未来发布到 npm/ClawHub、变成"受信任的官方插件"而改变（`PluginOrigin` 四个取值里，npm 全局安装对应的是 `global`，同样不豁免）。**这一点应该写进 README 和面向用户的迁移说明，而不能重复需求文档第130行"没有身份限制"这个说法**（该说法只对"借用连接身份"这一件事成立，对"能否原生注入"这件事不成立）。

3. 构建工具不依赖上游 `build-plugin-control-ui.mts`/`openclaw plugins build`，Taskfold 可以自己写等价的 esbuild/Vite 配置 + 一个写回 manifest 的小脚本，只要满足宿主侧的正则、体积（≤4MiB/文件、≤8MiB/插件总量、≤128个文件、≤16个样式表）与产物形态（自包含 ESM，默认导出 `{id, activate(host)}`）约束。

### 坑 1：同文档注入下 CSS 类名会与宿主壳层撞车

这是迁移中唯一真正咬人的问题。iframe 时代不存在——那时插件有独立文档、独立 CSS 作用域。

表现：`ui/src/host.css` 照搬过去、并已经按 `taskfold-app` 作用域限定之后，"新建项目"按钮仍然白字配浅底、完全不可见。

根因（CDP `CSS.getMatchedStylesForNode` 查明）：

```
taskfold-app .btn--primary            特异性 0-1-1   ← 插件
:root[data-theme-mode="light"] .btn   特异性 0-3-0   ← 宿主核心包，赢
```

宿主壳层自己也用 `.btn`。它抢走 `background`，而 `color` 仍走插件的 `var(--accent-foreground)`——宿主把这个变量定义成白色，于是白字浅底。

**修法必须是给类名加前缀，不能靠提特异性。** 宿主核心包（`control-ui-core-*.css`，不挂路由、每个页面都加载）单文件就有 970 个类名，全量 52 个样式表去重 4535 个，且随版本增长。提特异性只能压过*当前已知*的规则，宿主下个版本加一条更具体的（或带 `!important`）就会无声复发，而且复发时插件这边代码一行没改——这种"有效期不定"的修复不可接受。

实测撞名的类：`btn`、`callout`、`danger`、`is-active`、`is-completed`、`is-error`、`is-selected`。另有一批生成式短类名（`btn--primary`、`priority-*`、`is-*` 系列）当前没撞但极易撞。**特别注意模板里动态拼接的类名**（`` `is-${milestone.state}` ``、`` `priority-${card.priority}` `` 这类），静态 grep 类名列表看不出来，只能读模板。

约定：`browser/` 下新增裸类名一律加 `tf-` 前缀，或走 `taskfold-project__` 的 BEM 命名。

### 坑 2：主题变量可以直接继承，不要本地重定义

与坑 1 相反的一面：`--bg`/`--panel`/`--text`/`--muted`/`--border`/`--accent` 这些共享色板 token 由宿主 `:root` 提供，同文档下天然继承，实测全部拿到正确值。插件**不该**本地重新定义它们（那会和宿主主题切换打架）。只有插件独有的 token（Taskfold 的 `--warn`/`--info`/`--success`/`--duration-fast`/`--ease-out`）才本地定义。

iframe 版的 `host-context.ts` 用 `postMessage` 把宿主主题变量搬进 iframe——那整套机制在原生注入下是多余的，已废弃。

### 坑 3：改了产物必须显式刷新宿主缓存

宿主的 Control UI 产物目录（`browserCatalogs`）只在 `state.initialized === false` 或显式 `reloadManifest` 时才从磁盘重读。一旦初始化过，**改磁盘文件不会被感知**，浏览器里看到的还是旧产物——很容易误判成"我的代码没生效"。

刷新命令（UI-only，宿主源码注释原文 "never imports or replaces backend plugin code"，不重启 Gateway、不重载后端）：

```bash
openclaw gateway call plugins.controlUi.reload --params '{"pluginId":"taskfold"}'
```

**补充澄清（第 5 步清理时补做）：官方 `surfaces.md` 示例路径 `dist/control-ui/<content-hash>/index.js` 能否借内容哈希目录让宿主自动感知产物变化、从而免掉上面这条手动 reload？——不能，已读源码证实。**

- `control-ui-plugin-assets-BR1PXkvy.mjs:129-147` 的 `loadControlUiPluginCatalog(pluginId, reloadManifest=false)`：只有 `reloadManifest===true` 或 `!state.initialized`（该插件注册表本次生命周期里第一次建目录）时才会调用 `refreshBrowserCatalog()` 重新读取 manifest 与磁盘文件；`state.initialized` 一旦置真，之后任何请求（包括新开一个浏览器标签页）都直接复用已缓存的 `state.builds`/`state.revisions`，**根本不会重新读 `openclaw.plugin.json`，也不会重新 stat 磁盘**。这个判断只看 `reloadManifest` 这个布尔参数，和 `controlUi.entry` 字段的路径字面量长什么样（是否带哈希）完全无关。
- 出现在资源 URL 里的那段哈希（`revision`）是宿主在 `snapshotBrowserBuild()`（同文件 `:41-66`）里对当次读到的文件字节**现算**的 sha256，不是从磁盘目录名读出来的——即使把 `controlUi.entry` 改指向一个新的哈希子目录，只要 `state.initialized` 仍为 true 且没人传 `reloadManifest:true`，宿主连读这个新路径的机会都没有。
- 官方文档原话也印证了这一点：`surfaces.md`「controlUi reference」写的是 *"Assets follow the Gateway's authentication policy, are captured as immutable revisions, **and refresh only through the explicit UI reload flow**."*——官方自己就说刷新只有这一条路径。上游示例路径带 content-hash，更像是 `openclaw plugins build` 这个 CLI 自己按内容寻址组织构建产物（避免不同次构建的文件互相覆盖／便于缓存），是构建工具的组织习惯，跟宿主运行时"什么时候失效缓存"是两件事，不能从示例路径反推出后者。

**结论：不需要改造 `scripts/build-control-ui.mjs` 去产出 content-hash 目录，改了也不会免掉 `openclaw gateway call plugins.controlUi.reload` 这一步。** 继续用现有固定路径 `dist/control-ui/index.js` 即可，第 5 步未对构建脚本做此调整。

### 坑 4：`host.onEvent` 需要后端主动广播，不是白拿的

迁移长轮询时发现 `TASKFOLD_CHANGED_EVENT`（`src/contract/index.ts:321`）是**死代码**——全仓只有定义，后端从未 emit，所以 iframe 版 `main.ts` 里那个 `onEvent` 分支从来没触发过。

上游 workboard 能用 `host.onEvent(WORKBOARD_CHANGED_EVENT, …)`，是因为它后端有专门的 service 调 `ctx.gatewayEvents.emit("changed", change, {scope:"operator.read"})` 主动广播到 Gateway 事件通道。Taskfold 的 `store-change-tracker.ts` 只是个纯内存 EventEmitter，仅用于唤醒 `store.waitForChange()`，不出进程。

所以 `taskfold.changes.wait` 的 25 秒长轮询继续用 `host.request` 是当前唯一正确解。要换成事件推送，得先给后端加广播能力——那是独立一项工作。
