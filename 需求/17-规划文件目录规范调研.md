# 17 AI 规划文件目录规范调研

> **调研结论（2026-09-18）。** 回答一个问题：AI 辅助开发里的"规划 / 规格 / 任务文件"，业界有没有统一的目录命名规范可以遵循？
>
> 跨主题请从 [[README]] 进入。本文是**外部事实调研**，不含 Taskfold 的决策；对 Taskfold 的影响见第六节，作为 [[16-文件存储改造]] 分叉 B / C 的输入。
>
> 数据获取时间 **2026-09-18**（star 数等会变动的数字均以此时间为准）。信息源：各项目官方仓库与文档、GitHub API 实测、HN Algolia API。

## 一、结论先行

**没有统一标准，短期内也不会有。** 现状是"一层有共识、一层是战国"：

| 层 | 状态 | 收敛到什么 |
|---|---|---|
| **给 agent 看的项目说明文件** | ✅ 已收敛 | `AGENTS.md`。2025-12-09 随 MCP、goose 一起捐给 Linux Foundation 旗下 **Agentic AI Foundation**（联合创始：Anthropic、Block、OpenAI） |
| **规划 / 规格 / 任务的目录布局** | ❌ 战国，且**各家刻意不趋同** | 无。每家目录根、文件名、颗粒度都不同 |

**"刻意"这两个字是关键**：目录约定是这些工具彼此的产品差异化卖点，不是技术上没解决。OpenSpec 的 README 直接拿"vs Spec Kit：笨重、门禁死板"当广告词。**没人想统一。**

唯一的跨工具中立提案（`.agents/rules/` RFC，`aicodingrules.org`）只覆盖"规则"层，且基本无人采用——`agent-rules-spec` 仓库只有 2 星。针对"规划/spec 目录"本身，调研范围内**没有找到任何跨厂商 RFC 或标准化提案**；搜到的所有横向对比都是"帮你选一个"的评测，不是"帮你统一"的规范。

> ⚠️ 这一条是**基于搜索范围的推断**，不能排除有更小众的提案未被搜到。

## 三、唯一的隐性收敛：三段式

概念层面确实有事实趋同——几乎所有方案的产出物都能映射到同一个三段式：

| 方案 | 需求/规格 | 设计/计划 | 任务 |
|---|---|---|---|
| Spec Kit | `spec.md` | `plan.md` | `tasks.md` |
| Kiro | `requirements.md` | `design.md` | `tasks.md` |
| OpenSpec | `proposal.md` + `specs/` | `design.md` | `tasks.md` |
| BMAD v6 | `SPEC.md` | — | `stories.yaml` |

**文件名和目录根完全没趋同，但"先定要什么、再定怎么做、最后拆成可执行项"这个顺序趋同了。** 抄这个模式（而不是抄某一家的具体目录）风险最低。

> 这是基于多个仓库实际目录树归纳的推断，可视为较可靠。

## 四、入库 vs gitignore：这一条有明确共识

**7/7 主流方案一致主张规划文件入库。** 唯一被 gitignore 的是"机器本地状态指针"：Spec Kit 的 `feature.json`（当前功能指针）、本地密钥、本地覆盖配置。

网上流传的"plans/ 应该 gitignore、只 commit specs/"出自个人 dotfiles PR，**不是主流工具的做法**。

## 五、社区态度：没人在吵目录，大家在吵 SDD 本身

HN 实测（2026-09-18 via Algolia API）：

| 标题 | 分数/评论 | 日期 |
|---|---|---|
| AGENTS.md – Open format for guiding coding agents | 837 / 382 | 2025-08-20 |
| AGENTS.md outperforms skills in our agent evals | 524 / 196 | 2026-01-29 |
| My agent.md to improve LLM-assisted code quality | 415 / 176 | 2026-08-23 |
| Evaluating AGENTS.md: are they helpful for coding agents? | 232 / 161 | 2026-02-16 |
| **Spec-Driven Development: The Waterfall Strikes Back** | 225 / 191 | 2025-11-15 |
| Verified Spec-Driven Development (VSDD) | 211 / 118 | 2026-02-28 |
| OpenSpec – A lightweight and configurable AI spec framework | 194 / 98 | 2026-09-16 |

**关键观察：调研范围内没有找到任何一条高赞评论呼吁"应该统一目录结构"。** 社区吵的是更根本的东西：

- "工作流对每个人都太具体了……我有自己完善的框架"——印证人人自建一套
- "我完全放弃了规范部分……**代码就是规范**"——质疑维护独立 spec 文档的价值本身
- 主张反过来做：让 LLM 读代码实时生成规范，任何与代码不同步的规范都是**负债**
- "世界很复杂，每种解决方案都有其受众"——"不需要统一"的多数派
- 对 Kiro 流程的批评："用大锤砸核桃"（一个小 bug 被展开成 4 个用户故事、16 条验收标准）

还有一篇 225 赞的《Spec-Driven Development: The Waterfall Strikes Back》，直接把 SDD 类比成瀑布模型复辟。

### 反直觉的效果研究

- **ETH Zurich + LogicStar.ai**（arXiv:2602.11988，2026-02）：无论 LLM 生成还是人工编写的 `AGENTS.md`，**普遍不能提升任务成功率，反而平均增加 20% 以上推理成本**。
- arXiv:2605.10039（2026-05，作者 Damon McMillan）：对 1,650 个 Claude Code 会话做因子实验，文件大小/位置/结构/矛盾这 4 个变量对指令遵循度**均无可检测影响**；唯一显著效应是"会话内每多一个函数调用，合规度下降约 5.6%"。
  > ⚠️ **这篇常被误传为 ETH Zurich 的研究，实际不是。** 引用时注意区分。

社区结论性的一句话（HN 142 赞标题）："好的 AGENTS.md 是一次模型升级，差的比没有文档更糟。"——**文件本身不是关键，写法才是。**

## 六、对 Taskfold 的影响

### 6.1 没有标准可抄，这反而简化了 [[16-文件存储改造]] 的分叉 B / C

既然不存在"遵循它就对了"的规范，卡片文件的目录布局就**纯按自己的需求定**，不必为兼容某家而扭曲设计。可抄的只有模式，不是具体路径：

- **入库这条有共识**（第四节 7/7）——这是分叉 B 选 B2/B3 的一个正面论据，但不是决定性的：那 7 家存的是"规格文档"，Taskfold 存的是**看板状态 + 执行账本**，性质不同。执行账本跟着分支走会失真（[[7-数据与接口]] 铁律 4 已经点出度量时间序列的问题）。
- **Backlog.md 的 `<prefix>-<id> - <Title>.md` 命名**是分叉 C 选 C2 时的直接参照。
- **归档目录分离**（`archive/` 与 `completed/` 分开、ID 回收规则不同）是多家共有的模式，值得抄。

### 6.2 一个产品层的观察

Taskfold 如果将来要读别人的规划文件（[[8.5-流程规划与Skills增强]] 方向），会一头撞进这个碎片化——**9 种目录根、各自的文件格式**。这不是存储改造要解决的问题，但在做产品规划时要知道：**"通用规划文件读取器"不是一个能做完的功能。** 要么只支持 GSD `.planning/`（现有路线），要么定义一个明确的白名单。

### 6.3 本仓库 `需求/` 目录自己

本仓库用的是中文数字编号（`1-规划评审.md` … `17-*.md`）+ `[[wiki 链接]]`，不符合上述任何一家。**这没有问题**——第一节的结论就是没有标准可违反。而且这套约定有一个实际优点：`15.7` / `15.8` / `15.9` / `15.10` 这种子编号能表达"同一个调查的分支"，上述方案里只有 OpenSpec 的 `changes/` 有类似表达力。

不建议为了"向业界看齐"改造 `需求/` 目录——BMAD-METHOD 半年内把自己的目录约定整体推翻重写了一次（v4/v5 的 `docs/` → v6 的 `_bmad/`），跟风的成本是实打实的。

## 七、给"选一个不容易被淘汰的约定"的三条建议

均为**基于证据的推断**，非官方定论：

1. **规划文件入库**——7/7 主流方案的一致选择，gitignore 规划文件是极少数派。
2. **抄"spec → plan/design → tasks"三段式命名**，不必抄任何一家的具体目录根。这是概念层面最接近事实标准的东西。
3. **不要等统一标准出现再动手**——从社区态度和 BMAD-METHOD 自我推翻的例子看，这个领域还在快速演化。**"选一个够用的、自己稳定住"比"等标准"更现实。**
