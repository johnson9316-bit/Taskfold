「科学度量」要落到具体指标，否则是空话。指标由 `events`、`run_events` 与文件投影计算；`metric_snapshots` 只保存每日时间序列，不维护另一套业务真相。

| 指标 | 定义 | 用途 |
|------|------|------|
| **燃尽图** | 当前重点剩余点数 / 天 | 当前计划健康度 |
| **累积流图 CFD** | 各状态工作项数 / 天 | 识别瓶颈环节 |
| **周期时间 Cycle Time** | `doing` → `done` 耗时 | 交付效率 |
| **前置时间 Lead Time** | 创建 → `done` 耗时 | 端到端响应速度 |
| **吞吐量 Throughput** | 滚动 14 天完成项数 | 个人交付节奏 |
| **速率 Velocity** | 滚动 14 天完成点数 | 当前重点规划的参考，不作为团队容量承诺 |
| **缺陷密度** | bug 数 / 完成故事点 | 质量 |
| **缺陷逃逸率** | 上线后发现 bug / 总 bug | 测试有效性 |
| **阻塞时长** | `blocked` 累计停留 | 个人执行卡点 |
| **需求交付周期** | `inbox` → `done` | 需求管理全景 |
| **范围变更率** | 当前重点中途增删项 / 初始重点项 | 计划质量（[[3-需求与工作管理]]） |

**GSD 专属指标（v0.6 新增，其他看板给不出的）**：

| 指标 | 定义 | 用途 |
|------|------|------|
| **阶段停留分布** | 各 GSD 阶段耗时占比 | 看瓶颈在 Discuss（想不清）还是 Execute（做不完） |
| **Verify 返工率** | Verify → Execute 回环次数 / phase 数 | **最有价值的一个**：直接反映 Plan 质量 |
| **Plan 通过率** | plan-checker 一次通过 / 总计划数 | 规划成熟度 |
| **Wave 并行度** | 平均每 wave 的 plan 数 | 拆解粒度是否合理；并行度低说明依赖过密 |
| **Phase 交付周期** | Discuss 起 → Ship 止 | GSD 循环的端到端速度 |
| **上下文重置次数** | 每 phase 的 session 边界数 | 是否频繁被 context rot 打断 |
| **人机操作比** | `events.actor_type` 中 agent 与 human 的比例 | AI 实际承担了多少（[[7-数据与接口]]） |

**执行调度指标（v0.8 新增，来自 `runs` / `run_events`，[[4-执行调度与AI]]）**：

| 指标 | 定义 | 用途 |
|------|------|------|
| **一次成功率** | `done` 的 run / 总 run | 上下文包（[[4-执行调度与AI]]）组装得好不好 |
| **人工介入率** | 进过 `awaiting_human` 的 run / 总 run | **调度层的核心 KPI**：目标是让它降下来，但不是降到 0 |
| **平均等人时长** | `awaiting_human` → 人响应的耗时 | 人是不是瓶颈；巡检（[[4-执行调度与AI]]）该多久跑一次 |
| **介入原因分布** | 按 [[4-执行调度与AI]] 的触发条件分类 | 定位改进点：是提问多、还是权限卡、还是 Verify 老失败 |
| **会话成本** | token / 时长，按 phase 与 work_item 汇总 | 预算与 ROI |
| **中止率** | `aborted` / 总 run | 跑飞的频率 |
| **并发实际值** | 同时 running 的 run 数分布 | `max_concurrent_runs` 该调大还是调小（[[4-执行调度与AI]]） |

> 这些指标的原始数据来自 `.planning/`、`STATE.md` 与 `runs` 表，但**时间序列必须由 taskfold 自己按天快照**——`.planning/` 只存当前状态（[[7-数据与接口]] 铁律 3）。

> 度量红线：**不做人效排名、不按人统计产出**。指标用于改进流程，不用于考核个人。

## 数据设计

### 数据真相（⚠️ v0.6 **调整**：按实体分权，不再一刀切）

**旧决策（v0.1–v0.5）：SQLite 是唯一流程真相，MD 只是正文。** GSD 内化后这条不够用了——GSD 产物是 agent 要读、Git 要版本化的文件，不能降级为「SQLite 的导出」。

**但也不必反过来一刀切。** gsd-core 已 vendor 进本仓库（[[5-技术架构与选型]]），但仍需假设用户或官方工具会改动文件，因此必须**按实体划分真相归属**：

| 实体 | 真相在哪 | 理由 |
|------|---------|------|
| ~~**GSD 产物**：`PROJECT.md`、`REQUIREMENTS.md`、`ROADMAP.md`、`STATE.md`、`phases/**`~~ | ⏸ **本版本暂缓** | GSD 缝合整体推迟（[[1-规划评审]] 决策 6）。原结论（文件、`.planning/` 兼容布局）保留备用，本版本不实现 |
| **taskfold 独有**：卡片、里程碑、个人当前重点、bug、RICE、links、执行者标识 | **文件**（项目仓库 `.taskfold/`，Markdown + frontmatter） | ⚠️ **已改**（[[16-文件存储改造]]）。原结论是 SQLite，理由是"关系型、需组合查询"——实测该理由不成立：全库零 `GROUP BY`、唯一 1 处 JOIN、`list()` 本就是全量读入内存再用 JS 过滤排序 |
| **执行账本**：`runs`、`run_events`<br>**度量历史**：时间序列快照 | **文件**（插件目录 `~/.openclaw/plugins/taskfold/` 下 `runs/`、`metrics/`） | ⚠️ **已改**（[[16-文件存储改造]] 第六节）。**不进项目仓库**：跨项目才能算，且跟着分支走会失真。**transcript 全文仍不存**，只存 `host_ref_kind + host_ref_id` 与可选可恢复会话指针（[[4-执行调度与AI]]、[[14-OpenClaw技能策略]]）。具体文件格式待 M4 设计 |
| **复盘档**（v0.8）：`TIMELINE.md`、`HANDOFF.md` | **文件**（phase 目录下 `runs/`） | 要跟着 phase 一起 Git 版本化、要能被 agent 读；但**不改上游既有文件格式**（[[4-执行调度与AI]]，放置位置待实测 [[6-OpenClaw集成]]） |

**铁律**：

1. **保持 `.planning/` 格式兼容**，即便逻辑已内化。收益：用户既有的 GSD 项目可直接被读取（天然的采纳入口），且与官方 gsd-core 双向互操作。
2. **写 GSD 产物一律经 vendored 的 `gsd-tools.cjs`**，不自己拼 MD —— 免费获得其 `STATE.md.lock` 原子写语义。
3. **文件侧的投影必须可重建** —— `taskfold reindex` 能从 `.planning/` 重算所有 GSD 派生字段。（⚠️ 原文作"重算 SQLite 中的派生列"，载体已改，语义不变。）
4. **taskfold 独有实体是原生数据，不可重建，须备份**（尤其度量时间序列：`.planning/` 只存当前状态，不存时间序列，CFD / 燃尽全靠按天快照）。⚠️ **备份策略需按文件形态重写**：原方案是备份单个 `.sqlite` 文件；改文件后卡片随项目 Git 走反而更安全，但插件目录下的 `runs/`、`metrics/` 无版本控制。**不阻塞当前实施**——度量功能属 M9，现有代码一行未实现（2026-09-18 全量 grep 确认），到 M9 设计度量时一并定备份方式。
5. ⚠️ **本条已反转**（[[16-文件存储改造]] 分叉 B2）：Git 跟 `.planning/`、代码**与 `.taskfold/`**——卡片数据现在要入库。只有插件目录下的项目注册表、`runs/`、`metrics/` 不进任何仓库。
6. **仍要假设文件会被外部改动** —— 用户可能同时装着官方 gsd-core，或手工编辑 MD。需变更检测（[[5-技术架构与选型]]）。

> ⚠️ 这句已过期：现网已有 102 张真实卡片（[[16-文件存储改造]] 5.3 实测），迁移需要迁移器与对账，不再是"零成本"。

### 表结构演进目标（⚠️ 整节作废）

> **本节的 `CREATE TABLE` 规划已随 [[16-文件存储改造]] 整体作废。** 保留原文仅作实体清单与字段语义的参考——哪些实体存在、各自有哪些属性仍然有效，**存储形态一律以 [[16-文件存储改造]] 第六节为准**。

-- 已有（v0.1）

-- 新增 / 改造

links        (from_id, to_id, kind, created_at)
comments     (id, item_id, actor_type, actor_id, body, created_at)
              -- 评论存 taskfold 侧，不写入 .planning/
events       (id, item_id, kind, from_value, to_value, actor_type, actor_id, created_at)
work_items_fts                                            -- FTS5 虚表，全文检索

-- 执行调度（v0.8 新增，[[4-执行调度与AI]]）

             -- watched = 是否纳入每日巡检（[[4-执行调度与AI]]）

              resumable_session_id, -- 可空；仅支持真终端接管的后端提供

`cards` → `work_items` 为改名 + 加列，v0.1 数据可原地迁移。

> **`runs.host_ref_kind + host_ref_id` 是执行账本的外部关联键**：它用于取消、观察和调阅宿主任务。`resumable_session_id` 只在后端确认可接管时写入；`takeover` API 必须据此返回命令或明确返回“该 run 不支持终端接管”。

`events` 扩展 `from_value / to_value / actor_type / actor_id` —— **[[7-数据与接口]] 度量全靠它，这是最优先的 schema 改动**。

工作流定义、自动化规则不入库，走 YAML 文件（人可读、可 Git 版本化）。

### 文件布局（**采用 `.planning/` 兼容布局**）

不再自建一套 MD 目录，直接沿用 GSD 的既定结构（每个项目仓库一份）：

├── config.json             # 工作流配置
├── continue-here.md        # /gsd-pause-work 的会话恢复上下文
└── phases/

**taskfold 自己的文件**（不混入 `.planning/`，避免污染上游格式）：

### 执行者标识与可移植性

**执行者标识**——个人版不建立 `users`、`assignee`、角色或权限系统，但仍要区分人、agent 与系统，才能解释事件、复盘 run 与计算人机操作比。

| 项 | 做法 |
|----|------|
| `events` / `comments` | 使用 `actor_type + actor_id`，不存自由字符串 |
| 人 | 固定标识 `human:local-owner`；M1 仅支持本机所有者 |
| agent | `agent:<backend>:<name>`，例如 `agent:acp:claude-code` |
| 系统 | `system:taskfold`，用于 reindex、自动化和巡检 |
| 多人扩展 | 不预留用户表和角色。若重新立项小团队版，先设计认证、同步、权限与数据迁移，再引入 `users` |

**可移植性**——当前版本是单机个人工具，不为未承诺的团队部署引入 Postgres、权限或同步复杂度。`TaskfoldKeyedStore` 抽象（`src/backend/src/persistence-types.ts:42-64`）只负责隔离存储后端与便于测试——**正是这个抽象让 [[16-文件存储改造]] 只需重写一个文件**；当小团队方向重新立项时，再以实际并发和部署需求评估存储方案。
